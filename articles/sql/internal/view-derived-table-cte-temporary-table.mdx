同じ抽出条件を、派生テーブル、CTE、View、一時テーブルで書けるとき、何を基準に選べばよいのでしょうか。問い合わせの中に名前が欲しいのか、定義を複数のSQLから使いたいのか、ある時点の結果を保存したいのかで選択が変わります。

ここではPostgreSQL 17を対象に、商品の在庫という説明用データで違いを見ます。掲載SQLはPostgreSQL 17.10で実行し、結果と計画を確認しました。MySQLとの違いは最後に範囲を分けて扱います。

## 名前とデータは、いつまで残りますか？

| 形式 | 名前を使える範囲 | 保存するもの |
| --- | --- | --- |
| 派生テーブル | `FROM` のサブクエリを含む問い合わせのスコープ | そのSQLの一部。後続の別SQLから使う表は作りません |
| CTE | `WITH` を含む1つのSQL文と、その中で参照が認められる範囲 | 名前付きの問い合わせ。実行時に中間結果を保持するかは別の判断です |
| 通常のView | 作成後、削除するまで。TEMP viewはセッション内 | 問い合わせの定義。通常のViewは結果を保存しません |
| 一時テーブル | セッション内。`ON COMMIT` で短くすることもできます | 独立した表の行。インデックスを作り、行を更新できます |

派生テーブルとCTEはSQL文内の構造です。通常のViewは定義がDBに残り、参照時にその問い合わせが使われます。Viewの名前が残ることと、結果の行が保存されることを分けて考えます。[PostgreSQL 17: SELECT](https://www.postgresql.org/docs/17/sql-select.html)、[CREATE VIEW](https://www.postgresql.org/docs/17/sql-createview.html)

## 同じ抽出を3通りで書くと、何が変わりますか？

コードは新しいpsql接続で上から続けて実行する構成です。既存表を使わず、最後に `ROLLBACK` します。

```sql
BEGIN;
CREATE TEMP TABLE vt_products (
  id integer PRIMARY KEY,
  status text NOT NULL,
  stock integer NOT NULL
) ON COMMIT DROP;
INSERT INTO vt_products (id, status, stock) VALUES
  (1, 'active', 10), (2, 'active', 20), (3, 'archived', 30);
ANALYZE vt_products;
```

派生テーブルでは、サブクエリの結果に `p` という別名を付けます。

```sql
SELECT p.id, p.stock
FROM (
  SELECT id, stock FROM vt_products WHERE status = 'active'
) AS p
ORDER BY p.id;
```

CTEでは、そのSQL文の中で参照する問い合わせに `vt_selected_products` という名前を付けます。

```sql
WITH vt_selected_products AS (
  SELECT id, stock FROM vt_products WHERE status = 'active'
)
SELECT id, stock FROM vt_selected_products ORDER BY id;
```

Viewでは、定義を保存して、別のSQL文からも名前で参照します。今回は片付けやすいTEMP viewを使います。

```sql
CREATE TEMP VIEW vt_current_products AS
SELECT id, stock FROM vt_products WHERE status = 'active';
SELECT id, stock FROM vt_current_products ORDER BY id;
```

いずれも、この時点では `id` が1・2、`stock` が10・20の2行が期待結果です。CTEの名前は次のSQL文では使えませんが、作成済みのViewは使えます。この違いだけでは、どれが速いかまでは決まりません。

通常のViewは結果を物理的に保存しません。TEMP viewもその点は同じで、「TEMPだから結果をコピーする」という意味ではありません。[PostgreSQL 17: CREATE VIEW](https://www.postgresql.org/docs/17/sql-createview.html)

## 一時テーブルへコピーした後、元の行が変わるとどうなりますか？

ここで、現在の抽出結果を別の表へコピーします。

```sql
CREATE TEMP TABLE vt_snapshot ON COMMIT DROP AS
SELECT id, stock FROM vt_current_products;
CREATE INDEX vt_snapshot_id_idx ON vt_snapshot (id);
ANALYZE vt_snapshot;
SELECT id, stock FROM vt_snapshot ORDER BY id;
```

作成直後の期待結果は同じ2行です。続いて元表の在庫を変え、商品3も公開中にします。

```sql
UPDATE vt_products SET stock = 15 WHERE id = 1;
UPDATE vt_products SET status = 'active' WHERE id = 3;
SELECT id, stock FROM vt_current_products ORDER BY id;
SELECT id, stock FROM vt_snapshot ORDER BY id;
```

View側の期待結果は、`(id, stock)` が `(1, 15)`・`(2, 20)`・`(3, 30)` の3行です。一時テーブル側は作成時の `(1, 10)`・`(2, 20)` のままです。Viewの結果は、その問い合わせから見える元表に基づきます。元表を変更しても、コピー済みの一時テーブルは自動更新されません。[PostgreSQL 17: CREATE TABLE AS](https://www.postgresql.org/docs/17/sql-createtableas.html)

この例は同じトランザクション内の自分自身の更新を読むものです。別接続の変更がいつ見えるかはトランザクションの分離レベルにも関係するので、「Viewなら他の接続の最新値が常に見える」とは一般化しません。[PostgreSQL 17: Transaction Isolation](https://www.postgresql.org/docs/17/transaction-iso.html)

## 更新できるのは一時テーブルだけですか？

一時テーブルへの更新は、そのコピーを変えます。

```sql
UPDATE vt_snapshot SET stock = 999 WHERE id = 1;
SELECT p.stock AS base_stock, v.stock AS view_stock, s.stock AS copied_stock
FROM vt_products AS p
JOIN vt_current_products AS v USING (id)
JOIN vt_snapshot AS s USING (id)
WHERE p.id = 1;
```

期待値は `base_stock = 15`、`view_stock = 15`、`copied_stock = 999` です。次にViewを通して更新します。

```sql
UPDATE vt_current_products SET stock = 17 WHERE id = 1;
SELECT p.stock AS base_stock, v.stock AS view_stock, s.stock AS copied_stock
FROM vt_products AS p
JOIN vt_current_products AS v USING (id)
JOIN vt_snapshot AS s USING (id)
WHERE p.id = 1;
```

このViewは単一の表から列をそのまま選んだ単純な定義なので、自動更新可能です。期待値は元表とViewが17、コピーは999のままになります。集約、`DISTINCT`、結合などを含むViewまで同様に更新できるわけではありません。自動更新の条件や、条件外の行を作らせない `CHECK OPTION` は別途確認します。[PostgreSQL 17: Updatable Views](https://www.postgresql.org/docs/17/sql-createview.html#SQL-CREATEVIEW-UPDATABLE-VIEWS)

`WITH` 自体にはデータ変更文を含める機能もありますが、この記事のCTE例は読み取り専用のSELECTです。SELECTのCTEに名前を付けただけで、更新可能な表が作られるわけではありません。[PostgreSQL 17: データ変更文を含むWITH](https://www.postgresql.org/docs/17/queries-with.html#QUERIES-WITH-MODIFYING)

## CTEは毎回、一時的な表へ実体化されますか？

PostgreSQL 17では、非再帰でvolatile関数を含まないSELECTのCTEが外側から1回だけ参照される場合、通常は外側の問い合わせへ取り込まれて、まとめて最適化されます。同じCTEを複数回参照する場合は、既定では別に計算して結果を共有します。

`MATERIALIZED` は別計算を指定し、`NOT MATERIALIZED` は条件を満たすCTEを外側へ取り込む指定です。後者には重複計算が増える可能性があります。再帰CTEや、副作用のないSELECTという条件を満たさないCTEでは `NOT MATERIALIZED` は無視されます。PostgreSQL 12より前には、この取り込みは行われませんでした。[PostgreSQL 17: WITHの最適化](https://www.postgresql.org/docs/17/sql-select.html#SQL-WITH)

次の3つは、同じCTEを2回参照し、指定だけを変えています。いずれも結果として期待するのは `id = 2, stock = 20` の1行です。`EXPLAIN ANALYZE` の表示では結果行が計画情報に置き換わります。

```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)
WITH vt_selected_products AS (
  SELECT id, stock FROM vt_products WHERE status = 'active'
)
SELECT a.id, a.stock
FROM vt_selected_products AS a
JOIN vt_selected_products AS b USING (id)
WHERE b.id = 2;

EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)
WITH vt_selected_products AS MATERIALIZED (
  SELECT id, stock FROM vt_products WHERE status = 'active'
)
SELECT a.id, a.stock
FROM vt_selected_products AS a
JOIN vt_selected_products AS b USING (id)
WHERE b.id = 2;

EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)
WITH vt_selected_products AS NOT MATERIALIZED (
  SELECT id, stock FROM vt_products WHERE status = 'active'
)
SELECT a.id, a.stock
FROM vt_selected_products AS a
JOIN vt_selected_products AS b USING (id)
WHERE b.id = 2;
```

`CTE Scan` やCTEを計算する枝があるか、外側の絞り込みがどこで行われるかを読みます。`Materialize` という計画ノードを見つけただけで、「このCTEが実体化された」とは判定しません。ノードとCTE名の対応まで追ってください。計画の読み方は[EXPLAINとEXPLAIN ANALYZE](/tech-note/articles/sql/internal/explain-analyze/)で扱います。

このデータを17.10で実行した際は、既定と `MATERIALIZED` の計画に `CTE vt_selected_products` の枝と、同じCTE名を読む2つの `CTE Scan` がありました。`NOT MATERIALIZED` にはそのCTEの枝がなく、元表を読む2つの走査がありました。3種類とも返す行は同じでしたが、この観測だけで一般的な速度差までは判断していません。

条件を早く適用できる利点と、共通の計算を再利用できる利点は、問い合わせによって変わります。この3行の表では速度の優劣を決めません。また、CTEの実体化はそのSQL文の実行中の処理であり、後続のSQLから使えるTEMP TABLEの作成とは違います。[PostgreSQL 17: CTE Materialization](https://www.postgresql.org/docs/17/queries-with.html#QUERIES-WITH-CTE-MATERIALIZATION)

## 一時テーブルを選ぶと、何を管理する必要がありますか？

コピーの作成、必要なインデックス、統計、使い終わった後の寿命まで管理します。PostgreSQLのautovacuumは一時表を処理できないため、この例では投入後に明示的な `ANALYZE vt_snapshot` を実行しています。元表にある統計やインデックスが、`CREATE TABLE AS SELECT` のコピーへそのまま引き継がれると考えないようにします。[PostgreSQL 17: Temporary Tables](https://www.postgresql.org/docs/17/sql-createtable.html)

PostgreSQLの一時表は既定ではコミット後も行を保持します。`ON COMMIT DELETE ROWS` は行を空にし、`ON COMMIT DROP` は表を削除します。セッションが終われば一時表もなくなります。接続プールを使うアプリケーションでは、アプリケーションの1リクエストとDBセッションの寿命が同じとは限らないため、同じ接続で処理を完結させる設計が必要です。[PostgreSQL 17: ON COMMIT](https://www.postgresql.org/docs/17/sql-createtable.html#SQL-CREATETABLE-ON-COMMIT)

この例では作成したトランザクション全体を戻すため、表やViewの作成も取り消されます。セッション終了やコミット時の削除そのものを、このコードで再現しているわけではありません。

```sql
ROLLBACK;
```

## MySQLでも同じ指定を使えますか？

MySQL 8.4にも派生テーブル、View、CTEを外側へ取り込む処理と、中間結果を保持する処理があります。ただし制御に使う `MERGE` / `NO_MERGE` ヒントや `derived_merge` 設定などは、PostgreSQLの `AS MATERIALIZED` とは別の仕様です。集約や `DISTINCT` などが取り込みを妨げる条件も、対象DBの資料で確認します。この記事ではMySQLの実行検証は行っていません。[MySQL 8.4: Derived Tables, Views, CTEsの最適化](https://dev.mysql.com/doc/refman/8.4/en/derived-table-optimization.html)

1つのSQLを読みやすく分けたいなら派生テーブルやCTE、複数のSQLへ共通の定義を提供したいならView、コピーを後続の処理で使い回したいなら一時テーブルが候補になります。名前の寿命、更新を反映させたい時点、再利用する単位を先に決めると、実行計画で比較すべき点も絞れます。
