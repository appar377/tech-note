遅いSQLに `EXPLAIN` を付けると、見積りの実行計画を確認できます。そこへ `ANALYZE` を足すと、問い合わせが実行され、行数や時間の実測値も表示されます。更新SQLなら、更新も実行されます。

この記事ではPostgreSQL 17を対象に、計画の数字をどの単位で読むかを整理します。SQLは合成データを使い、PostgreSQL 17.10で結果と計画の項目を確認しました。少数行の確認例なので、速度の優劣や本番の処理時間を示すものではありません。

## EXPLAINだけでは、何がまだ分からないのですか？

同じpsql接続で、コードを上から順に実行する構成です。専用の一時表だけを作り、最後の `ROLLBACK` で片付けます。

```sql
BEGIN;
CREATE TEMP TABLE ea_groups (id integer PRIMARY KEY) ON COMMIT DROP;
CREATE TEMP TABLE ea_items (
  id integer PRIMARY KEY,
  group_id integer NOT NULL,
  status text NOT NULL,
  amount integer NOT NULL
) ON COMMIT DROP;
INSERT INTO ea_groups (id) VALUES (1), (2), (3);
INSERT INTO ea_items (id, group_id, status, amount) VALUES
  (1, 1, 'queued', 10), (2, 1, 'ready', 20),
  (3, 2, 'queued', 30), (4, 2, 'ready', 40),
  (5, 3, 'queued', 50), (6, 3, 'ready', 60);
ANALYZE ea_groups;
ANALYZE ea_items;
```

ここでの単独の `ANALYZE ea_items` は、表の内容に関する統計を集め、プランナーの判断材料を更新します。問い合わせを計測する `EXPLAIN (ANALYZE)` とは役割が違います。[PostgreSQL 17: ANALYZE](https://www.postgresql.org/docs/17/sql-analyze.html)

```sql
EXPLAIN (FORMAT JSON)
SELECT id, amount
FROM ea_items
WHERE status = 'ready'
ORDER BY id;
```

JSON内の `Plan` には、どの処理をどのように組み合わせる予定かが入ります。

| フィールド | 読み取る内容 |
| --- | --- |
| `Node Type` | 走査、結合、ソートなど、そのノードの処理 |
| `Startup Cost` / `Total Cost` | 最初の行まで／全行までの見積りコスト。時間のミリ秒ではありません |
| `Plan Rows` | そのノードが出力すると見積もった行数 |
| `Plan Width` | 出力する1行の平均サイズの見積り。単位はバイトです |
| `Plans` | 子ノード。結合などでは複数の枝があります |

表全体の読み取り行数と、条件を通過してノードから出る行数は違います。`Plan Rows` を「スキャンした行数」と読むと、フィルターのある計画を誤解します。子の出力を親がどう使うか、木の枝ごとに追います。[PostgreSQL 17: Using EXPLAIN](https://www.postgresql.org/docs/17/using-explain.html)

この段階では `Actual Rows` や `Execution Time` はありません。実際の行数や所要時間を、見積りコストから確定することはできません。

## estimated rowsとactual rowsは、同じノードで比べますか？

まず問い合わせそのものが返す行を確認します。

```sql
SELECT id, amount
FROM ea_items
WHERE status = 'ready'
ORDER BY id;
```

このデータで期待する結果は、`id` が2・4・6、`amount` が20・40・60の3行です。その結果を保ったまま、実行計画を計測します。

```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)
SELECT id, amount
FROM ea_items
WHERE status = 'ready'
ORDER BY id;
```

`Plan Rows` と `Actual Rows` は同じノードで比較します。問い合わせ全体の期待結果が3行でも、途中のノードが受け渡す行数まで3行とは限りません。走査で多くの行を読み、条件や集約で減らしている可能性があります。

見積りと実測が大きく違う場合は、その差が生まれた枝を調べます。ただし `LIMIT` などにより処理が途中で止まったノードでは、最後まで処理する見積りと途中までの実測が違っても、それだけで統計の誤りとは判断できません。[PostgreSQL 17: EXPLAINの注意点](https://www.postgresql.org/docs/17/using-explain.html#USING-EXPLAIN-CAVEATS)

少数行の例で `Seq Scan` が選ばれても失敗ではありません。全行を読む費用が小さければ、その選択が妥当なことがあります。このデータで得た計画を、大規模な本番表にそのまま当てはめないでください。

## rowsだけでなくloopsも読むのはなぜですか？

繰り返し実行されるノードでは、`Actual Rows` とノードの時間は1回あたりの平均です。全体の仕事量を考えるときには `Actual Loops` も必要になります。表示には丸めがあるため、積を常に厳密な件数と扱うことも避けます。[PostgreSQL 17: EXPLAIN ANALYZE](https://www.postgresql.org/docs/17/using-explain.html#USING-EXPLAIN-ANALYZE)

次は、グループごとに合計を求める相関サブクエリです。

```sql
SELECT g.id,
  (SELECT sum(i.amount) FROM ea_items AS i WHERE i.group_id = g.id) AS total
FROM ea_groups AS g
ORDER BY g.id;
```

期待する合計は、グループ1が30、2が70、3が110です。計画では内側の集約や走査が何回呼ばれるかを確認します。

```sql
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, FORMAT JSON)
SELECT g.id,
  (SELECT sum(i.amount) FROM ea_items AS i WHERE i.group_id = g.id) AS total
FROM ea_groups AS g
ORDER BY g.id;
```

`TIMING OFF` により、各ノードの時間を測るための時計読み取りを省きます。行数と実行回数、問い合わせ全体の `Execution Time` は引き続き取得できます。`Plans` の枝をたどり、実際に `Actual Loops` が大きいノードを探してください。このデータを17.10で実行した際は、内側のAggregateが `Actual Rows = 1`、`Actual Loops = 3` となりました。3グループについて集約を1回ずつ実行し、各回で1行を返したと読めます。環境や問い合わせが変われば、同じノード配置になる保証はありません。[PostgreSQL 17: TIMING](https://www.postgresql.org/docs/17/sql-explain.html)

## Buffersはディスクを読んだ回数ですか？

`BUFFERS` はブロックへのアクセスを読む手掛かりです。次の区分を分けて見ます。

| 区分 | 対象 |
| --- | --- |
| shared | 通常の表やインデックス |
| local | 一時表やそのインデックス |
| temp | ソートやハッシュなどの処理が使う一時ファイル |

今回の例は一時表なので、表へのアクセスはlocalの欄を見ます。tempは「自分で作ったTEMP TABLE」の読み取り欄ではありません。hitは既にバッファ内にあったため読み込みを回避できた回数で、上位ノードの値には子ノードの分も含まれます。各段の値を足すと重複して数えてしまいます。[PostgreSQL 17: BUFFERS](https://www.postgresql.org/docs/17/sql-explain.html)

readがあっても、それだけで物理ディスクの待ち時間までは分かりません。OSのページキャッシュから取得できる場合もあるためです。I/Oを詳しく調べるときは、DBの統計とOS側の観測を合わせます。[PostgreSQL 17: I/O統計の範囲](https://www.postgresql.org/docs/17/monitoring-stats.html)

## Planning TimeとExecution Timeを足せば、画面の待ち時間ですか？

`Planning Time` は、解析済みの問い合わせから計画を作る時間です。構文解析や書き換えは含みません。`Execution Time` は、実行器の開始・終了などを含む実行側の時間で、計画作成は含みません。

さらに、この計測では検索結果をクライアントへ送らず、通常は出力形式への変換も行いません。計測自体の負荷もあります。そのため2つを足しても、アプリケーションの接続待ち、通信、オブジェクト化、画面描画を含む時間にはなりません。ノードの時間にも親子の重複があるので、全ノードを単純に合計しないようにします。[PostgreSQL 17: 実行時間の範囲](https://www.postgresql.org/docs/17/using-explain.html#USING-EXPLAIN-ANALYZE)

## UPDATEにANALYZEを付けると、値は変わりますか？

次の順番で、1行の値を見ます。期待値は最初が10、実行を伴う計画の後が11、savepointへ戻した後が10です。

```sql
EXPLAIN (FORMAT JSON)
UPDATE ea_items SET amount = amount + 1 WHERE id = 1;
SELECT amount FROM ea_items WHERE id = 1;
SAVEPOINT ea_before_update;
EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)
UPDATE ea_items SET amount = amount + 1 WHERE id = 1;
SELECT amount FROM ea_items WHERE id = 1;
ROLLBACK TO SAVEPOINT ea_before_update;
SELECT amount FROM ea_items WHERE id = 1;
RELEASE SAVEPOINT ea_before_update;
```

`EXPLAIN (FORMAT JSON)` はこの更新の計画を作りますが、更新処理は実行しません。`EXPLAIN (ANALYZE, ...)` は更新処理も実行します。更新件数は、最上位ノードの `Actual Rows` だけで決めず、対象行の値も確認してください。`RETURNING` のない更新では、更新した行数とノードの出力行数は一致するとは限りません。[PostgreSQL 17: 更新文の計画](https://www.postgresql.org/docs/17/using-explain.html#USING-EXPLAIN-ANALYZE)

この例にはトリガーやシーケンスはありません。一般のSQLへ置き換えるときは、`ROLLBACK` で全ての副作用を取り消せるとは考えないでください。例えば `nextval` が進めたシーケンス値は、トランザクションを中断しても再利用のために戻されません。[PostgreSQL 17: Sequence Manipulation Functions](https://www.postgresql.org/docs/17/functions-sequence.html)

```sql
ROLLBACK;
```

## 計画を読んだ後、何を確かめますか？

まず結果の正しさを保ち、次に見積りと実測がずれる位置、繰り返し回数、読み込みや一時ファイルの発生を調べます。統計の更新、条件や結合の見直し、インデックスの追加は、その観測に対応する候補として比較します。ノード名だけで修正を決める必要はありません。

CTEやViewへの書き換えが計画へ与える影響は、[View・派生テーブル・CTE・一時テーブルの違い](/tech-note/articles/sql/internal/view-derived-table-cte-temporary-table/)で扱います。

MySQL 8.4でも `EXPLAIN ANALYZE` は問い合わせを実行しますが、出力はTREE形式です。この記事のPostgreSQL用オプションやJSONフィールドをそのまま移植せず、対象DBの仕様で読み替えてください。MySQLでの実行検証は本稿の対象外です。[MySQL 8.4: EXPLAIN Statement](https://dev.mysql.com/doc/refman/8.4/en/explain.html)
