Wine経由のMT5でウィンドウが開かないとき、まず分けたいのは「接続先がない」と「接続先から拒否される」です。どちらも画面が出ない原因になり得ますが、環境変数を足す操作と接続許可を変える操作では影響が違います。

さらに、Waylandのセッションで起動したアプリが、Waylandへ直接接続しているとは限りません。対象プロセスの経路を確かめてから、その経路に必要な値を読みます。この記事は仕様に基づく切り分け方で、LinuxやMT5での障害を再現した記録ではありません。

## Waylandのセッションなら、X11は関係ないのか

| 対象アプリの経路 | 接続先 | 主に確認するもの |
| --- | --- | --- |
| X11クライアント → Xorg / Xvfbなど | X server | `DISPLAY`、X11側の認証・接続制御 |
| X11クライアント → XWayland → compositor | XWaylandというX server | クライアント側はX11。XWaylandとcompositorの関係も確認 |
| native Waylandクライアント → compositor | Wayland socket | `WAYLAND_DISPLAY`、runtime directoryなど |

XWaylandはWaylandクライアントとして動くX serverです。X11アプリからはX serverへの接続に見えるため、Waylandセッション内でもX11の接続条件が関わります。[Wayland: X11 Application Support](https://wayland.freedesktop.org/docs/book/Xwayland.html)

Wineの経路も版と構成に依存します。Wine 10.0のリリースノートではWayland driverが既定で有効になり、両方が利用可能な場合はX11 driverが優先すると説明されています。この記載をすべてのWine版へ広げたり、対象アプリの実際の経路を環境変数だけで確定したりはしません。[Wine 10.0: Wayland driver](https://github.com/wine-mirror/wine/blob/wine-10.0/ANNOUNCE.md#wayland-driver)

たとえば説明用の環境に`XDG_SESSION_TYPE=wayland`と`DISPLAY=:77`が両方あっても矛盾ではありません。前者はセッションに関する情報、後者はX11接続先です。デスクトップ名やセッション名から各プロセスの経路を推定しすぎない点は、[GUI環境の観察](/tech-note/articles/linux/mt5-ubuntu/02-gui-flavors-validation)と共通します。

## DISPLAYとXAUTHORITYはそれぞれ何を指定するのか

`DISPLAY`は接続先を指定します。X11の基本形は`hostname:displaynumber.screennumber`です。たとえば`:77`はローカルのdisplay 77を指定する表現であり、77番のサーバーを起動する命令ではありません。[X.Org: Display Names](https://xorg.freedesktop.org/archive/X11R7.5/doc/man/man7/X.7.html)

Cookie認証を使うX11接続では、接続先の指定に加え、サーバーが受け入れる認証情報が必要です。`XAUTHORITY`はクライアントが参照する認証用ファイルの場所を指します。ファイル名が常に`.Xauthority`であるとは限りません。[X.Org: Xsecurity](https://xorg.freedesktop.org/archive/X11R7.5/doc/man/man7/Xsecurity.7.html)

| 状態 | そこから言えること | まだ言えないこと |
| --- | --- | --- |
| `DISPLAY`に値がある | 接続先の指定がある | サーバーが存在し、到達できる |
| `XAUTHORITY`が未設定 | 明示的な上書きがない | Cookie認証が不可能である |
| 認証用ファイルを読める | そのプロセスがファイルへアクセスできる | 対象displayに合うエントリがあり、サーバーが受け入れる |
| X11接続が成功する | その時点で接続が受け入れられた | MT5の描画・入力・常駐も成功する |

`XAUTHORITY`が未設定なら、X11の標準的な仕組みではホームディレクトリの`.Xauthority`が参照先になります。したがって「未設定だから直す」とは限りません。逆に、別セッションのファイルを明示して失敗することも考えられます。[X.Org: xauth — Environment](https://xorg.freedesktop.org/archive/X11R7.5/doc/man/man1/xauth.1.html)

`xauth`は認証用ファイルを扱うツールです。`list`は秘密のCookie値も出力するため、公開ログへ貼る診断例にはしません。ファイルの存在や所有者だけの確認と、内容の取り扱いを分けます。なお、`xauth`は通常のファイル操作ではX serverへ接続せず、`generate`は接続する操作です。ファイルを読めたことを接続テストの成功と見なさないようにします。[X.Org: xauth](https://xorg.freedesktop.org/archive/X11R7.5/doc/man/man1/xauth.1.html)

## native WaylandにXauthorityを渡せば直るのか

native Waylandの接続では、X11のCookieファイルを指定しても接続先は作られません。libwayland-clientの`wl_display_connect`では、指定名や`WAYLAND_DISPLAY`などから接続先が決まります。相対名のsocketは`XDG_RUNTIME_DIR`を基準にし、絶対パスや既存file descriptorを使う場合もあります。[Wayland Client API: wl_display_connect](https://wayland.freedesktop.org/docs/html/apb.html)

`XDG_RUNTIME_DIR`はユーザーごとのruntime fileやsocketを置く場所です。所有者や権限、ログイン状態と結びつく寿命が仕様に含まれます。別ユーザーのディレクトリ名をコピーして環境変数へ入れるだけでは、そのセッションへのアクセスが成立するとは言えません。[XDG Base Directory Specification](https://specifications.freedesktop.org/basedir/latest/)

ここでも、socketの指定、socketへのアクセス、必要なプロトコル機能の対応を分けて確認します。Wineのdriverを切り替える操作は、表示経路そのものを変えるため、元の条件を記録せずに行う切り分けには向きません。

## 手動起動とサービス起動で何を比べるか

同じ実行ファイルでも、呼び出すユーザーとプロセスに渡る環境が違えば、別の表示先やprefixを使う可能性があります。比較するのは、その起動方法で対象プロセスへ実際に渡す値です。

| 比較する項目 | 切り分ける差 |
| --- | --- |
| 実行ユーザー | 認証用ファイル、socket、prefixへアクセスする主体 |
| `DISPLAY`またはWayland接続先 | 手動時と同じ表示経路を選んでいるか |
| X11認証用ファイルの参照元 | 明示値・既定値・セッション管理側の設定のどれか |
| `WINEPREFIX` | 同じWine側の状態を使っているか |
| 起動元の環境の組み立て方 | シェル、system manager、user managerの差 |

systemdのsystem serviceは、ログイン中のシェルの環境をそのままコピーする仕組みではありません。一方、user managerから起動するサービスには、そのmanagerが持つ環境が継承される場合があります。「systemdには常にDISPLAYがない」と固定せず、どのmanagerから起動するかを含めます。[systemd v258: systemd.exec](https://github.com/systemd/systemd/blob/v258/man/systemd.exec.xml)

SSHでもX11 forwardingが設定されていれば`DISPLAY`が用意されることがあります。その値を適当な`:0`へ置き換えると、転送先の指定まで変えてしまいます。[OpenSSH: DISPLAY](https://man.openbsd.org/ssh.1#DISPLAY)

`cannot open display`のようなメッセージだけで、到達不能と認証失敗を一意に決めることはできません。接続先の指定、サーバーやsocketの存在、アクセスするユーザー、認証方式の対応を順に分けて確認します。Linux上の診断や実接続は本稿では未実行です。

接続を通すために`xhost +`を使うと、X serverのアクセス制御を無効にします。対象ユーザーに限定する形式も、Cookie認証を修復する操作ではなく、別の接続許可を追加する操作です。ここでは許可を広げるコマンドを対処例にしません。[X.Org: xhost](https://xorg.freedesktop.org/archive/X11R7.5/doc/man/man1/xhost.1.html)

常設の表示先を用意する設計は[Ubuntu Serverのheadless構成](/tech-note/articles/linux/mt5-ubuntu/03-ubuntu-server-headless-design)、サービスの具体的な起動環境は[systemd管理](/tech-note/articles/linux/mt5-ubuntu/06-systemd-operation)へ分けます。
