systemdがサービスを起動したことと、その中のPythonが目的のMT5へ接続できたことは、別の状態です。常駐構成では、プロセスを誰が管理し、どの条件を満たしたら接続確認済みとするかを分けて決めます。

ここではWine上のMT5とPython連携をサービス化する際の設計を扱います。systemd v258の公式マニュアルを参照した説明であり、Ubuntuへのunit適用、WineやMT5の起動、API接続は行っていません。対象OSに搭載されたsystemdの版への適用も確認が必要です。

## どのプロセスを、誰が起動・終了させますか

まず管理対象を分けます。X11を使う構成なら表示サーバー、MT5のterminal、Pythonの接続クライアントが候補です。ただし、いつでも3つのサービスに分ければよいわけではありません。

MetaTrader5の`initialize()`は、接続のためにterminalを起動する場合があります。terminal専用サービスを置く設計でも、Python側からの起動を許すのかを決めておきます。[initializeの動作](https://www.mql5.com/en/docs/python_metatrader5/mt5initialize_py)

| 管理する対象 | 先に答えておく問い |
|---|---|
| 表示先 | 既存のセッションへ接続するのか、独立して起動するのか |
| terminal | 専用サービスとPython側のどちらを起動の担当にするか |
| Pythonクライアント | terminalがなくなったとき、待機・終了・再接続のどれを選ぶか |
| 終了時の処理 | 接続を閉じる処理と、terminalを終了させる処理を誰が担当するか |

APIの`shutdown()`は接続を閉じる関数です。terminalそのものを終了させる処理として代用しません。[shutdownの仕様](https://www.mql5.com/en/docs/python_metatrader5/mt5shutdown_py)

X11以外の表示経路もあるため、Xvfbや`DISPLAY`を全構成へ機械的に追加しません。表示先の設計は[headless構成](/tech-note/articles/linux/mt5-ubuntu/03-ubuntu-server-headless-design/)に分けます。

## Afterを指定すると、APIが使えるまで待ちますか

`After=`はunit間の起動順序を指定します。それだけで相手を起動する指定にはなりません。相手も起動する関係は`Wants=`や`Requires=`で表し、順序とは別に選びます。[systemd v258のunit依存関係](https://github.com/systemd/systemd/blob/v258/man/systemd.unit.xml)

たとえば、表示用サービスを`After=`に書くと、そのunitの起動処理が終わってから後続へ進む関係を作れます。ただし、何を起動完了とみなすかはサービスの`Type=`にも依存します。

| Type | systemdが起動完了と扱う主な時点 | 追加で確認すること |
|---|---|---|
| `simple` | 主プロセスをforkした直後 | 実行ファイルの実行、アプリの初期化 |
| `exec` | 主プロセスの実行ファイルを実行できた後 | アプリの初期化や接続 |
| `notify` | サービスから`READY=1`を受けた後 | 通知を送る条件が、必要な準備と一致しているか |

この違いは[systemd v258のサービス種別](https://github.com/systemd/systemd/blob/v258/man/systemd.service.xml)に定義されています。`Type=exec`にしても、Wineやterminalの初期化完了まで自動で判断するわけではありません。

`Type=notify`も設定だけでは成立しません。通知を送る実装と、`NotifyAccess=`などの受け入れ条件が必要です。MT5や任意のWine起動コマンドがその通知に対応している、と仮定しないようにします。[sd_notifyの通知と受け入れ条件](https://github.com/systemd/systemd/blob/v258/man/sd_notify.xml)

接続確認を起動条件に含めるなら、確認する対象、期限、失敗時の扱いを実装側で決めます。一定時間の待機を入れただけでは、準備完了の証拠にはなりません。

## 対話シェルで動いた条件を、どうサービスへ渡しますか

サービスの環境を、ログイン中のシェルと同じだと考えないことが出発点です。system managerとuser managerでは環境変数の継承条件が異なり、unitの`Environment=`や`EnvironmentFile=`なども値の供給元になります。[systemd v258のプロセス環境](https://github.com/systemd/systemd/blob/v258/man/systemd.exec.xml)

移行時には、実行ユーザー、ホームの扱い、作業ディレクトリ、Pythonの実行ファイル、Wine prefix、対象terminalを対応付けます。X11を使うなら表示先と認証の経路も必要です。シェルの環境変数を丸ごとコピーするより、各プロセスに何が必要かを明らかにします。

`DISPLAY`の値があることは、表示サーバーへの接続成功を意味しません。`XAUTHORITY`の値があることも、認証情報の正しさを証明しません。接続と認証の違いは[Wayland・X11・Xauthority](/tech-note/articles/linux/mt5-ubuntu/03-wayland-x11-xauthority/)で扱っています。

## activeと接続確認を、記録上も分けられますか

次は、説明用の記録を分類するPython 3の例です。systemdやMT5へ問い合わせるコードではありません。入力はすべて合成値で、API、環境変数、ファイル、プロセス、ネットワークを参照しません。

`run-A`と`run-B`は対象構成の起動世代を区別する説明用IDです。terminalや接続クライアントを再起動したら、記録側で世代を変える設計を想定しています。これはsystemdから自動で得られる値を表したものではありません。

```python file=connection_evidence.py
import json


def connection_evidence(unit_state, current_run, observation):
    if unit_state not in {"active", "activating", "inactive", "failed"}:
        raise ValueError("unsupported unit state")
    if not isinstance(current_run, str) or not current_run:
        raise ValueError("current_run must be a nonempty identifier")
    result = observation["result"]
    if result not in {"unknown", "success", "failure"}:
        raise ValueError("unsupported observation result")
    if unit_state != "active":
        return "unit-not-active"
    if result == "unknown":
        return "connection-unconfirmed"
    if observation["run"] != current_run:
        return "observation-from-other-run"
    if result == "failure":
        return "connection-failed"
    return "connection-confirmed-at-observation"


cases = [
    ("not-checked", "active", {"run": None, "result": "unknown"}),
    ("same-run-success", "active", {"run": "run-B", "result": "success"}),
    ("previous-run-success", "active", {"run": "run-A", "result": "success"}),
    ("same-run-failure", "active", {"run": "run-B", "result": "failure"}),
    ("inactive-with-success", "inactive", {"run": "run-B", "result": "success"}),
    ("starting", "activating", {"run": None, "result": "unknown"}),
    ("failed-unit", "failed", {"run": "run-B", "result": "success"}),
]

print(json.dumps([
    {"case": name, "state": connection_evidence(unit, "run-B", observation)}
    for name, unit, observation in cases
], indent=2))
```

`connection_evidence.py`として保存して実行すると、JSONの配列を出す設計です。Python 3.11.5で7つの合成入力を実行し、本文から取り出したコードでも、次の期待値とJSONの全項目が一致しました。systemdやAPIの状態を採取したログではありません。

| 合成ケース | 期待する分類 |
|---|---|
| `not-checked` | `connection-unconfirmed` |
| `same-run-success` | `connection-confirmed-at-observation` |
| `previous-run-success` | `observation-from-other-run` |
| `same-run-failure` | `connection-failed` |
| `inactive-with-success`、`starting`、`failed-unit` | `unit-not-active` |

この例は4つのunit状態だけを受け取り、`active`以外では以前の接続結果を現在の確認に使いません。`active`でも、確認していない場合や別世代の結果しかない場合は区別します。

成功の分類名を「観測時点で接続確認済み」としたのは、その後も接続が続いているとは限らないためです。同じ世代の中での切断、記録の有効期限、観測と判定の間の状態変化は、この小さな例では扱っていません。また、接続確認は口座の状態や後続処理の成功を判定するものではありません。

## Restartを付ければ、止まった処理を復旧できますか

`Restart=on-failure`は、異常終了や所定のタイムアウトなどを契機に再起動を試みる設定です。プロセスが生きたまま接続処理で行き詰まっている状態を、この設定だけで検出するわけではありません。[systemd v258の再起動条件](https://github.com/systemd/systemd/blob/v258/man/systemd.service.xml)

watchdogを使う場合も、サービス側から定期的な通知が必要です。通知を送れていることを、処理内容全体の正しさへ広げて解釈しません。[sd_notifyのwatchdog通知](https://github.com/systemd/systemd/blob/v258/man/sd_notify.xml)

さらに、プロセスを起動し直すことと、途中まで進んだ処理をどこから再開するかは別の設計です。前回の完了点や再実行時の重複を確認できないまま、再起動回数だけを増やしても処理の整合性は戻りません。

サービス化後に状況が変わったときは、[症状から構成を切り分ける記事](/tech-note/articles/linux/mt5-ubuntu/07-final-architecture-troubleshooting/)で、起動条件・プロセス・APIの記録を分けて確認します。
