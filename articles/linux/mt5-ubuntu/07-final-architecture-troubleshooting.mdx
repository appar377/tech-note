「画面が出ない」「Pythonから接続できない」「サービスにすると動かない」は、同じ問題とは限りません。症状ごとに確認する境界を選び、分かったことと、まだ見ていないことを分けると、次に調べる対象を絞れます。

このシリーズは、Ubuntu系Linux、表示経路、Wine、MT5、Python、systemdの役割を9本に分けて整理しました。ここではそれらを使って切り分ける順序を考えます。特定の構成で導入や連続稼働が成功したという報告ではありません。

## どの構成にも、同じ表示サーバーが必要ですか

最初に、対象の構成を一行で説明できるようにします。たとえば「WineのX11経路を使い、独立したXサーバーへ接続する」という構成案なら、表示先への接続が確認対象に入ります。これはLinux上のすべてのWine構成に共通する前提ではありません。

Wine 10.0ではWaylandドライバーが既定で有効になり、X11とWaylandの両方を利用できる場合にはX11が優先されると説明されています。したがって、OSやデスクトップの名前だけで、個々のWineプロセスの表示経路を断定しません。[Wine 10.0のリリースノート](https://github.com/wine-mirror/wine/blob/wine-10.0/ANNOUNCE.md)

MetaQuotesのLinux導入ガイドはWineを利用する方法を案内していますが、任意の表示経路、Python、中継サービス、常駐設定を組み合わせた検証結果ではありません。採用した構成の条件を別に残します。[Linuxへの導入ガイド](https://www.metatrader5.com/en/terminal/help/start_advanced/install_linux)

## 症状から、どの境界へ戻りますか

次の表は原因一覧ではありません。症状から確認の入口を選ぶための表です。右端にある結論は、その症状だけではまだ出せません。

| 症状・分かったこと | 次に照合する境界 | まだ決められないこと |
|---|---|---|
| ウィンドウが表示されない | 選んだ表示経路、接続・認証、対象terminalの起動 | OSやWine全体の非対応 |
| GUIは表示できるがAPIを使えない | Python配布物、対象terminal、API接続 | GUIを変更すれば直ること |
| 対話起動では動き、サービスでは動かない | 実行ユーザー、環境、prefix、実行ファイル、起動順序 | `DISPLAY`だけが原因であること |
| サービスは`active`だが接続確認がない | そのサービスの起動完了条件と、アプリ側の接続結果 | APIが準備完了であること |
| 再起動前の成功記録しかない | 同じ条件が復元されたか、今回の起動で再確認したか | 過去の結果が現在にも当てはまること |

Python連携はterminalとのプロセス間通信です。ウィンドウを描画できた結果は、その通信の確認を代替しません。[Python Integration](https://www.mql5.com/en/docs/python_metatrader5)

同じように、systemdのサービス種別による起動完了とアプリの準備完了も区別します。たとえば`Type=exec`は実行ファイルを実行できた時点を扱い、その後の接続成功を自動で確認するものではありません。[systemd v258のサービス種別](https://github.com/systemd/systemd/blob/v258/man/systemd.service.xml)

## 未確認を、失敗と取り違えずに記録できますか

説明用の例として、3つの症状に対する確認項目を決めます。`confirmed`はその項目を確認できた、`failed`はその項目の確認が失敗した、`unknown`はまだ確認できていない、という記録です。

次のPython 3コードは、与えられた記録を分類するだけです。実環境を調べる診断器ではなく、API呼び出しや環境変数・ファイル・プロセスの参照もありません。すべての入力は合成値です。

```python file=inspection_summary.py
import json


PLANS = {
    "no-window": ("display-route", "terminal-launch"),
    "api-unavailable": ("python-package", "terminal-target", "api-connection"),
    "service-only-failure": ("launch-context", "process-start", "api-connection"),
}


def inspection_summary(symptom, observations):
    if symptom not in PLANS:
        raise ValueError("choose a supported symptom")
    summary = {"confirmed": [], "failed": [], "unknown": []}
    for check in PLANS[symptom]:
        state = observations.get(check, "unknown")
        if state not in summary:
            raise ValueError("unsupported observation state")
        summary[state].append(check)
    return summary


cases = [
    ("no-observations", "api-unavailable", {}),
    ("package-failure", "api-unavailable", {"python-package": "failed"}),
    ("connection-failure", "api-unavailable", {
        "python-package": "confirmed", "terminal-target": "confirmed",
        "api-connection": "failed",
    }),
    ("window-confirmed-only", "api-unavailable", {"terminal-launch": "confirmed"}),
    ("service-context-unknown", "service-only-failure", {
        "process-start": "confirmed", "api-connection": "failed",
    }),
    ("window-plan-confirmed", "no-window", {
        "display-route": "confirmed", "terminal-launch": "confirmed",
    }),
]

print(json.dumps([
    {"case": name, "checks": inspection_summary(symptom, observations)}
    for name, symptom, observations in cases
], indent=2))
```

`inspection_summary.py`として保存すると、6つの例についてJSONを出す設計です。Python 3.11.5で6つの合成入力を実行し、本文から取り出したコードでも、次の分類とJSONの全項目が一致しました。実環境の診断結果ではありません。

| 合成ケース | 期待する読み取り方 |
|---|---|
| `no-observations` | APIに関する3項目すべてが未確認 |
| `package-failure` | 配布物の確認が失敗。接続先とAPIは未確認 |
| `connection-failure` | 配布物と接続先は確認済み。API接続の確認が失敗 |
| `window-confirmed-only` | GUI起動の記録を、API側の確認へ転用しない |
| `service-context-unknown` | プロセス起動は確認済みでも、起動環境は未確認として残る |
| `window-plan-confirmed` | 表示と起動の2項目について確認済み。他の機能の結果は含めない |

記録にない項目は`unknown`として扱います。たとえばAPI接続の確認が失敗しても、未確認の起動環境を「問題なし」に書き換えません。また、選んだ確認項目に含まれない情報は、この分類には使いません。対象外の項目が成功したからといって、対象の確認が終わったことにはならないためです。

実際に使う記録では、確認した条件、時点、対象の起動世代も必要です。この例は同じ対象・条件に整理済みの入力を前提とし、古い記録の選別や根本原因の推定は実装していません。

## 変更前後を比べるとき、何をそろえますか

原因を絞るには、「前は動いた」という記憶を、比較できる条件へ分解します。

- OS・アーキテクチャ、Wine・Python・パッケージの版をそろえます。
- 実行ユーザー、prefix、対象terminal、表示経路、起動方法を対応付けます。
- 確認した項目と時点を記録し、未確認や別の起動で得た結果を混ぜません。

サービスへ移した場合は、対話シェルの環境がそのまま引き継がれるとは考えません。system managerとuser managerの環境の組み立てには違いがあります。[systemd v258の実行環境](https://github.com/systemd/systemd/blob/v258/man/systemd.exec.xml)

条件を一つ変えた後は、その変更が関わる境界を再確認します。表示方式を変えたら接続と認証、Pythonを変えたら配布物と読み込み、起動主体を変えたら環境と終了処理が対象です。複数の設定を一度に変更しても、その結果だけではどの変更が影響したかを分けられません。

共有する記録には説明用IDを使い、口座情報、認証情報、Xauthorityのcookie、環境変数全体を貼り付けないようにします。必要なのは「何を、どの条件で確かめたか」が対応する記録です。
