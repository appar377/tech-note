`order.with_lock` は手元の `order` を読み直し、`InstanceOrder.lock.find(order.id)` は別のオブジェクトを返します。どちらも行ロックを使いますが、Ruby上の値や保存差分が同じように更新されるわけではありません。

変更直後のインスタンスを読み直すと、`after_commit` が参照する保存差分を消すことがあります。その最小再現は[with_lockで保存差分が消える条件](/tech-note/articles/rails/active_record/with-lock-dirty-tracking-after-commit/)に分けました。ここでは、別インスタンスへ変えれば十分なのかを考えます。

以下は説明用の注文モデルです。`instance_orders` テーブルには `status` という文字列カラムだけを用意し、日時カラムや独自callbackを設けていません。Ruby 3.4.4、Active Record 8.1.3、PostgreSQL 17.10で確認した例です。

```ruby
class InstanceOrder < ActiveRecord::Base
end
```

## 別インスタンスなら、元の保存差分は残る

次の例では、更新した `original` と、ロックして取得した `locked` が同じDB行を表します。外側のtransaction内なので、後者からも自分の更新を読めます。

```ruby
original = InstanceOrder.create!(status: 'pending').reload

InstanceOrder.transaction do
  original.update!(status: 'confirmed')
  locked = InstanceOrder.lock.find(original.id)

  locked.equal?(original) # => false
  locked.status # => 'confirmed'
  locked.saved_change_to_status? # => false
  original.saved_change_to_status? # => true
end
```

この範囲では、`locked` の取得は `original` をreloadしません。ただし、この順序は「更新前の判断を保護する」例にはなっていません。すでに古い値から判断して更新した後でロックしても、その判断をやり直したことにはならないためです。なお、この例の `UPDATE` 自体もDBの行ロックを取得します。

[with_lockの実装](https://api.rubyonrails.org/v8.1.3/classes/ActiveRecord/Locking/Pessimistic.html)はtransaction内で `lock!` を呼び、保存済みインスタンスをロック付きでreloadします。対して `lock.find` はロック句を付けた検索です。

| 呼び方 | ロック後に読むオブジェクト | 手元の値への影響 |
| --- | --- | --- |
| `original.with_lock` | `original` | 再読込され、保存差分は消える |
| `InstanceOrder.lock.find(id)` | 戻り値の別インスタンス | `original` は以前のまま |

未保存の変更がある `original` に `with_lock` を呼ぶと、この版では例外になります。変更をいったん `save!` してからロックする回避策では、判断と更新の順序が逆転します。通常はロックを取ってから値を代入します。

## ロックしても、古い変数の値は新しくならない

別の取得結果を使わず、元の変数を読み続けると判断を誤ります。

```ruby
stale = InstanceOrder.create!(status: 'pending').reload
InstanceOrder.find(stale.id).update!(status: 'confirmed')

InstanceOrder.transaction do
  locked = InstanceOrder.lock.find(stale.id)
  stale.status # => 'pending'
  locked.status # => 'confirmed'
end
```

`stale` は、別インスタンスで行った保存を自動では取り込みません。ロック付き検索の後は、`locked.status` で判断し、同じ `locked` に更新を集めます。[Active Recordのreload](https://api.rubyonrails.org/v8.1.3/classes/ActiveRecord/Persistence.html#method-i-reload)が明示的な再読込であることも、この区別につながります。

## IDを受け取り、ロック後に判断する

一度だけ `pending` から `confirmed` に進める説明用serviceは、次の順序にできます。

```ruby
class ConfirmInstanceOrder
  def self.call(id)
    InstanceOrder.transaction do
      order = InstanceOrder.lock.find(id)
      return false unless order.status == 'pending'

      order.update!(status: 'confirmed')
      true
    end
  end
end
```

先に対象をロックし、そのとき読んだ値で判断して更新します。呼び出し元のインスタンスを再利用しないので、serviceの外にある変数は更新されません。

```ruby
order = InstanceOrder.create!(status: 'pending').reload
ConfirmInstanceOrder.call(order.id) # => true
ConfirmInstanceOrder.call(order.id) # => false
order.status # => 'pending'
order.reload.status # => 'confirmed'
```

この例は同じ接続のtransactionに限った処理です。対象が存在しなければ `find` は例外になり、存在しない行をロックして待つわけではありません。競合時の待機やロックの寿命は[PostgreSQLでの行ロック](/tech-note/articles/rails/active_record/rails-pessimistic-locking-select-for-update/)で扱います。

## callbackのためにインスタンスを増やす前に

「元の差分を残すために別インスタンスを使う」は局所的な修正候補です。元インスタンスに追加の保存やreloadが入れば、参照する差分は再び変わります。また、同じ行の複数インスタンスを更新したとき、すべてにtransaction callbackが実行されると期待することもできません。[公式callbackガイド](https://guides.rubyonrails.org/active_record_callbacks.html#after-commit-and-after-rollback)にもこの制約があります。

保存の差分は、業務全体の「確定イベント」を永続的に表すものではありません。外部通知が必須なら、変更と通知予定を同じtransactionに記録し、未配送を後からたどれる形を検討します。[after_commitと通知予定の保存](/tech-note/articles/rails/active_record/after-commit-business-workflow/)では、この設計をfakeの配送先で確認します。

## 漏れた通知を、同じ値の再保存で直さない

すでに確定している注文をもう一度同じ値で保存しても、新しい状態変更にはなりません。

```ruby
order.update!(status: 'confirmed')
order.saved_change_to_status? # => false
```

通知漏れを補正するときは、対象、必要な通知、既存の配送記録を照合し、明示的な再投入処理を作ります。「存在確認してから作る」だけでは並行実行で重複し得るので、DBの一意制約と受信側の冪等性も必要です。SQLによる直接更新や `update_columns` はcallbackを通らないため、callbackを再実行する補正にはなりません。

検証では同一インスタンスのreload、別取得での差分保持、古い値の残存、未保存変更の拒否、二度目の確定、同値保存、存在しない対象の7例を確認しました。実際の通知、既存データの補正、同じ行の複数インスタンスを更新した場合のcallback選択は、この例では実行していません。
