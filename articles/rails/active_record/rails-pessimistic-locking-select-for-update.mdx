## 概要

`with_lock`をRubyの排他制御のように捉えていたため、何をロックし、いつ解放され、別プロセスへどう効くのかが曖昧だった。SQLへ降りて考えることで、行ロックの範囲と限界が明確になった。

`lock!`と`with_lock`はDBトランザクション上の悲観的ロックを扱うAPIであり、プロセス内Mutexではない。守れるのは、対象DBとトランザクションが提供するロック範囲だけである。

## この記事で学べること

- 悲観的ロックと楽観的ロックの違い
- `lock!`と`with_lock`の呼び出し形
- 生成される`SELECT ... FOR UPDATE`
- ロック保持期間はトランザクション終了まで
- 別プロセス・別Podからも同じDB行に効く理由
- 対象行が存在しない場合に何を守れないか

## 実装コード例

```ruby
class Account < ApplicationRecord
  def withdraw!(amount)
    with_lock do
      raise "insufficient" if balance < amount

      update!(balance: balance - amount)
    end
  end
end
```

```sql
SELECT *
FROM accounts
WHERE id = 42
FOR UPDATE;
```

### 当初の理解・誤解

当初は、API名やメソッド名から直感的に挙動を推測していました。しかし実際には、`lock!`と`with_lock`はDBトランザクション上の悲観的ロックを扱うAPIであり、プロセス内Mutexではない。守れるのは、対象DBとトランザクシ... という観点で見る必要がありました。

### 観測したこと

- 2スレッド/2接続で同じ行を更新する最小再現
- SQLログ
- デッドロックを避けるためID順でロックする例
- タイムアウトをテストする際は`sleep`依存を避け、同期プリミティブを使う

### 修正案の比較

| 方針 | 見るべき点 |
| --- | --- |
| 悲観的ロック | 競合を直列化しやすいが、待機・デッドロック・スループット低下 |
| 楽観的ロック | 競合が少ない場合に効率的だが、リトライ設計が必要 |

## 内部動作

Railsの抽象化は、Rubyオブジェクト、Active Record、SQL、DBトランザクションの上に成り立っています。重要なのは、Railsのメソッド呼び出しがそのままDBの履歴や外部サービスの状態になるわけではない、という点です。

- 行ロックはDB接続とトランザクションに紐づく
- Rubyのスレッドロックとは別物
- ロック句や挙動はPostgreSQL/MySQL等で差がある

```text
Ruby object
  -> Active Record
  -> SQL / transaction
  -> database row
  -> callback or job boundary
```
