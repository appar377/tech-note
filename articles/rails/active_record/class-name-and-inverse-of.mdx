関連名を`posts`、モデルを`AuthoredPost`、外部キーを`writer_id`にしたいとき、`class_name`だけで設定は済むでしょうか。関連先のクラスと、DBで結び付ける列は別の指定です。さらに、子から親へ戻ったときに同じRubyオブジェクトを参照するかは、逆関連の扱いに関係します。

ここでは著者と記事の小さな例で三つを分けます。Ruby 3.4.4、Active Record 8.1.3、pg 1.6.3、PostgreSQL 17.10の専用ローカルDBで、新規親子・参照の同一性・保存に関する8例をRSpecで確認しています。

以下の二つのテーブルを用意します。コード中の名前や記事名は合成値です。保存例があるため、使い捨てのローカルDBを使います。

- `association_authors`：主キー`id`と`name:string`。
- `authored_posts`：主キー`id`、`title:string`、`writer_id:bigint`。`writer_id`は`association_authors.id`を参照する外部キーです。

各列は`NULL`を許可せず、`writer_id`にインデックスを付けます。モデル定義から順にRuby例を実行できる構成です。末尾のRSpec抜粋はテスト用の別ブロックです。

## クラス・列・逆関連をそれぞれ指定する

```ruby
class AssociationAuthor < ActiveRecord::Base
  self.table_name = "association_authors"

  has_many :posts,
    class_name: "AuthoredPost",
    foreign_key: "writer_id",
    inverse_of: :writer
  accepts_nested_attributes_for :posts
  validates :name, presence: true
end

class AuthoredPost < ActiveRecord::Base
  self.table_name = "authored_posts"

  belongs_to :writer,
    class_name: "AssociationAuthor",
    foreign_key: "writer_id",
    inverse_of: :posts,
    optional: false
  validates :title, presence: true
end
```

`has_many :posts`側で指定している内容は、次の三つです。

- `class_name: "AuthoredPost"`：関連先のRubyクラスを選びます。
- `foreign_key: "writer_id"`：関連を結ぶ子テーブルの列を選びます。
- `inverse_of: :writer`：子のどの関連が、この親へ戻る逆関連なのかを示します。

子の`belongs_to :writer`側も、同じ列と対応する逆関連`:posts`を指定しています。`optional: false`は、子の検証で著者の関連を必須にするための指定です。DBの外部キー制約や`NOT NULL`制約を作る設定ではありません。[Rails 8.1.3の関連付けオプション](https://api.rubyonrails.org/v8.1.3/classes/ActiveRecord/Associations/ClassMethods.html)

通常、`belongs_to :writer`からは`writer_id`が推論されます。一方、`has_many`側では親のクラス名などから外部キーを推論します。Rails 8.1.3には、明示した逆関連から相手側の外部キーを求める分岐もあるため、「`foreign_key`を書かないと必ず不一致になる」とは限りません。この例では両側に`writer_id`を書き、スキーマとの対応を明示しています。[外部キーを推論する実装](https://github.com/rails/rails/blob/v8.1.3/activerecord/lib/active_record/reflection.rb#L772-L781)

## まだIDのない親へ、子から戻れるのはなぜか

親を保存する前に、関連を通して子を組み立てます。

```ruby
author = AssociationAuthor.new(name: "Aki")
post = author.posts.build(title: "Draft")

author.id                 # => nil
post.writer_id            # => nil
post.writer.equal?(author) # => true
post.valid?               # => true
author.valid?             # => true
```

この時点では、親の行も外部キーの値もありません。それでも`post.writer`が親を返せるのは、関連の中で親への参照を持っているためです。逆関連を設定する処理は、関連元のオブジェクトを逆側の参照先へ渡します。[逆関連を設定する実装](https://github.com/rails/rails/blob/v8.1.3/activerecord/lib/active_record/associations/association.rb#L121-L144)

また、`optional: false`の検証は、`writer_id`が埋まっているかだけを確認するものではありません。この例では、まだ未保存の`author`を関連先として参照できるので、親の存在を要求する検証に通ります。[belongs_toの検証処理](https://github.com/rails/rails/blob/v8.1.3/activerecord/lib/active_record/associations/builder/belongs_to.rb#L111-L137)

`valid?`に通っても、レコードがDBへ保存されたわけではありません。ここまでの`new`と`build`は、親子をメモリ上で組み立てています。

## inverse_ofを無効にすると、何が違うか

比較用に、同じテーブルへ別のモデルを割り当てます。クラス名の対応を変え、両側の`inverse_of`を`false`にします。検証とnested attributesの設定は同じです。

```ruby
class NoInverseAuthor < ActiveRecord::Base
  self.table_name = "association_authors"

  has_many :posts,
    class_name: "NoInversePost",
    foreign_key: "writer_id",
    inverse_of: false
  accepts_nested_attributes_for :posts
  validates :name, presence: true
end

class NoInversePost < ActiveRecord::Base
  self.table_name = "authored_posts"

  belongs_to :writer,
    class_name: "NoInverseAuthor",
    foreign_key: "writer_id",
    inverse_of: false,
    optional: false
  validates :title, presence: true
end
```

このモデルでも未保存の親から子を組み立てます。

```ruby
without_inverse = NoInverseAuthor.new(name: "Mio")
unlinked_post = without_inverse.posts.build(title: "Draft without inverse")

unlinked_post.writer_id # => nil
unlinked_post.writer    # => nil
unlinked_post.valid?    # => false
unlinked_post.errors[:writer].empty? # => false
```

子には親を再検索するためのIDがなく、逆関連による親への参照もありません。そのため、親の関連を必須とする検証に通りません。親がすでに保存されていれば、外部キーで読み出して検証できる場合はありますが、それは同じRubyオブジェクトを参照することとは別です。

`inverse_of`を省略すると、Railsが自動で逆関連を推論できる場合があります。省略と`false`は同じではありません。Rails 8.1.3では、明示した`foreign_key`、`through`、スコープや設定などが自動推論の条件に影響します。比較ではその違いを曖昧にしないため、無効化を明示しています。[自動inverse推論の条件](https://github.com/rails/rails/blob/v8.1.3/activerecord/lib/active_record/reflection.rb#L699-L765)

## nested attributesでは、保存までどうつながるか

`accepts_nested_attributes_for :posts`は、親へ`posts_attributes=`という入力口を追加し、関連のautosaveを有効にします。`inverse_of`はその入力口を作る機能ではありません。[Railsのnested attributes](https://api.rubyonrails.org/v8.1.3/classes/ActiveRecord/NestedAttributes/ClassMethods.html)

新しい親へ二つの記事を渡して保存します。

```ruby
nested_author = AssociationAuthor.new(
  name: "Ren",
  posts_attributes: [{ title: "First" }, { title: "Second" }]
)
children = nested_author.posts.to_a

children.map(&:writer_id) # => [nil, nil]
children.all? { |child| child.writer.equal?(nested_author) } # => true

nested_author.save!

nested_author.persisted?             # => true
children.all?(&:persisted?)            # => true
children.map(&:writer_id).uniq        # => [nested_author.id]
AuthoredPost.where(writer_id: nested_author.id).order(:id).pluck(:title)
# => ["First", "Second"]
```

保存前の検証ではメモリ上の親を参照し、保存時には親のIDが子の`writer_id`へ入ります。親子を保存する処理は、親の保存が開始するトランザクション内で行われます。子の検証に失敗したときに親だけ残らないことも、実装に合わせて確認します。[nested attributesの保存](https://api.rubyonrails.org/v8.1.3/classes/ActiveRecord/NestedAttributes/ClassMethods.html#label-Saving)

## 別のfindでも同じオブジェクトが返るのか

`inverse_of`は、アプリ内のあらゆる読み込みを一つのオブジェクトへまとめる仕組みではありません。保存した親を二度読み直すと、同じ行を表す別のインスタンスになります。

```ruby
first = AssociationAuthor.find(nested_author.id)
second = AssociationAuthor.find(nested_author.id)

first == second       # => true
first.equal?(second)  # => false

first.name = "Only the first instance"
second.name           # => "Ren"
first == second       # => true
```

Active Recordの`==`は、同じオブジェクトである場合に加え、同じモデルクラスでIDが一致する場合にも`true`を返します。全属性の値を比較しているわけではありません。[Active Recordの==](https://api.rubyonrails.org/v8.1.3/classes/ActiveRecord/Core.html#method-i-3D-3D)

Rubyの`equal?`は、同じオブジェクトかどうかを見る比較です。逆関連が元の親を再利用しているかを調べるなら、こちらで区別します。[Ruby 3.4のequal?](https://docs.ruby-lang.org/en/3.4/BasicObject.html#method-i-equal-3F)

## 設定を変えたとき、何をテストへ残すか

未保存の親から子を組み立てる画面や処理では、「後で保存できた」だけでなく、保存前の検証と参照の関係を確かめます。次は、モデルを読み込んだRSpecの`describe`内へ置く例です。各例の前に`authored_posts`、`association_authors`の順で検証用データを削除し、空のDBから始めます。

```ruby
it "validates a child against its unsaved inverse parent without a foreign key value" do
  author = AssociationAuthor.new(name: "Aki")
  post = author.posts.build(title: "Draft")

  expect(author.id).to be_nil
  expect(post.writer_id).to be_nil
  expect(post.writer).to equal(author)
  expect(post.valid?).to be(true)
  expect(author.valid?).to be(true)
  expect(AssociationAuthor.count).to eq(0)
  expect(AuthoredPost.count).to eq(0)
end
```

一覧表示のN+1問題は、この参照の確認とは別に考えます。逆関連で親の再取得を避けられる場合があっても、必要な関連を一括で読む`includes`などの代わりにはなりません。[関連のeager loading](https://api.rubyonrails.org/v8.1.3/classes/ActiveRecord/Associations/ClassMethods.html#label-Eager+loading+of+associations)

親子が互いを参照すると、一方を保持する間は接続されたオブジェクトも参照されます。関連を含むレコード群を長寿命のキャッシュへ残すなら、何をどこまで保持するかも確認します。双方向の参照があることだけでメモリリークや使用量の大小を判断することはできません。

クラスが違う問題、外部キーの列が違う問題、同じオブジェクトを参照していない問題を分けると、修正すべき設定も見つけやすくなります。`inverse_of`で、クラス名やスキーマの不一致まで直そうとしないことが要点です。
