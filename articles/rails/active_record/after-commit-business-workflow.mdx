注文の確定後に通知を送るとして、`after_commit`の中で通知処理が失敗したら、注文まで取り消されるでしょうか。取り消されません。callbackが始まった時点で、DBの更新はすでにコミットされています。

`after_commit`は「確定した更新に対して処理を始める」時点を提供します。外部システムへの配送成功や、その後の再試行まで保証する機能ではありません。配送漏れから復旧する必要があるなら、送る予定もDBに残す設計を考えます。

以下はRuby 3.4.4、Active Record 8.1.3、pg gem 1.6.3、PostgreSQL 17.10の専用ローカルDBで8例を確認した説明用の例です。実サービスへは接続せず、外部の受信側はメモリ上のfakeで置き換えます。

## after_saveとafter_commitでは、失敗した時点のDB状態が違う

`after_save`は保存を囲むトランザクションの内側で実行されます。その後でロールバックされる可能性があるため、ここから外部へ通知すると、取り消された更新を通知してしまう場合があります。

`after_commit`はコミット後に実行されます。このため、ロールバックした更新では呼ばれません。一方、callbackが例外を返しても、確定済みのDB更新は元に戻りません。[RailsのTransaction Callbacksの説明](https://github.com/rails/rails/blob/v8.1.3/guides/source/active_record_callbacks.md#transaction-callbacks)で、この違いが明記されています。

次のモデルは、その境界を調べるためのものです。`save_probe`と`commit_probe`には、テストで観察したい処理を渡します。業務処理で使う`WorkflowOrder`と、callbackを試すクラスを分けています。

```ruby
class WorkflowOrder < ActiveRecord::Base
  self.table_name = "workflow_orders"
end

class OutboxEvent < ActiveRecord::Base
  self.table_name = "outbox_events"
end

# An isolated callback probe; the business service below uses WorkflowOrder.
class CallbackProbeOrder < WorkflowOrder
  attr_accessor :save_probe, :commit_probe

  after_save { save_probe&.call }
  after_commit { commit_probe&.call }
end
```

説明用の`workflow_orders`テーブルには、文字列の`status`があります。callbackから意図的に例外を発生させても、保存した行は残ります。

```ruby
order = CallbackProbeOrder.new(
  status: "confirmed",
  commit_probe: -> { raise IOError, "synthetic external failure" }
)

begin
  order.save!
rescue IOError
  # 境界を確かめるため、ここでは意図した例外を受け止めます。
end

WorkflowOrder.find(order.id).status # => "confirmed"
```

呼び出し元で`save!`が例外になったことだけを見て、「注文は未保存だから同じ操作を最初からやり直す」と判断すると、すでに確定した処理を重ねる可能性があります。DBの更新結果と外部配送の結果を、それぞれ確認できるようにします。

## callbackの条件だけで、業務上の出来事を表せるか

モデルのcallbackを入口にする場合、通常の`update!`以外の更新経路も調べます。`update_columns`はvalidationとcallbackを通らずに更新します。直接SQLで書き換えても、Rubyのmodel callbackは実行されません。[update_columnsのAPI](https://api.rubyonrails.org/v8.1.3/classes/ActiveRecord/Persistence.html#method-i-update_columns)に、この省略が示されています。

また、`saved_change_to_status?`が参照するのは、最後の保存に対応する変更情報です。一つのトランザクション内で何度も保存した場合の業務上の履歴全体ではありません。`reload`も変更情報を消します。[Dirty Trackingの実装](https://github.com/rails/rails/blob/v8.1.3/activerecord/lib/active_record/attribute_methods/dirty.rb)が対象とする範囲を確認し、複数回保存をまたぐ重要な出来事を後から推測しないようにします。

次の例では「注文を確定する」という操作をサービスとして明示し、その操作の中で配送予定を記録します。更新をすべてcallbackへ寄せるかどうかではなく、どの操作を一つの業務上の入口にするかを決めます。

## 注文の更新と、配送する予定を同じトランザクションに入れる

`outbox_events`には次の列を用意します。

- `event_key`: イベントを識別する文字列。DBにunique indexを作ります。
- `order_id`と`kind`: どの注文について何が起きたかを表します。
- `delivered_at`: 配送済みの記録。未配送なら`nil`です。

この例では、注文は`pending`から`confirmed`へ一度だけ進むものとします。再び未確定へ戻して確定し直す業務や、一注文で複数種類の確定を行う業務は含めません。

```ruby
class ConfirmWorkflowOrder
  def call(order_id)
    WorkflowOrder.transaction do
      order = WorkflowOrder.lock.find(order_id)
      case order.status
      when "pending"
        order.update!(status: "confirmed")
        OutboxEvent.create!(
          event_key: "order-confirmed:#{order.id}",
          order_id: order.id,
          kind: "order_confirmed"
        )
      when "confirmed"
        # Repeating this one-time transition does not create a new event.
      else
        raise ArgumentError, "order must be pending or confirmed"
      end
      order
    end
  end
end
```

`order.update!`と`OutboxEvent.create!`は同じトランザクションに属します。後者に失敗すれば、前者もロールバックされます。二つのモデルは同じDB接続を使う前提です。Active Recordのトランザクションは[DB接続ごとの処理](https://api.rubyonrails.org/v8.1.3/classes/ActiveRecord/Transactions/ClassMethods.html)なので、Outboxを別のDBへ分けると、この原子性はそのままでは得られません。

`lock.find`で注文の行をロックし、状態の確認と変更を同じ範囲で行っています。[Railsの悲観ロック](https://api.rubyonrails.org/v8.1.3/classes/ActiveRecord/Locking/Pessimistic.html)は`SELECT ... FOR UPDATE`を利用します。[PostgreSQLの行ロック](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-ROWS)の下で、同じ注文を更新する処理が競合した場合の境界を作ります。

確定済みの注文に同じサービスを呼んだ場合は、追加のイベントを作りません。キーは確定という一回の出来事に対応させ、DBのunique indexでも重複を制限します。ただし、ほかのコードが直接`status`を変えたために配送予定が欠けた場合を、このサービスが自動修復するわけではありません。入口を迂回する書き込み経路も整理する必要があります。

このように、業務データと配送予定を同時に記録する方法がTransactional Outboxです。[AWSのパターン説明](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)も、DB更新とイベントの記録を同じトランザクションに置き、後から配送する構成を示しています。

## 配送した後、配送済みの記録を付ける

次は、イベント一件を送る関数です。コミット済みのイベントを、注文確定のトランザクションの外から処理する前提です。通常は未配送のイベントを探す処理やジョブから、この関数を呼びます。

```ruby
class DeliverOutboxEvent
  def initialize(gateway:, after_delivery: nil, clock: -> { Time.current })
    @gateway = gateway
    @after_delivery = after_delivery
    @clock = clock
  end

  def call(event_id)
    event = OutboxEvent.find(event_id)
    return :already_delivered if event.delivered_at

    @gateway.deliver(
      event_key: event.event_key,
      order_id: event.order_id,
      kind: event.kind
    )
    @after_delivery&.call # A test seam for a stop after remote success.
    event.update!(delivered_at: @clock.call)
    :delivered
  end
end
```

`gateway.deliver`は、受信側の成功を確認した場合だけ正常に戻り、失敗時には例外を返す契約です。配送前に`delivered_at`を更新すると、その直後に停止した場合、実際には送っていないのに配送済みになります。この例では、成功を確認してから更新しています。

それでも、成功した直後から`delivered_at`を書き込むまでの間に停止する可能性は残ります。再起動後には未配送として見つかるため、同じ通知をもう一度送ります。Outboxが配送漏れからの回復を助けることと、重複配送が起きないことは別です。

`after_delivery`は、この停止箇所をテストで再現するために置いています。実際のプロセス停止や通信障害を完全に再現する機構ではありません。

## 同じキーで再送したとき、受信側は何を約束するか

以下のfakeは、同じ`event_key`と内容なら、配送の呼び出しが複数回あっても処理結果を一件に保ちます。同じキーで違う内容を送った場合は拒否します。

```ruby
# Memory-only fake: this is a contract for tests, not a production receiver.
class FakeWorkflowGateway
  attr_reader :attempts, :effects

  def initialize
    @attempts = []
    @effects = {}
  end

  def deliver(event_key:, order_id:, kind:)
    payload = { order_id: order_id, kind: kind }
    @attempts << event_key
    if @effects.key?(event_key) && @effects.fetch(event_key) != payload
      raise ArgumentError, "event key was reused with a different payload"
    end
    @effects[event_key] ||= payload
    :accepted
  end
end
```

このHashはメモリ上の説明用実装です。実際の受信側では、キーの保存期間、同時到着時の扱い、処理結果と重複排除記録の保存方法を確認します。キーをリクエストへ付けるだけで、相手が二重処理を防ぐわけではありません。

配送直後の停止を、次のRSpecで確かめます。同じfakeを保持したままworkerを作り直し、受信側は処理済みだが送信側は未記録、という状態から再試行します。

```ruby
RSpec.describe "配送直後に停止したworkerの再試行" do
  it "同じイベントキーを使い、fake側の処理結果を一件に保つ" do
    order = WorkflowOrder.create!(status: "pending")
    ConfirmWorkflowOrder.new.call(order.id)
    event = OutboxEvent.find_by!(order_id: order.id)
    gateway = FakeWorkflowGateway.new
    interrupted = DeliverOutboxEvent.new(
      gateway: gateway,
      after_delivery: -> { raise IOError, "synthetic worker stop" }
    )

    expect { interrupted.call(event.id) }.to raise_error(IOError)
    expect(event.reload.delivered_at).to be_nil
    expect(gateway.effects.size).to eq(1)

    retry_worker = DeliverOutboxEvent.new(gateway: gateway)
    expect(retry_worker.call(event.id)).to eq(:delivered)
    expect(gateway.attempts).to eq([event.event_key, event.event_key])
    expect(gateway.effects.size).to eq(1)
    expect(event.reload.delivered_at).not_to be_nil
  end
end
```

ここで確認しているのは、同じキーを再使用する送信側と、重複を一件にまとめるfakeの契約です。外部システムをまたぐexactly-onceの保証を証明しているわけではありません。

## callbackへ残す処理と、配送基盤へ移す処理を決める

DB確定後にキャッシュを消すような処理は、`after_commit`が役立つ場面です。その場合も、失敗したときに古い値がどれほど残るか、後から再構築できるかを確認します。処理が必要かどうかを呼び出し元で明示したいならサービスを使い、配送予定を失うと復旧できない処理ならOutboxのような永続的な記録を検討します。

ジョブを使う場合も、投入成功と外部処理の成功は分かれます。利用するキューの再試行・重複実行・保存の保証を確認します。この最小例には、未配送イベントの定期走査、複数workerの取得競合、バックオフ、失敗回数の記録、配送順序、監視、古いイベントの削除は含めていません。これらを設計して初めて、配送を運用し続けられます。

Outboxには、後の配送で必要になる内容も記録します。この例は注文IDと出来事の種類だけですが、当時の宛先や金額が必要なら、後で変わり得る注文の現在値だけから組み立てないようにします。

付属の8例では、callbackの実行時点、commit後の例外、callbackを通らない更新、更新と配送予定の同時保存、unique制約違反時のロールバック、配送失敗、配送直後の停止、キーの再使用を扱います。実HTTP、実ジョブキュー、OSによるプロセス終了、複数workerの同時配送は検証範囲に含めません。
