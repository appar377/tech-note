履歴から最新の値を取り出し、まだない行だけ現在値のテーブルへ追加したい。この処理は、「どの履歴を選ぶか」と「どの行へ書き込むか」を分けると読みやすくなります。

ここでは説明用の在庫履歴を使い、SKUごとに一行を選んでから不足行を補います。既存の在庫値は上書きしない契約です。PostgreSQL 17.10で、候補の選択と初回・再投入後の結果を確認しました。SQLを使うだけで高速になるという比較はしていません。

## 同じSKUの履歴から、どの行を選びますか

次のSQLを同じ検証用接続で実行する前提です。一時テーブルなので、接続を切り替えると利用できません。

```sql file=raw_summary/setup.sql
CREATE TEMPORARY TABLE raw_stock_events (
  id integer PRIMARY KEY,
  sku text NOT NULL,
  quantity integer NOT NULL CHECK (quantity >= 0),
  recorded_at timestamptz NOT NULL
);

CREATE TEMPORARY TABLE raw_stock_levels (
  sku text PRIMARY KEY,
  quantity integer NOT NULL CHECK (quantity >= 0)
);

INSERT INTO raw_stock_events (id, sku, quantity, recorded_at) VALUES
  (1, 'A', 3, '2026-09-01 00:00:00+00'),
  (2, 'A', 5, '2026-09-02 00:00:00+00'),
  (3, 'A', 7, '2026-09-02 00:00:00+00'),
  (4, 'B', 0, '2026-09-03 00:00:00+00'),
  (5, 'C', 4, '2026-09-04 00:00:00+00');

INSERT INTO raw_stock_levels (sku, quantity) VALUES ('C', 99);
```

SKU Aには同じ時刻の履歴が二つあります。ここでは「記録時刻が新しい方、同時刻ならidが大きい方」という説明用の規則を採用します。idが大きければ業務上も必ず新しい、という一般則ではありません。

```sql file=raw_summary/latest.sql
WITH ranked AS (
  SELECT id, sku, quantity,
    ROW_NUMBER() OVER (
      PARTITION BY sku
      ORDER BY recorded_at DESC, id DESC
    ) AS rn
  FROM raw_stock_events
)
SELECT id, sku, quantity
FROM ranked
WHERE rn = 1
ORDER BY sku;
```

確認する期待値は次の3行です。

| id | sku | quantity |
| --- | --- | --- |
| 3 | A | 7 |
| 4 | B | 0 |
| 5 | C | 4 |

`PARTITION BY sku`は順位を付ける範囲を分け、`ORDER BY recorded_at DESC, id DESC`はその範囲内の順番を決めます。時刻だけでは同順位の行の順が決まらないため、今回の規則に必要なidも指定しています。[PostgreSQLのWindow Function](https://www.postgresql.org/docs/17/tutorial-window.html)

Window Functionは、集計結果一行へまとめるGROUP BYとは異なり、元の行を残したまま値を計算します。このSQLでは、その後で外側のSELECTが`rn = 1`へ絞っています。順位を計算するSELECT自身のWHEREへ`rn = 1`を書く形にはしません。

## 選んだ行のうち、何を書き込みますか

現在値のテーブルには、すでにCが99で入っています。最新履歴のCが4でも、今回の処理では99を維持します。

```sql file=raw_summary/backfill.sql
WITH ranked AS (
  SELECT sku, quantity,
    ROW_NUMBER() OVER (
      PARTITION BY sku
      ORDER BY recorded_at DESC, id DESC
    ) AS rn
  FROM raw_stock_events
)
INSERT INTO raw_stock_levels (sku, quantity)
SELECT ranked.sku, ranked.quantity
FROM ranked
WHERE ranked.rn = 1
  AND NOT EXISTS (
    SELECT 1
    FROM raw_stock_levels AS existing
    WHERE existing.sku = ranked.sku
  )
ON CONFLICT (sku) DO NOTHING
RETURNING sku, quantity;
```

`INSERT ... SELECT`は、SELECTが返した列を指定した順に挿入します。Rubyへ各行を返してモデルを一つずつ作る手順はありません。ただし、このSQLはRailsモデルのvalidationやcallbackを呼びません。現在値のテーブルに付けた非負のCHECK制約と主キーは、DB側の制約として働きます。[INSERTの仕様](https://www.postgresql.org/docs/17/sql-insert.html)と[DB制約](https://www.postgresql.org/docs/17/ddl-constraints.html)

`NOT EXISTS`は、問い合わせ時点で同じSKUがない行を選びます。その確認だけでは、別の処理が直後に同じSKUを作ることまでは防げません。最後の`ON CONFLICT (sku) DO NOTHING`で、主キーに衝突した場合も既存行を上書きしない契約に合わせています。競合する別処理の値が正しいかまで、このSQLで判断するわけではありません。

`RETURNING`が返すのは、この文が実際に挿入した行です。初回はAの7とBの0を期待しますが、RETURNINGの行順は固定しません。比較するときはSKUで並べます。

## 再投入しても同じ結果になる範囲を確かめます

書き込み後は、このSELECTで現在値を読みます。

```sql file=raw_summary/read.sql
SELECT sku, quantity
FROM raw_stock_levels
ORDER BY sku;
```

初回の期待値はAが7、Bが0、Cが99です。続けて同じ`backfill.sql`をもう一度実行し、`read.sql`で再取得します。

| 確認点 | 初回 | 2回目 |
| --- | --- | --- |
| 新たに挿入される行 | A、B | なし |
| Aの現在値 | 7 | 7 |
| Bの現在値 | 0 | 0 |
| Cの現在値 | 99 | 99 |

この契約は不足行を補うためのものです。あとからAの新しい履歴が追加されても、Aの現在値は更新しません。最新履歴へ常に同期する処理が必要なら、更新を許す条件や古い履歴の再投入を別に設計します。

また、先に実行した`latest.sql`の確認結果と、後から実行する`backfill.sql`は別の文です。間で履歴が増える状況なら同じ候補集合になるとは限りません。このfixtureは入力を固定し、並行処理を走らせずに確認する範囲です。

## Railsから使うときに、構文以外で残る判断は何ですか

実アプリでは、対象DB、トランザクションの範囲、一度に処理する量を決めます。一つのSQLで処理できても、大量の書き込みにはロックやログ出力などのコストがあります。この小さな例から、本番の処理時間や再開方法は判断できません。

外から受け取る値をSQL文字列へ直接埋め込まず、Active Recordの問い合わせAPIやbindを使う設計にします。接続APIの`exec_query`はbindを受け取れますが、テーブル名や並び順などの識別子を入力値用のbindで自由に置き換えられるわけではありません。[Railsの接続API](https://api.rubyonrails.org/v8.1.3/classes/ActiveRecord/ConnectionAdapters/DatabaseStatements.html#method-i-exec_query)

MySQLのSQLをPostgreSQLへ移す場合も、構文名だけで同じ処理だと考えない方が確実です。たとえばMySQLの`LENGTH`はバイト数、PostgreSQLでtextに使う`length`は文字数です。PostgreSQLでバイト数が必要なら`octet_length`を使います。文字数とバイト数の差だけで、全角文字の有無を判定することもできません。[MySQL 8.4の文字列関数](https://dev.mysql.com/doc/refman/8.4/en/string-functions.html#function_length)、[PostgreSQL 17の文字列関数](https://www.postgresql.org/docs/17/functions-string.html)

更新するUPSERTへ進む場合は[ON DUPLICATE KEY UPDATEとON CONFLICTの違い](/tech-note/articles/rails/sql/on-duplicate-key-update/)を確認します。今回のように既存行を維持する処理では、その契約を先に固定したうえで、候補の選択と書き込みを別々に読めるSQLにします。
