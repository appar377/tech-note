「利用者ごとの最新ログインを1件」にするには、時刻が同じ行をどう選ぶか、時刻がNULLの行を候補に残すかまで決めます。`ROW_NUMBER()`は連番を付けますが、業務上の「最新」の定義まで補ってはくれません。

以下は合成データによる例です。PostgreSQL 17.10で、本文のSQLと同時刻・NULL・絞り込み位置を含む7ケースの結果を確認しています。

## 同じ時刻の2行に、どちらを1番にしますか

説明用のログイン履歴を作ります。利用者1の`id=11, 12`は同時刻、利用者3は時刻がすべてNULLです。本文のSQLは同じ接続で掲載順に実行し、最後に`ROLLBACK`できます。

```sql
BEGIN;
SET LOCAL TIME ZONE 'UTC';
CREATE TEMP TABLE rn_logins (
  id integer PRIMARY KEY,
  user_id integer NOT NULL,
  logged_in_at timestamptz
) ON COMMIT DROP;
INSERT INTO rn_logins (id, user_id, logged_in_at) VALUES
  (10, 1, '2026-10-02 10:00:00+00'),
  (11, 1, '2026-10-02 11:00:00+00'),
  (12, 1, '2026-10-02 11:00:00+00'),
  (13, 1, NULL),
  (20, 2, '2026-10-02 09:00:00+00'),
  (21, 2, NULL),
  (30, 3, NULL),
  (31, 3, NULL);
```

この例では、時刻が新しい行を優先し、同時刻なら大きいidを採用します。idは主キーなので、この列まで比較すると候補間の順序が決まります。ただし「大きいidなら実際の発生時刻も遅い」と主張しているわけではなく、同時刻を解決するための説明用の規則です。

```sql
SELECT id, user_id,
  ROW_NUMBER() OVER (
    PARTITION BY user_id
    ORDER BY logged_in_at DESC NULLS LAST, id DESC
  ) AS row_num
FROM rn_logins
ORDER BY user_id, row_num;
```

期待する番号は次のとおりです。

| user_id | idの順序 | row_num |
| --- | --- | --- |
| 1 | 12, 11, 10, 13 | 1, 2, 3, 4 |
| 2 | 20, 21 | 1, 2 |
| 3 | 31, 30 | 1, 2 |

`PARTITION BY`は番号を振り直す単位、window内の`ORDER BY`はその中での並び方を指定します。時刻だけで並べると同時刻のどちらに1番が付くかを固定できません。安定した1件を必要とするなら、最後まで順序を決められる列を追加します。[PostgreSQLのwindow function入門](https://www.postgresql.org/docs/17/tutorial-window.html)

一番外側の`ORDER BY user_id, row_num`は、結果を表示する順序です。window内の順序とは役割が異なり、結果全体の順序を保証したいなら外側にも指定します。[PostgreSQLのORDER BY](https://www.postgresql.org/docs/17/queries-order.html)

## 最新1件を残す条件は、どこに書きますか

window functionは`WHERE`で絞った行集合を対象に計算します。同じSELECTの`WHERE row_num = 1`に出力aliasを置いて、その計算結果を絞ることはできません。CTEまたは副問い合わせで一段分けます。[PostgreSQLのwindow functionの評価位置](https://www.postgresql.org/docs/17/tutorial-window.html)

```sql
WITH ranked AS (
  SELECT id, user_id, logged_in_at,
    ROW_NUMBER() OVER (
      PARTITION BY user_id
      ORDER BY logged_in_at DESC NULLS LAST, id DESC
    ) AS row_num
  FROM rn_logins
)
SELECT user_id, id
FROM ranked
WHERE row_num = 1
ORDER BY user_id;
```

この例の期待値は`(user_id, id) = (1, 12), (2, 20), (3, 31)`です。`WHERE row_num <= 2`にすれば、各利用者から最大2行を残せます。結果全体を2行に切る`LIMIT 2`とは異なります。

条件をwindow計算より前へ置くと、候補自体が変わります。「最新行を取ってから条件を確認する」のか、「条件を満たす履歴だけから最新を取る」のかを、先に決めます。

## NULLの日時を、最新候補に残しますか

PostgreSQLの`DESC`は、指定がなければNULLを先に並べます。この例で`NULLS LAST`を外すと、利用者1は`id=13`、利用者2は`id=21`が1番になります。NULLを日時の新旧と同じ意味で扱わないため、末尾へ置く指定を明示しています。[PostgreSQLのNULLの並び順](https://www.postgresql.org/docs/17/queries-order.html)

ただし`NULLS LAST`は行を除外する指定ではありません。すべてNULLの利用者3では、idの規則に従って31が残ります。「日時不明なら結果に含めない」が要件なら、候補を作る内側で除外します。

```sql
WITH ranked AS (
  SELECT id, user_id, logged_in_at,
    ROW_NUMBER() OVER (
      PARTITION BY user_id
      ORDER BY logged_in_at DESC NULLS LAST, id DESC
    ) AS row_num
  FROM rn_logins
  WHERE logged_in_at IS NOT NULL
)
SELECT user_id, id
FROM ranked
WHERE row_num = 1
ORDER BY user_id;
```

こちらの期待値は`(1, 12), (2, 20)`だけです。日時が分からない利用者に対して、存在しない最新日時を補う処理はしていません。

MySQL 8.4では、NULLは昇順で先、降順で後に並ぶため、PostgreSQLの既定と異なります。両方でwindow functionを使えても、NULLを含む並びはそのまま移植して同じ結果になるとは限りません。MySQL向けの構文と並び順は別に確認します。この稿ではMySQLの実行検証はしていません。[MySQLのwindow ORDER BY](https://dev.mysql.com/doc/refman/8.4/en/window-functions-usage.html)

## 同率の最新行をすべて残したい場合はどうしますか

`ROW_NUMBER`は行ごとに番号を付けます。同じ時刻を同順位にしたい場合は、`RANK`や`DENSE_RANK`で何を同値とみなすかを指定します。下では、行番号にだけidを追加し、順位は日時だけで比較します。

```sql
SELECT id,
  ROW_NUMBER() OVER (ORDER BY logged_in_at DESC NULLS LAST, id DESC) AS row_num,
  RANK() OVER (ORDER BY logged_in_at DESC NULLS LAST) AS rank_num,
  DENSE_RANK() OVER (ORDER BY logged_in_at DESC NULLS LAST) AS dense_rank_num
FROM rn_logins
WHERE user_id = 1
ORDER BY row_num;
```

| id | row_num | rank_num | dense_rank_num |
| --- | --- | --- | --- |
| 12 | 1 | 1 | 1 |
| 11 | 2 | 1 | 1 |
| 10 | 3 | 3 | 2 |
| 13 | 4 | 4 | 3 |

同時刻の`id=11, 12`はいずれも`rank_num=1`です。`RANK`は次を3位、`DENSE_RANK`は2位にします。順位用のORDER BYにも一意なidを足すと同率ではなくなるので、1行に決める条件と同率を認める条件を混同しないようにします。[PostgreSQLの順位関数](https://www.postgresql.org/docs/17/functions-window.html)

```sql
ROLLBACK;
```

このクエリは最新候補を取り出すもので、元の履歴は削除しません。重複データの整理へ使う場合も、まず[重複キーの定義](/tech-note/articles/rails/sql/sql-group-by-having-duplicates)を確かめます。保持すべき関連や履歴を確認せず、`row_num > 1`をそのまま削除条件にする例にはしていません。

Railsからは、このCTEをSQLとして実行して結果を受け取れます。任意の検索条件を足す場合も、window計算の前後のどちらへ入るかを確認します。ここで検証対象にしているのはSQLの結果で、Active Recordへの組み込みや実データでの実行計画・性能は別途確認が必要です。
