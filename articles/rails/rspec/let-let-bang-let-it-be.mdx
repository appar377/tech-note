一覧のテストで、`let(:entry) { create(:entry) }`と書いたのに、一覧が空のままになることがあります。`let`は値を使うまで評価しないため、対象を検索しただけではそのレコードは作られません。

`let!`に変えるとexampleの前に評価されます。さらにTestProfの`let_it_be`を使うと、初期化の範囲がexample groupへ変わります。この三つは、評価する時点と結果を使い回す範囲を分けて選びます。

## letとlet!は、いつ評価されるか

まずDBを使わず、記事の追加とその順序を記録するクラスで比べます。以下の最初の二つのRubyブロックだけなら、RSpecを使える純Ruby環境で実行できます。

```ruby
require "rspec/autorun"

class LifecycleCatalog
  attr_reader :entries, :events

  def initialize
    @entries = []
    @events = []
  end

  def add(label)
    events << [:add, label]
    entries << label
    label
  end
end
```

`let`と`let!`のどちらも、値を繰り返し参照したときは同じexample内の結果を再利用します。違いは、最初の評価を待つか、before hookで呼び出すかです。[RSpecのletとlet!](https://rspec.info/features/3-13/rspec-core/helper-methods/let/)

```ruby
RSpec.describe LifecycleCatalog do
  let(:catalog) { described_class.new }

  context "letで記事を追加する場合" do
    let(:entry) { catalog.add("Ruby") }

    it "参照しない間は一覧へ追加しない" do
      expect(catalog.entries).to eq([])
      expect(catalog.events).to eq([])
    end

    it "最初の参照で追加し、再参照では追加しない" do
      expect(catalog.events).to eq([])
      expect(entry).to eq("Ruby")
      expect(entry).to eq("Ruby")
      expect(catalog.entries).to eq(["Ruby"])
      expect(catalog.events).to eq([[:add, "Ruby"]])
    end
  end

  context "let!で記事を追加する場合" do
    let!(:entry) { catalog.add("RSpec") }

    it "entryを呼ばなくてもexampleの開始前に追加する" do
      expect(catalog.entries).to eq(["RSpec"])
      expect(catalog.events).to eq([[:add, "RSpec"]])
    end

    it "別exampleでは新しい一覧へ一度だけ追加する" do
      expect(entry).to eq("RSpec")
      expect(catalog.entries).to eq(["RSpec"])
      expect(catalog.events).to eq([[:add, "RSpec"]])
    end
  end

  context "beforeとlet!を並べる場合" do
    before { catalog.events << :before_first }
    let!(:entry) { catalog.add("Hooks") }
    before { catalog.events << :before_last }

    it "同じgroupでは登録したbefore hookの順で準備する" do
      expect(catalog.events).to eq([:before_first, [:add, "Hooks"], :before_last])
      expect(catalog.entries).to eq(["Hooks"])
    end
  end
end
```

最初のcontextでは、`catalog`は読んでも`entry`は呼んでいません。そのため追加は起きません。次のexampleで`entry`を二度読んでも、`add`の呼び出しは一度です。

`let!`のcontextでは、example内から`entry`を読まなくても記事が追加されています。この性質は、検索・集計・件数のテストで「実行前にデータが存在すること」が前提になる場合に役立ちます。

最後の例は、`let!`が「ほかのbeforeより必ず先」ではないことを示すためのものです。RSpec 3.13.6の実装では、`let!`は`let`を定義し、それを呼ぶ`before`を登録します。同じgroupでの登録順が、この例の準備順になります。[let!の実装](https://github.com/rspec/rspec/blob/rspec-core-v3.13.6/rspec-core/lib/rspec/core/memoized_helpers.rb#L400-L403)

親groupや`prepend_before`なども組み合わせる場合は、そのhookの順序も含めて確認します。[RSpecのbefore/after hooks](https://rspec.info/features/3-13/rspec-core/hooks/before-and-after-hooks/)

## let_it_beでは、何が共有されるか

`let_it_be`はRSpec標準ではなく、TestProfが提供します。初期化ブロックをgroup開始時の`before_all`で実行し、その結果を各exampleから参照できるようにします。DBレコードを毎exampleで作り直す方法とは、共有の範囲が違います。[TestProf 1.6.3のlet_it_be](https://github.com/test-prof/test-prof/blob/v1.6.3/docs/recipes/let_it_be.md)

| 定義 | 初期化される時点 | この例での値の範囲 |
| --- | --- | --- |
| `let` | example内の最初の参照 | そのexample内で再利用 |
| `let!` | example前のbefore hook | そのexample内で再利用 |
| `let_it_be` | group開始時のbefore_all | group内で初期値を共有 |

ここからはDBを使います。Ruby 3.4.4、RSpec 3.13.0（core 3.13.6）、TestProf 1.6.3、Active Record 8.1.3、PostgreSQL 17.10を対象にしています。前節を含む7例をローカルで実行し、すべて成功しました。

使い捨てDBへ接続し、`let_lifecycle_records`に主キー`id`と`label:string NOT NULL`を用意してから、後続のコードを読み込みます。全ブロックを連結して実行する場合も、事前にActive Recordの接続とschemaを設定してください。TestProfのmodifierを登録するため、Active Recordを先に読み込みます。

```ruby
require "active_record"
gem "test-prof", "1.6.3"
require "test_prof/recipes/rspec/let_it_be"

class LetLifecycleRecord < ActiveRecord::Base
  self.table_name = "let_lifecycle_records"
end
```

次は読み取り専用のカテゴリ一件を共有する例です。`before(:context)`の削除は検証専用テーブルを空にするためのもので、本番DBでは実行しません。

```ruby
RSpec.describe "let_it_beで読み取り用のDB行を共有する" do
  before(:context) { LetLifecycleRecord.delete_all }
  let_it_be(:category, freeze: true) { LetLifecycleRecord.create!(label: "Reference") }
  before_all { @original_category = category }

  it "exampleから参照する前にDB行が用意されている" do
    expect(LetLifecycleRecord.pluck(:label)).to eq(["Reference"])
  end

  it "初期化で作った同じインスタンスを読み取る" do
    expect(category).to equal(@original_category)
    expect(category.label).to eq("Reference")
    expect(category).to be_frozen
    expect(LetLifecycleRecord.count).to eq(1)
  end
end
```

`category`を参照する前でもDBに行があり、参照した場合は初期化で作ったオブジェクトを使っています。`freeze: true`は、その共有オブジェクトの属性変更を検出するために付けています。DBの行を他の経路から更新できなくする制約ではありません。

## groupの後片付けと、exampleの分離は同じか

TestProfの`before_all`は、group全体をDBトランザクションで包み、groupの終了時に戻します。しかし、各exampleの間でDBを戻す処理までは追加しません。書き込みを含むspecでは、RSpec Railsのtransactional fixturesなど、example単位の分離を別に用意する必要があります。[before_allの適用範囲](https://github.com/test-prof/test-prof/blob/v1.6.3/docs/recipes/before_all.md)

さらに、DBを戻しても、Rubyオブジェクトの属性やキャッシュが自動で元に戻るとは限りません。`let_it_be`が返した同じオブジェクトを更新すると、次のexampleが変更後の値を見る場合があります。[共有状態とreload/refind/freeze](/tech-note/articles/rails/rspec/let-it-be-shared-state-pollution)では、DBの行とRubyのメモリを分けて扱います。

`let`でも、外側で一度作ったオブジェクトを返すだけなら、それを自動複製はしません。今回の純Ruby例が独立しているのは、`let(:catalog)`の中で`new`しているためです。「letならどの値でも独立する」という意味ではありません。

## 置き換える前に、何を確認するか

必要なときだけ作るなら`let`、検索や集計の前提として先に存在させたいなら`let!`を使うと、準備の意図を表せます。`let_it_be`は、複数exampleが共通して読むデータについて、初期化の繰り返しが負担になっているときに検討します。

この例で記録しているのは`add`の呼び出し順と回数で、性能測定ではありません。置き換えを判断する際は、同じ環境・同じexample集合で実行時間とデータ作成回数を計測し、順序を変えても結果が変わらないことを確かめます。速さの数値や改善率はここでは示していません。

更新や削除の対象まで共有する必要があるか、callbackが共有レコードを書き換えていないかも確認します。条件の分け方は[describe・context・it](/tech-note/articles/rails/rspec/describe-context-it)、example定義を再利用する話は[shared_examples](/tech-note/articles/rails/rspec/shared-examples)へ分けています。定義の共有と、テストデータの共有は別の判断です。
