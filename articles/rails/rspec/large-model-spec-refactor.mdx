model specを開いても、どの入力が必要で、何を確かめているのか分からない。そうなったら、まず例を「入力の検証」「更新可否」「保存後の通知」のような責務ごとに並べ直します。その中で、結果を変える条件を`context`に置きます。ファイルを増やす前に、一つの例を読んで前提と期待が追える形を作るためです。

ここでは、説明用の会員モデルを使い、モデル本体を変えずに同じ6つの契約を並べ替えます。対象はRuby 3.4.4、Active Model 8.1.3、RSpec 3.13.0（core 3.13.6 / expectations 3.13.5 / mocks 3.13.8）です。この固定構成で、掲載コードの整理前6例・整理後6例を実行し、すべて成功しました。

## 何を残し、何をまとめるのでしょうか

最初に、各例について「入力・操作・期待する結果」を書き出します。見た目が似た例でも、境界が違えば残します。今回の対応は次のとおりです。

| 確認する責務 | 入力・条件 | 残す期待 |
| --- | --- | --- |
| 入力の検証 | active、1席 | 有効である |
| 入力の検証 | active、0席 | 席数のエラーになる |
| 入力の検証 | unknown、1席 | 状態のエラーになる |
| 更新可否 | active | 更新対象になる |
| 更新可否 | paused | 更新対象にならない |
| 更新可否 | cancelled | 更新対象にならない |

pausedとcancelledは同じ結果でも、別の状態です。将来一方だけ扱いが変わる可能性があるため、ここでは別の例にします。反対に、入力・操作・期待が完全に同じなら、重複している理由を確認して一つにできます。「どちらもfalseだから」という理由だけで削ると、条件が一つ消えます。

検証対象は次のモデルです。`ActiveModel::Model`で属性の初期化と検証を利用するため、DBは必要ありません。[Active Model 8.1.3の定義](https://github.com/rails/rails/blob/v8.1.3/activemodel/lib/active_model/model.rb)と[検証API](https://api.rubyonrails.org/v8.1.3/classes/ActiveModel/Validations.html)に沿った例です。

```ruby file=lib/model_spec_refactor.rb
require "active_model"

module ModelSpecRefactor
  class Membership
    include ActiveModel::Model

    attr_accessor :status, :seats

    validates :status, inclusion: { in: %w[active paused cancelled] }
    validates :seats, numericality: { only_integer: true, greater_than: 0 }

    def renewal_allowed?
      status == "active"
    end
  end
end
```

`renewal_allowed?`は状態だけを判定します。入力を検証する`valid?`も、課金・保存・通知も呼びません。実際の更新処理全体をこの戻り値だけで許可する実装例ではありません。

## 同じ期待を、責務と条件の順に並べます

整理前のspecでは、入力エラーと更新可否が交互に現れます。小さいうちは追えますが、条件を追加すると、同じ責務の例が離れていきます。次を`spec/model_spec_refactor_spec.rb`に保存します。

```ruby file=spec/model_spec_refactor_spec.rb
require "rspec"
require_relative "../lib/model_spec_refactor"

RSpec.describe ModelSpecRefactor::Membership, "整理前" do
  it "既知の状態と 1 席を受け付ける" do
    membership = described_class.new(status: "active", seats: 1)
    expect(membership).to be_valid
  end

  it "active は更新対象になる" do
    membership = described_class.new(status: "active", seats: 1)
    expect(membership.renewal_allowed?).to be(true)
  end

  it "0 席を受け付けない" do
    membership = described_class.new(status: "active", seats: 0)
    expect(membership).not_to be_valid
    expect(membership.errors.of_kind?(:seats, :greater_than)).to be(true)
  end

  it "paused は更新対象にならない" do
    membership = described_class.new(status: "paused", seats: 1)
    expect(membership.renewal_allowed?).to be(false)
  end

  it "未知の状態を受け付けない" do
    membership = described_class.new(status: "unknown", seats: 1)
    expect(membership).not_to be_valid
    expect(membership.errors.of_kind?(:status, :inclusion)).to be(true)
  end

  it "cancelled は更新対象にならない" do
    membership = described_class.new(status: "cancelled", seats: 1)
    expect(membership.renewal_allowed?).to be(false)
  end
end
```

整理後は`describe`で責務を分け、その内側の`context`で入力の差を示します。比較用として、同じファイルの末尾に次を追加します。実際の整理では、確認が済んだら整理前のgroupを取り除きます。

```ruby file=spec/model_spec_refactor_spec.rb
RSpec.describe ModelSpecRefactor::Membership, "整理後" do
  subject(:membership) { described_class.new(status: status, seats: seats) }

  let(:status) { "active" }
  let(:seats) { 1 }

  describe "入力の検証" do
    it "既知の状態と 1 席を受け付ける" do
      expect(membership).to be_valid
    end

    context "0 席の場合" do
      let(:seats) { 0 }

      it "席数のエラーを返す" do
        expect(membership).not_to be_valid
        expect(membership.errors.of_kind?(:seats, :greater_than)).to be(true)
      end
    end

    context "状態が未知の場合" do
      let(:status) { "unknown" }

      it "状態のエラーを返す" do
        expect(membership).not_to be_valid
        expect(membership.errors.of_kind?(:status, :inclusion)).to be(true)
      end
    end
  end

  describe "#renewal_allowed?" do
    it "active は更新対象になる" do
      expect(membership.renewal_allowed?).to be(true)
    end

    context "paused の場合" do
      let(:status) { "paused" }

      it "更新対象にならない" do
        expect(membership.renewal_allowed?).to be(false)
      end
    end

    context "cancelled の場合" do
      let(:status) { "cancelled" }

      it "更新対象にならない" do
        expect(membership.renewal_allowed?).to be(false)
      end
    end
  end
end
```

`membership`の作り方は一つですが、席数や状態を変える場所は、その条件のすぐ近くにあります。エラーの例は無効になることに加えて、どの属性の検証に失敗するかも確認しています。別の属性が偶然無効だったために通る例を避けるためです。

実行用のRSpecとActive Modelが入った環境で、保存したファイルを指定します。

```sh
bundle exec rspec spec/model_spec_refactor_spec.rb --format documentation
```

この比較用ファイルには、整理前6例・整理後6例の計12例があります。12例はすべて成功しました。ただし、示した6つの契約を保ったことの確認であり、モデルの全入力を網羅したことにはなりません。

## 共通の準備は、どこまで上に置くと読めるでしょうか

`let`は、そのexampleで初めて参照されたときに評価され、同じexample内で値を保持します。別のexampleとは保持した値を共有しません。今回の`subject`もexampleごとにモデルを作るため、ある例で追加されたエラーを次の例の前提にしません。[RSpecのletの仕様](https://rspec.info/features/3-13/rspec-core/helper-methods/let/)

ただし、`let`のブロックが外で作った同じオブジェクトを返していれば、そのオブジェクトまで自動で複製されるわけではありません。また、親に準備を集めるほど、子の例から見えない前提が増えます。入力エラーの検証に不要な関連レコードや外部送信のstubは、その検証の共通準備には置きません。

今回の例では二つの入力だけなので、親に置いても追えます。子の`context`が何段も上の`let`を上書きしないと読めなくなったら、そのgroupの中でモデルを直接作る方が明快なこともあります。準備の行数を減らすこと自体を目的にしません。

## specの整理で済む問題と、本体を見直す問題は違います

入力の検証にメール送信のstubが必要になったり、一覧を作るテストに請求や通知の準備まで必要になったりする場合は、テストの配置だけでは前提を減らせません。モデルがどの処理を呼び出しているかを追い、計算、永続化、外部送信をそれぞれどこで確かめるか決めます。

外部送信を別のオブジェクトに移す場合は、呼び出し元から引数が渡ることと、移した先の処理の検証が必要です。既存の結合テストを消してconstructorへの期待だけに置き換えると、実行される処理を確かめる範囲が狭まります。DBや外部サービスとの境界は[本物とテストダブルの使い分け](/tech-note/articles/rails/rspec/real-vs-mock-boundary/)で扱います。

責務と条件が整理できていても、一つのファイルでは探しづらい場合は[model specを複数ファイルに分ける手順](/tech-note/articles/rails/rspec/split-large-model-spec/)へ進めます。分割後も同じ大きな準備が残るなら、まず、その準備を必要にしている依存関係を見直します。
