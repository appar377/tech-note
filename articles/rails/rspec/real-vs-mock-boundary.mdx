`create!`を呼ぶことを期待したテストが通っても、一意インデックスがあるか、途中の失敗で先のINSERTが戻るかは分かりません。そこを確認したいテストで`create!`や`transaction`を差し替えると、確かめたい処理を取り除いてしまいます。

一方、登録完了の通知が届くところまで毎回つなぐ必要はありません。この稿では、DBの保存と制約を実際に動かし、通知先だけをメモリ上に要求を記録するfakeへ切り離します。関心事は用語の分類ではなく、どの結果をどの境界で確かめるかです。

対象環境はRuby 3.4.4、RSpec 3.13.0、Active Record 8.1.3、pg gem 1.6.3、PostgreSQL 17.10です。通常の6例はローカルで実行し、すべて成功しました。アドレスと表示名は合成データで、実際の通知を送るクライアントは用意しません。

## このテストで本物にするものを決める

例は、複数の購読者をまとめて登録する処理です。一件でもDBへの登録に失敗したら、その呼び出しで追加した行を全部取り消します。DB登録が終わってから、各購読者について通知先へ要求を送ります。

| 確かめたいこと | この例で動かすもの |
| --- | --- |
| 空のaddressを入力エラーにする | 本物のモデルとpresence validation |
| 同じaddressをDBへ二重に入れない | 本物のPostgreSQLとunique index |
| 二件目の失敗で一件目も取り消す | 本物のActive Record transactionとDB |
| 登録後、指定した宛先・表示名で通知を要求する | 通知先を記録用fakeへ置き換える |
| 受信側まで通知が届く | 今回のテストでは確認しない |

以下の例は専用のテストDB向けです。DB接続と次のmigrationの反映を済ませ、example全体を別のトランザクションで囲まない構成で実行します。各exampleでは対象テーブルを空にします。

```ruby
require "rspec"
require "active_record"

class CreateBoundarySubscribers < ActiveRecord::Migration[8.1]
  def change
    create_table :boundary_subscribers do |t|
      t.string :address, null: false
      t.string :display_name, null: false
    end
    add_index :boundary_subscribers, :address, unique: true
  end
end
```

一意性の条件は、保存したaddressの値です。メールアドレスの正規化、形式の検査、大文字小文字の統一はこの例に含めていません。

## 保存処理を動かし、通知だけを切り離す

モデルにはpresence validationを置きます。一意性はDBのインデックスで拒否される経路を確認したいため、ここではuniqueness validationを追加していません。後者を追加しても、それだけでDBの一意制約が作られるわけではない点は[公式Railsガイド](https://guides.rubyonrails.org/active_record_validations.html#uniqueness)にも説明されています。

```ruby
class BoundarySubscriber < ActiveRecord::Base
  self.table_name = "boundary_subscribers"
  validates :address, :display_name, presence: true
end

class RecordingWelcomeGateway
  attr_reader :messages

  def initialize
    @messages = []
  end

  def deliver(address:, display_name:)
    @messages << {address: address, display_name: display_name}
    nil
  end
end

class RegisterBoundarySubscribers
  def initialize(gateway:)
    @gateway = gateway
  end

  def call(entries)
    if BoundarySubscriber.connection.transaction_open?
      raise ArgumentError, "call outside an existing transaction"
    end

    subscribers = BoundarySubscriber.transaction do
      entries.map do |entry|
        BoundarySubscriber.create!(address: entry.fetch(:address), display_name: entry.fetch(:display_name))
      end
    end
    subscribers.each do |subscriber|
      @gateway.deliver(address: subscriber.address, display_name: subscriber.display_name)
    end
    subscribers.map(&:id)
  end
end
```

`RecordingWelcomeGateway`は送信しません。渡された要求を`messages`へ記録するだけです。`RegisterBoundarySubscribers`は保存の成功・失敗をDBへ任せ、通知の実際の配送だけをテストの外へ出しています。

外側のトランザクションを禁止しているのは、この小さな例で`transaction`ブロック終了をcommit境界にするためです。[Active Recordのネストしたtransaction](https://api.rubyonrails.org/v8.1.3/classes/ActiveRecord/Transactions/ClassMethods.html)は、既定では外側に参加する場合があります。外側があるのに直後の通知を「commit後」と呼ばないよう、[transaction_open?](https://api.rubyonrails.org/v8.1.3/classes/ActiveRecord/ConnectionAdapters/DatabaseStatements.html#method-i-transaction_open-3F)で条件を確認しています。

```ruby
RSpec.describe RegisterBoundarySubscribers do
  before { BoundarySubscriber.delete_all }
  let(:gateway) { RecordingWelcomeGateway.new }
  let(:service) { described_class.new(gateway: gateway) }

  it "persists real DB rows and records only the outgoing request in a fake" do
    entries = [
      {address: "first@example.test", display_name: "First"},
      {address: "second@example.test", display_name: "Second"}
    ]
    ids = service.call(entries)
    expect(ids.length).to eq(2)
    expect(BoundarySubscriber.where(id: ids).order(:address).pluck(:address, :display_name)).to eq([
      ["first@example.test", "First"], ["second@example.test", "Second"]
    ])
    expect(gateway.messages).to eq(entries)
  end
end
```

このテストはDBを再問い合わせし、保存した二行の値を見ています。同時にfakeの記録から、通知要求の宛先と表示名を確認します。モデルのメソッドが呼ばれたことだけを見ているわけではありません。ただし、DBに残ったことと通知先へ渡したことまでが範囲で、配送成功は含みません。

## 二件目の重複で、一件目も戻ることをDBで見る

次は、二件目が既存のaddressと重複する例です。入力の一件目は新規なので、実装がトランザクションを外していれば、その行だけ残る可能性があります。

```ruby
RSpec.describe RegisterBoundarySubscribers do
  before { BoundarySubscriber.delete_all }
  let(:gateway) { RecordingWelcomeGateway.new }
  let(:service) { described_class.new(gateway: gateway) }

  it "rolls back an earlier insert on a real database uniqueness failure" do
    existing = BoundarySubscriber.create!(address: "taken@example.test", display_name: "Existing")
    entries = [
      {address: "new@example.test", display_name: "New"},
      {address: "taken@example.test", display_name: "Duplicate"}
    ]
    expect { service.call(entries) }.to raise_error(ActiveRecord::RecordNotUnique)
    expect(BoundarySubscriber.pluck(:id, :address, :display_name)).to eq([
      [existing.id, "taken@example.test", "Existing"]
    ])
    expect(gateway.messages).to eq([])
  end
end
```

期待しているのは、`RecordNotUnique`と、もともとの一行だけが残ることです。通知要求も0件です。[PostgreSQLのunique制約](https://www.postgresql.org/docs/17/ddl-constraints.html#DDL-CONSTRAINTS-UNIQUE-CONSTRAINTS)を実際に通すため、モデルをdoubleにしたテストでは確認できない範囲になります。

例外を検査する位置はtransactionの外です。PostgreSQLではDBエラー後のトランザクションが利用不能になる場合があり、[Active RecordもStatementInvalidをブロック内で握りつぶさないよう説明しています](https://api.rubyonrails.org/v8.1.3/classes/ActiveRecord/Transactions/ClassMethods.html)。ここでは処理全体の巻き戻しを終えてから結果を調べます。

この例は逐次実行による一意制約の確認です。複数接続を競合させる負荷試験や、並行実行時のアプリケーションの再試行までは検証していません。

## 保存前の入力検査と、保存中の失敗は別に確かめる

presence validationだけを調べたいなら、レコードを保存する必要はありません。ただし、Active Recordは属性情報などをDBから読むことがあるので、「INSERTしない」と「DBへ全く接続しない」は同じではありません。

```ruby
RSpec.describe RegisterBoundarySubscribers do
  before { BoundarySubscriber.delete_all }
  let(:gateway) { RecordingWelcomeGateway.new }
  let(:service) { described_class.new(gateway: gateway) }

  it "checks presence validation without inserting a record" do
    subscriber = BoundarySubscriber.new(address: "", display_name: "Example")
    expect(subscriber).not_to be_valid
    expect(subscriber.errors.of_kind?(:address, :blank)).to eq(true)
    expect(BoundarySubscriber.count).to eq(0)
  end

  it "rolls back the batch when a later model validation fails" do
    entries = [
      {address: "valid@example.test", display_name: "Valid"},
      {address: "invalid@example.test", display_name: ""}
    ]
    expect { service.call(entries) }.to raise_error(ActiveRecord::RecordInvalid)
    expect(BoundarySubscriber.count).to eq(0)
    expect(gateway.messages).to eq([])
  end
end
```

最初の例は単体の入力検査、二つ目は入力検査の失敗を含めたバッチ全体のロールバックです。同じvalidationに関係していても、見ている契約が異なります。

逆に、保存まで確認したいのに`create!`をstubすれば、その結果からDB保存を推測できません。次は失敗確認用の別ファイル`expected_failures/stubbed_persistence_spec.rb`へ分けて実行する例です。前のモデル定義とDB接続を読み込みます。この1例を別に実行し、DBの件数が0のため失敗することを確認しました。

```ruby expected-failure
RSpec.describe "intentional persistence boundary failure" do
  before { BoundarySubscriber.delete_all }

  it "cannot infer a stored row from a stubbed create! result" do
    subscriber = BoundarySubscriber.new(id: 101, address: "stub@example.test", display_name: "Stub")
    allow(BoundarySubscriber).to receive(:create!).and_return(subscriber)
    service = RegisterBoundarySubscribers.new(gateway: RecordingWelcomeGateway.new)
    service.call([{address: "stub@example.test", display_name: "Stub"}])
    expect(BoundarySubscriber.count).to eq(1)
  end
end
```

未保存のRubyオブジェクトにidや属性があっても、DBに行があるとは限りません。この例ではcreate!の実処理を飛ばしているため、最後のDB件数の期待を満たせません。保存メソッドを呼ぶこと自体の検証と、保存された状態の検証を分ける理由です。

## 通知の失敗を入れても、commit済みの行は戻らない

依存先を置き換えると、通知側の失敗をテストで指定できます。ここではfakeのdeliverを例外へ差し替えます。

```ruby
RSpec.describe RegisterBoundarySubscribers do
  before { BoundarySubscriber.delete_all }
  let(:gateway) { RecordingWelcomeGateway.new }
  let(:service) { described_class.new(gateway: gateway) }

  it "retains committed rows when the injected delivery fails" do
    allow(gateway).to receive(:deliver).and_raise(IOError, "synthetic delivery failure")
    entry = {address: "saved@example.test", display_name: "Saved"}
    expect { service.call([entry]) }.to raise_error(IOError, "synthetic delivery failure")
    expect(BoundarySubscriber.pluck(:address, :display_name)).to eq([["saved@example.test", "Saved"]])
    expect(gateway).to have_received(:deliver).with(**entry).once
  end

  it "refuses an outer transaction so the block exit is the commit boundary" do
    BoundarySubscriber.transaction do
      expect { service.call([{address: "nested@example.test", display_name: "Nested"}]) }
        .to raise_error(ArgumentError, "call outside an existing transaction")
    end
    expect(BoundarySubscriber.count).to eq(0)
    expect(gateway.messages).to eq([])
  end
end
```

通知が失敗しても、保存済みの行は残ることを期待しています。この結果を「登録と通知が一緒に成功する」とは説明できません。複数宛先の途中で通知が止まるケースや、commit直後にプロセスが停止するケースも、今回の実装では救済しません。

実際に登録後の配送を再試行可能にするなら、登録と配送意図の保存、再試行、重複処理を含む別の設計が必要です。その範囲は[after_commitと外部処理の境界](/tech-note/articles/rails/active_record/after-commit-business-workflow/)で扱います。この稿は、テストでどこを本物にするかを説明するための最小例です。

controllerやroutingを通すrequest spec、実際の通知クライアントがプロトコルに合うかを調べるテストも、ここには含まれません。DBの契約はDBで、外部へ渡す要求は制御できる相手で確認し、残った接続部分を別のテストへ割り当てます。テストダブル自体の選び方は[Stub・Mock・Fakeの使い分け](/tech-note/articles/rails/rspec/stub-mock-fake-by-purpose/)を参照してください。
