実装が違う二つのクラスに、「同じ記事を二度追加しても重複しない」という共通の仕様があるとします。それぞれへ同じexpectationを書く代わりに、その振る舞いに名前を付けて再利用するのが`shared_examples`です。

共有するのはexampleの定義です。テスト対象のインスタンスや、前のexampleで変更した値まで共有する必要はありません。引数で渡す値と、exampleごとに`let`で作る値を分けると、共通化した後も前提を追いやすくなります。

## どの振る舞いを共通にするか

読みたい記事を、追加した順に持つリストを二通りで実装します。一方は配列、もう一方はHashのキーを使います。どちらも`add`で追加し、`titles`で現在の並びを取得するものとします。説明用の短いタイトルだけを使い、文字列自体は変更しません。

以下のRubyブロックを順に一つの`shared_examples_spec.rb`へ置けます。対象はRuby 3.4.4、RSpec 3.13.0（rspec-core 3.13.6）で、掲載した10例はローカルで実行し、すべて成功しました。DBやRailsへの依存はありません。

```ruby
require "rspec/autorun"

class ArrayReadingList
  def initialize(titles)
    @titles = titles.uniq
  end

  def add(title)
    @titles << title unless @titles.include?(title)
    self
  end

  def titles
    @titles.dup
  end
end

class IndexedReadingList
  def initialize(titles)
    @titles = titles.to_h { |title| [title, true] }
  end

  def add(title)
    @titles[title] = true
    self
  end

  def titles
    @titles.keys
  end
end
```

Hashも追加順を保つため、この限定した仕様では同じ結果を返せます。ここでは二つの実装の速度を比較していません。[RubyのHashの順序](https://docs.ruby-lang.org/en/3.4/Hash.html#class-Hash-label-Entry+Order)

## 引数とletを使って、共通のexampleを定義する

共有したいのは「末尾へ追加する」と「二度追加しても一件だけ増える」の二つです。

```ruby
RSpec.shared_examples "読みたい記事を重複せず追加できる" do |new_title|
  let(:reading_list) { described_class.new(initial_titles) }

  it "新しい記事を末尾に追加する" do
    expect(reading_list.titles).to eq(initial_titles)

    reading_list.add(new_title)

    expect(reading_list.titles).to eq(initial_titles + [new_title])
  end

  it "同じ記事を二度追加しても一件だけ増える" do
    expect(reading_list.titles).to eq(initial_titles)

    2.times { reading_list.add(new_title) }

    expect(reading_list.titles).to eq(initial_titles + [new_title])
  end
end
```

この定義だけではテストは実行されません。別のexample groupへ取り込まれたとき、そのグループにexampleが追加されます。[RSpecのshared examples](https://rspec.info/features/3-13/rspec-core/example-groups/shared-examples/)

`new_title`は共有例を取り込むときに渡す引数です。一方、`initial_titles`は取り込み先の`let`から、`reading_list`を作るときに読み取ります。この共有例が呼び出し元に求めるものは、次の三つです。

- `described_class`が`new(initial_titles)`で作れること。
- 作成したオブジェクトが`add`と`titles`を持つこと。
- `let(:initial_titles)`が、追加前の記事一覧を返すこと。

この依存が増えるほど、取り込み先だけを見て内容を理解するのが難しくなります。共有例の名前に加え、必要な入力も小さく保ちます。

## 条件ごとに同じ例を取り込む

空のリストと、すでに記事があるリストの両方で確かめます。クラスを切り替える以外は、同じ共有例を使います。

```ruby
[ArrayReadingList, IndexedReadingList].each do |list_class|
  RSpec.describe list_class do
    context "空のリストの場合" do
      let(:initial_titles) { [] }

      it_behaves_like "読みたい記事を重複せず追加できる", "Ruby".freeze
    end

    context "すでに記事がある場合" do
      let(:initial_titles) { ["Ruby".freeze] }

      it_behaves_like "読みたい記事を重複せず追加できる", "RSpec".freeze
    end

    it "呼び出し元の配列や返した配列の変更で記事が増減しない" do
      initial_titles = ["Ruby".freeze]
      reading_list = described_class.new(initial_titles)

      initial_titles << "Outside"
      reading_list.titles.clear

      expect(reading_list.titles).to eq(["Ruby"])
    end
  end
end
```

`it_behaves_like`は、共有例を入れる子グループを作ります。二つのクラスそれぞれに二つのcontextがあり、共有例の`it`が二つずつ展開されるので、この部分は8例です。最後の配列の分離を調べる例がクラスごとに一つ加わり、合計10例になります。

上のブロックを一つのファイルへまとめた場合は、次のように実行できます。共有定義は使う側より先に置きます。別ファイルへ分ける場合も、先に`require`で読み込む必要があります。RSpecが`spec/support`内を自動ですべて読み込むわけではありません。[共有例の読み込み順](https://rspec.info/features/3-13/rspec-core/example-groups/shared-examples/)

```bash
ruby shared_examples_spec.rb --format documentation
```

引数はexample groupの定義時に渡されます。したがって、example実行時のヘルパーである`let`を、そのまま取り込みの引数として呼び出す書き方はできません。今回のように固定値を引数へ渡し、各exampleで必要なデータは共有例の`let`や`it`の中から参照します。[共有定義を評価する実装](https://github.com/rspec/rspec/blob/rspec-core-v3.13.6/rspec-core/lib/rspec/core/shared_example_group.rb#L33-L40)

## 共有例と、共有された可変オブジェクトは違う

最初のexampleで`reading_list.add`を呼んでも、次のexampleは別のリストを作ります。`let(:reading_list)`のブロックがexampleごとに評価されるからです。各例の冒頭で初期状態も検査しているので、前の追加結果を前提にはしていません。[letのキャッシュ範囲](https://rspec.info/features/3-13/rspec-core/helper-methods/let/)

ただし、`let`が何でも複製してくれるわけではありません。グループの外で一度作ったリストを変数に入れ、`let`からその変数を返せば、各exampleは同じリストを参照します。共有例の引数へ可変の配列を渡して、各exampleで直接変更する場合も同様です。子グループを作ることと、渡されたオブジェクトを複製することは別です。[letをメソッドとして定義する実装](https://github.com/rspec/rspec/blob/rspec-core-v3.13.6/rspec-core/lib/rspec/core/memoized_helpers.rb#L306-L345)

今回の引数は固定の文字列、変更するリストは`let`内の`new`で作っています。また、最後のexampleで、呼び出し元の配列や`titles`が返した配列の変更が、リストの件数へ影響しないことを別に確認しています。この検査は配列の入れ物の分離を対象にしており、すべての要素の深いコピーを保証するものではありません。

DBの行まで共有する`let_it_be`の問題は、[共有状態によるテスト汚染](/tech-note/articles/rails/rspec/let-it-be-shared-state-pollution)で別に扱います。`shared_examples`を使うこと自体が、DBのfixtureを共有する指示になるわけではありません。

## include_examplesとshared_contextはどう違うか

`include_examples`は現在のグループへ共有例を取り込み、`it_behaves_like`は子グループへ取り込みます。同じグループへ複数回`include_examples`したとき、共有例が同じ名前の`let`を定義すると、後の定義が前のものを上書きする可能性があります。今回のように取り込みごとのグループを分けると、その衝突を避けやすくなります。[取り込み先を分ける実装](https://github.com/rspec/rspec/blob/rspec-core-v3.13.6/rspec-core/lib/rspec/core/example_group.rb#L328-L377)

`shared_context`は、主に共通の`let`・hook・ヘルパーをまとめるときに使います。ただし、`shared_examples`には`it`しか書けず、`shared_context`には準備しか書けない、という構文上の制限ではありません。RSpec 3.13.6では両者は同じ共有定義の仕組みを使っています。何を共有する定義なのかを、名前で読み手へ伝える使い分けです。[shared_contextの定義](https://github.com/rspec/rspec/blob/rspec-core-v3.13.6/rspec-core/lib/rspec/core/shared_example_group.rb#L90-L103)

共通化する基準を「3箇所以上」などの回数だけに決める必要はありません。同じ仕様として一緒に変更すべきか、呼び出し元で入力と期待結果を追えるかを確かめます。引数による分岐が増え、対象ごとに違う意味の検査になったなら、個別のexampleへ戻す余地があります。

一つのspec内の名前付けは[describe・context・it](/tech-note/articles/rails/rspec/describe-context-it)、ファイル全体の分割は[大きなspecを分ける基準](/tech-note/articles/rails/rspec/split-large-model-spec)で扱っています。共有例には、今回の「重複せず追加できる」のように、複数の対象へ同じ意味で適用できる振る舞いを残します。
