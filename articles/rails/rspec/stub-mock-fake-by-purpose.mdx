## 概要

Stub、Mock、Fakeの定義を暗記しても、外部APIクライアントやジョブをどれで置き換えるべきか判断できなかった。目的を「値の制御」「相互作用の検証」「動く代替実装」に分けると選びやすくなった。

テストダブルは用語より、何を保証したいかで選ぶ。Stubは入力に対する返り値を制御し、Mockは重要な相互作用を契約として検証し、Fakeは実際に動く軽量実装として振る舞う。

## この記事で学べること

- 用語分類には流派差があることを先に注記
- RSpecの`allow`、`expect(...).to receive`、spy
- Stubで外部レスポンスを固定する
- Mockで重要な通知・保存要求を検証する
- Fake RepositoryやFake Storageの利点
- verifying doubleを使う理由

## 前提知識

- Rails、Active Record、RSpec、SQLログの基本を読めること
- フレームワークのAPIを使った経験があり、状態・トランザクション・非同期処理の境界で詰まり始めていること
- この記事のコード例は匿名化した最小例であり、利用中のバージョンでは公式ドキュメントと実装を確認すること

## 実装コード例

```ruby
class UserNotifier
  def self.call(user)
    UserMailer.welcome(user).deliver_later
  end
end

RSpec.describe UserNotifier do
  it "uses a stub for return values" do
    mailer = instance_double(UserMailer, deliver_later: true)

    allow(UserMailer).to receive(:welcome).and_return(mailer)

    described_class.call(create(:user))

    expect(UserMailer).to have_received(:welcome)
  end
end
```

## 本編

### 発生した状況

Stub、Mock、Fakeの定義を暗記しても、外部APIクライアントやジョブをどれで置き換えるべきか判断できなかった。目的を「値の制御」「相互作用の検証」「動く代替実装」に分けると選びやすくなった。

### 当初の理解・誤解

当初は、API名やメソッド名から直感的に挙動を推測していました。しかし実際には、テストダブルは用語より、何を保証したいかで選ぶ。Stubは入力に対する返り値を制御し、Mockは重要な相互作用を契約として検証し、Fakeは実際に動く軽量実装と... という観点で見る必要がありました。

### 観測したこと

- DioではなくRails側のHTTP clientをstubする例
- `instance_double`と`have_received`
- インメモリFake Repository
- Fakeが本番実装と契約不一致になるテスト

### 修正案の比較

| 方針 | 見るべき点 |
| --- | --- |
| Stub | 簡単／過度に使うと統合不良を見逃す |
| Mock | 相互作用を保証／リファクタリング耐性が下がる |
| Fake | 現実的／実装と保守が増える |

## 内部動作

Railsの抽象化は、Rubyオブジェクト、Active Record、SQL、DBトランザクションの上に成り立っています。重要なのは、Railsのメソッド呼び出しがそのままDBの履歴や外部サービスの状態になるわけではない、という点です。

- Mockの意味はライブラリ/書籍で差がある
- テストダブルは本番契約を自動で保証しない

```text
Ruby object
  -> Active Record
  -> SQL / transaction
  -> database row
  -> callback or job boundary
```

## 調査手順

1. まず、入力値・保存前状態・保存後状態・コールバックや非同期処理の発火地点をログに残します。
2. 次に、DBやHTTP通信など外部境界をまたぐ処理を分けて、どこまでが同じトランザクションや同じライフサイクルに属するかを確認します。
3. 最後に、修正後の設計を最小テストへ落とし込み、同じ誤解が再発しないようにします。

- Mockの意味はライブラリ/書籍で差がある
- テストダブルは本番契約を自動で保証しない

## 再発防止テスト

```ruby
RSpec.describe "stub-mock-fake-by-purpose" do
  it "境界条件を固定する" do
    result = described_class.new.call

    expect(result).to be_present
  end
end
```

## 一般化できる設計原則

- API名が短いほど、裏側の実行モデルを確認する
- 状態を「値」「オブジェクト」「DB row」「外部サービス」のどこに置いているかを分けて考える
- トランザクションや非同期処理の境界をまたぐ副作用は、明示的な設計として扱う
- テストは成功確認だけでなく、誤解しやすい境界条件を固定する

## まとめ

「何を置き換えたか」より「このテストでどの契約を保証したいか」を先に決める。


この記事では、次のような短絡的な一般化は避けます。

- 用語警察のような記事にしない
- すべての依存をMock化しない
