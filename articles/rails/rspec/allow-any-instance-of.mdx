内部で作られるオブジェクトのメソッドを差し替えたいとき、`allow_any_instance_of`は手早く書けます。ただし、対象はその一つのオブジェクトに限られません。同じexampleの中で、別の目的で作ったインスタンスにも設定が効きます。

もう一つ注意したいのが回数です。`allow_any_instance_of(...).to receive(...).twice`と、`expect_any_instance_of(...).to receive(...).twice`を同じ意味で読むことはできません。前者は呼び出しを必須にする期待ではなく、後者もクラス全体の合計回数を数えるものではありません。

対象はRuby 3.4.4、RSpec 3.13.0、rspec-mocks 3.13.8です。通常の9例はローカルで実行し、すべて成功しました。通常のRubyブロックは上から一つのspecに並べられます。「失敗確認用」としたブロックだけは別ファイルへ分けます。

## 作成済みのオブジェクトにも、これから作るものにも効く

表示用のラベルを返すクラスで確認します。`render_calls`は元の`render`が実行されたかを見るための説明用の値です。DBや外部通信はありません。

```ruby
require "rspec"

module AnyInstanceExample
  class LabelFormatter
    attr_reader :prefix, :render_calls

    def initialize(prefix:)
      unless prefix.is_a?(String) && !prefix.empty?
        raise ArgumentError, "prefix is required"
      end
      @prefix = prefix
      @render_calls = 0
    end

    def render(value:)
      @render_calls += 1
      "#{@prefix}:#{value}"
    end
  end

  class LegacyLabels
    def call(prefix:, value:)
      LabelFormatter.new(prefix: prefix).render(value: value)
    end
  end

  class InjectedLabels
    def initialize(formatter:)
      @formatter = formatter
    end

    def call(value:)
      @formatter.render(value: value)
    end
  end
end
```

```ruby
RSpec.describe AnyInstanceExample::LabelFormatter do
  it "affects an existing instance and a later instance but skips the method body" do
    existing = described_class.new(prefix: "before")
    allow_any_instance_of(described_class).to receive(:render).and_return("stubbed")
    later = described_class.new(prefix: "after")
    expect(existing.render(value: "x")).to eq("stubbed")
    expect(later.render(value: "x")).to eq("stubbed")
    expect([existing.prefix, later.prefix]).to eq(%w[before after])
    expect([existing.render_calls, later.render_calls]).to eq([0, 0])
  end
end
```

`existing`は設定前に作り、`later`は設定後に作っています。どちらも`render`の応答は置き換わり、元の本体にあるカウンター更新を通りません。prefixが保存されていることから、インスタンスの初期化まで消えたわけではないと分かります。

[any_instanceの公式説明](https://rspec.info/features/3-13/rspec-mocks/working-with-legacy-code/any-instance/)でも、個別オブジェクトを対象とする通常のAPIに対し、クラスのインスタンス全体へ作用する点が注意されています。この例で必要なのが特定の一つだけなら、対象を直接渡せます。

```ruby
RSpec.describe AnyInstanceExample::LabelFormatter do
  it "can stub one known instance while leaving another real" do
    chosen = described_class.new(prefix: "chosen")
    other = described_class.new(prefix: "other")
    allow(chosen).to receive(:render).and_return("stubbed")
    expect(chosen.render(value: "x")).to eq("stubbed")
    expect(other.render(value: "x")).to eq("other:x")
    expect(other.render_calls).to eq(1)
  end
end
```

`chosen`だけを差し替えたので、`other`は元の処理を実行します。依存先が複数あるテストでは、この違いが失敗を隠さないために役立ちます。

## メソッドのstubは、constructorまで飛ばさない

`render`を差し替えても、`LabelFormatter.new`は本物のままです。不正なprefixを渡せば初期化で例外になります。

```ruby
RSpec.describe AnyInstanceExample::LabelFormatter do
  it "does not skip the real constructor when an instance method is stubbed" do
    allow_any_instance_of(described_class).to receive(:render).and_return("stubbed")
    expect { described_class.new(prefix: nil) }.to raise_error(ArgumentError, "prefix is required")
  end
end
```

一方、`.new`そのものをstubしてdoubleを返すと、元の生成と初期化は実行されません。次の例では、本来拒否するnilが渡されても、テスト側で用意したオブジェクトを返します。

```ruby
RSpec.describe AnyInstanceExample::LabelFormatter do
  it "skips constructor validation if new itself is stubbed" do
    formatter = instance_double(described_class, render: "stubbed")
    allow(described_class).to receive(:new).with(prefix: nil).and_return(formatter)
    result = AnyInstanceExample::LegacyLabels.new.call(prefix: nil, value: "x")
    expect(result).to eq("stubbed")
    expect(formatter).to have_received(:render).with(value: "x").once
  end
end
```

このテストが見るのは、`LegacyLabels`が受け取ったformatterに`render`を送る部分です。constructorが正しい引数で実行できることを確認した結果ではありません。

同じ切り分けはRailsのクエリにも当てはまります。モデルのインスタンスメソッドを置き換えたからといって、呼び出し前の検索が自動で消えるわけではありません。反対に検索を行うscopeやクラスメソッド自体をstubすれば、そのSQLの結果は確認していません。この稿の実行例は純粋なRubyなので、Active Recordのクエリ検証までは含めません。

## twiceはallowとexpectを分けて読む

固定版の挙動を、次のように分けます。

| 設定 | 呼び出し回数の意味 |
| --- | --- |
| `allow_any_instance_of(...).to receive(...).twice` | 0回や1回でも未達の期待にはならない。同じインスタンスの3回目は拒否する |
| `expect_any_instance_of(...).to receive(...).twice` | 一つのインスタンスが2回受け取ることを期待する。別々の2個が1回ずつでは満たせない |

まずallowです。次の二例は、未使用のインスタンスがあってもよいことと、二つのインスタンスがそれぞれ2回呼べることを示します。戻り値を設定していないので応答はnilです。

```ruby
RSpec.describe AnyInstanceExample::LabelFormatter do
  it "does not require two calls when twice is attached to an allowance" do
    allow_any_instance_of(described_class).to receive(:render).twice
    described_class.new(prefix: "unused")
    used_once = described_class.new(prefix: "once")
    expect(used_once.render(value: "x")).to be_nil
  end

  it "allows two calls on each of two instances without a class-wide total" do
    allow_any_instance_of(described_class).to receive(:render).twice
    first = described_class.new(prefix: "a")
    second = described_class.new(prefix: "b")
    2.times { expect(first.render(value: "x")).to be_nil }
    2.times { expect(second.render(value: "x")).to be_nil }
  end
end
```

したがって、allowにtwiceを付けて「各インスタンスを必ず2回呼ぶテスト」と説明するのは不正確です。必要な呼び出しを検証するなら、[message expectationの回数指定](https://rspec.info/features/3-13/rspec-mocks/setting-constraints/receive-counts/)を使います。

```ruby
RSpec.describe AnyInstanceExample::LabelFormatter do
  it "satisfies an any-instance expectation using the same receiver twice" do
    expect_any_instance_of(described_class).to receive(:render).twice.and_return("stubbed")
    formatter = described_class.new(prefix: "a")
    expect(formatter.render(value: "x")).to eq("stubbed")
    expect(formatter.render(value: "x")).to eq("stubbed")
  end
end
```

このexpectationを満たすのは、同じformatterへの2回の呼び出しです。別のインスタンスを作ること自体は禁止しませんが、その別インスタンスへの同じメソッド呼び出しを合計へ足すことはできません。

なお、複数の戻り値を並べる設定も、各インスタンスで別々に進みます。

```ruby
RSpec.describe AnyInstanceExample::LabelFormatter do
  it "uses an independent return sequence for each instance" do
    allow_any_instance_of(described_class).to receive(:render).and_return("first", "next")
    first = described_class.new(prefix: "a")
    second = described_class.new(prefix: "b")
    expect([first.render(value: "x"), first.render(value: "x")]).to eq(%w[first next])
    expect(second.render(value: "x")).to eq("first")
  end
end
```

一つ目で二番目の応答まで進めても、二つ目は最初の応答から始まります。戻り値の列をクラス全体で共有する設定でもありません。

## 誤った回数の読み方を、失敗するspecで確かめる

次は失敗確認用です。通常のspecへ混ぜず、クラス定義を読み込む別ファイル`expected_failures/any_instance_counts_spec.rb`で実行します。3例を別に実行し、それぞれ以下の理由で失敗することを確認しました。

```ruby expected-failure
RSpec.describe "intentional any-instance count failures" do
  it "cannot combine one call on each of two receivers to satisfy twice" do
    expect_any_instance_of(AnyInstanceExample::LabelFormatter).to receive(:render).twice
    first = AnyInstanceExample::LabelFormatter.new(prefix: "a")
    second = AnyInstanceExample::LabelFormatter.new(prefix: "b")
    first.render(value: "x")
    second.render(value: "x")
  end

  it "fails an any-instance expectation when no instance receives the message" do
    expect_any_instance_of(AnyInstanceExample::LabelFormatter).to receive(:render).twice
    AnyInstanceExample::LabelFormatter.new(prefix: "unused")
  end

  it "rejects a third call to one instance under an allowance with twice" do
    allow_any_instance_of(AnyInstanceExample::LabelFormatter).to receive(:render).twice
    formatter = AnyInstanceExample::LabelFormatter.new(prefix: "a")
    3.times { formatter.render(value: "x") }
  end
end
```

最初は別のreceiverが同じメソッドを受け取るため、二つ目は期待した呼び出しがないため、三つ目は同じreceiverで上限を超えるための失敗です。具体的なobject IDやエラーメッセージ全文を固定する必要はありません。どの契約を破ったのかを確かめます。

## 一つの依存オブジェクトを渡せるなら、対象も明確になる

`InjectedLabels`にはformatterを引数で渡せます。そのオブジェクトに期待を置けば、他のインスタンスへ設定を広げずに済みます。

```ruby
RSpec.describe AnyInstanceExample::LabelFormatter do
  it "injects one collaborator and checks that receiver's call" do
    formatter = instance_double(described_class)
    expect(formatter).to receive(:render).with(value: "x").once.and_return("checked")
    service = AnyInstanceExample::InjectedLabels.new(formatter: formatter)
    expect(service.call(value: "x")).to eq("checked")
  end
end
```

この場合も、doubleを使ったテストがformatterの初期化や実装まで検証するわけではありません。組み立てる部分とformatter自身のテストは別に残します。どのオブジェクトとのやり取りを見ているかを、テストから読めるようにした変更です。

RSpecのstubと期待には[example単位のライフサイクル](https://rspec.info/features/3-13/rspec-mocks/basics/scope/)があり、終了後に解除されます。設定はexample内か`before(:example)`へ置き、doubleを別exampleへ使い回しません。

既存コードへ一時的にテストを足すときにany_instanceを使う余地はあります。使う場合は、置き換えたメソッド、影響するインスタンス、実行されない処理を説明できる範囲にとどめます。DBの保存や制約まで確認したいときの境界は、[実DBとテストダブルの使い分け](/tech-note/articles/rails/rspec/real-vs-mock-boundary/)で扱います。
