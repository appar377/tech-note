`context "正常系"`の中に`it "成功する"`とだけ書かれていると、何を準備し、何が成功すればよいのかをコードまで読まないと分かりません。`describe`には対象、`context`には条件、`it`には期待する結果を書くと、失敗したexampleを探しやすくなります。

ただし、この分け方は読み手へ意図を伝えるための慣習です。`describe`と`context`は、どちらもexample groupを作ります。`context`に条件を書くだけで、その状態のデータが用意されるわけではありません。[RSpecの基本構造](https://rspec.info/features/3-13/rspec-core/example-groups/basic-structure/)

## 一つの判定を、条件と結果に分ける

説明用に「確認済みで、退会していないアカウントだけ有効」と判定するクラスを使います。入力は`true`か`false`に限定します。RailsやDB、FactoryBotを使わない純Rubyの例です。

以下のRubyブロックを順に一つの`naming_spec.rb`へ置けます。対象環境はRuby 3.4.4、RSpec 3.13.0（rspec-core 3.13.6）で、掲載した6例はローカルで実行し、すべて成功しました。`rspec/autorun`はRubyからexampleを実行するための読み込みです。[RubyコマンドでRSpecを実行する](https://rspec.info/features/3-13/rspec-core/command-line/ruby/)

```ruby
require "rspec/autorun"

class NamingAccount
  def initialize(confirmed:, deleted:)
    @confirmed = confirmed
    @deleted = deleted
  end

  def active?
    @confirmed && !@deleted
  end
end
```

このクラスに対して、判定が変わる条件を並べます。

```ruby
RSpec.describe NamingAccount do
  subject(:account) { described_class.new(confirmed: confirmed, deleted: deleted) }

  let(:confirmed) { true }
  let(:deleted) { false }

  describe "#active?" do
    context "確認済みで退会していない場合" do
      it "有効と判定する" do
        expect(account.active?).to be(true)
      end
    end

    context "未確認の場合" do
      let(:confirmed) { false }

      it "無効と判定する" do
        expect(account.active?).to be(false)
      end
    end

    context "退会済みの場合" do
      let(:deleted) { true }

      it "確認済みでも無効と判定する" do
        expect(account.active?).to be(false)
      end
    end

    context "未確認かつ退会済みの場合" do
      let(:confirmed) { false }
      let(:deleted) { true }

      it "無効と判定する" do
        expect(account.active?).to be(false)
      end
    end
  end
end
```

外側の`RSpec.describe NamingAccount`がクラス、`describe "#active?"`がメソッドを表します。`#`をインスタンスメソッド、`.`をクラスメソッドの名前に使うのは記述上の慣習です。この文字列で対象メソッドが自動実行されることはありません。実行しているのは`it`内の`account.active?`です。

`context`と`it`をつなげると、「退会済みの場合、確認済みでも無効と判定する」と読めます。条件は`let(:deleted) { true }`で作り、期待する結果は`expect(account.active?).to be(false)`で検査しています。名前だけでなく、準備と検査がその説明に対応していることが必要です。

## contextを書けば、状態も変わるのか

次は、名前と入力が一致しない場合を意図的に作る比較です。通常のspecでこの名前付けを勧める例ではありません。どちらのグループでも、入力は`confirmed: false`のままです。

```ruby
RSpec.describe NamingAccount, "グループ名と実際の入力を分ける例" do
  let(:account) { described_class.new(confirmed: false, deleted: false) }

  describe "確認済みという名前だけを付けた場合" do
    it "未確認の入力は変わらず無効と判定する" do
      expect(account.active?).to be(false)
    end
  end

  context "確認済みという名前だけを付けた場合" do
    it "未確認の入力は変わらず無効と判定する" do
      expect(account.active?).to be(false)
    end
  end
end
```

`describe`を`context`へ変えても、メソッドへ渡す値は変わりません。RSpec 3.13.6の実装でも、両方が同じ`define_example_group_method`から定義されています。[example groupを作る実装](https://github.com/rspec/rspec/blob/rspec-core-v3.13.6/rspec-core/lib/rspec/core/example_group.rb#L246-L291)

なお、ここで扱っているのはグループ名とDSLの使い分けです。`:focus`や独自のmetadataに応じたfilter・hookを設定していれば、選ばれるテストや準備処理が変わる場合があります。タグや設定の効果まで「名前は影響しない」とまとめないようにします。[RSpecのmetadata](https://rspec.info/features/3-13/rspec-core/metadata/user-defined/)

## 共通の準備と、条件ごとの差分をどこへ置くか

最初の例では、`confirmed: true`と`deleted: false`を外側の初期条件にしています。各`context`は、結果を変える値だけを上書きします。`subject(:account)`はその条件で`NamingAccount`を作る、名前付きのヘルパーです。

`let`は最初に参照されたときに評価され、値は同じexampleの中で再利用されます。別のexampleまでその評価結果を持ち越す仕組みではありません。そのため、この例では条件ごとに新しいアカウントを作れます。[letの評価とキャッシュ範囲](https://rspec.info/features/3-13/rspec-core/helper-methods/let/)

ただし、準備を何段も外側へ追わないと値が分からないなら、共通化を減らした方が読みやすい場合があります。短いexampleで一度しか使わない値なら、`it`の中に直接書いても構いません。`let`や`subject`の数を増やすことが目的ではありません。

生成タイミングを詳しく比べるときは、[let・let!・let_it_beの使い分け](/tech-note/articles/rails/rspec/let-let-bang-let-it-be)で扱う範囲です。ここでは、条件の差がその場で読める配置に絞っています。

## 失敗したとき、どの条件か分かる名前にする

`it "falseを返す"`でも検査内容は書けます。この例では、その値が何を意味するかを残すため「無効と判定する」としています。どちらの書き方でも、名前とexpectationがずれていれば修正が必要です。

`--format documentation`を付けるとグループとexampleの名前を階層で確認できます。上のRubyブロックを一つのファイルへまとめた場合の実行コマンドです。[RSpecの出力形式](https://rspec.info/features/3-13/rspec-core/command-line/format-option/)

```bash
ruby naming_spec.rb --format documentation
```

確認したいのは、たとえば「NamingAccount → #active? → 未確認の場合 → 無効と判定する」というつながりです。「正常系」「異常系」だけで区切るより、入力の違いと結果の対応が見えます。

ネストの深さは、決まった段数よりも前提を追えるかで判断します。条件を増やすたびに一段ずつ深くする必要はありません。今回の「未確認かつ退会済み」のように、同時に扱う条件を一つのcontextへまとめる方法もあります。

同じ振る舞いを複数の対象で検査するなら[shared_examples](/tech-note/articles/rails/rspec/shared-examples)、一つのspec全体が大きくなったなら[ファイルを分ける基準](/tech-note/articles/rails/rspec/split-large-model-spec)を考えます。名前付けだけで、共有状態や責務の混在まで解消しようとしないことが大切です。
