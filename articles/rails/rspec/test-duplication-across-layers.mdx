モデルで「メールアドレスは必須」と確認していても、APIが空の入力を422へ変換し、保存しないことまでは分かりません。逆に、そのHTTP応答だけを確認しても、`nil`や空白、長さの境界をすべて確かめたことにはなりません。

同じ空文字を使う2つのテストを残すかは、入力の重なりだけでは決められません。モデルには値を受け入れる条件を、request specには外から見える応答と保存結果を担当させると、重ねる理由がはっきりします。

## 必須条件とHTTP応答は、どこでつながりますか

説明用の登録APIを用意します。モデルの条件は「空でないこと」と「最大80文字」の2つです。メールの構文、ドメイン、実際の到達性を検証する例ではありません。controllerは失敗した保存のerror typeをJSONへ変換します。

```ruby
class LayerSignup < ActiveRecord::Base
  self.table_name = "layer_signups"

  validates :email, presence: true, length: { maximum: 80 }
end

class LayerSignupsController < ActionController::Base
  before_action :identify_example_writer

  def create
    signup = LayerSignup.new(params.require(:signup).permit(:email))

    if signup.save
      render json: { id: signup.id, email: signup.email }, status: 201
    else
      codes = signup.errors.details.transform_values do |details|
        details.map { |detail| detail.fetch(:error).to_s }
      end
      render json: { errors: codes }, status: 422
    end
  end

  private

  def identify_example_writer
    return if request.headers["X-Example-Identity"] == "alpha"

    render json: { error: "unauthorized" }, status: 401
  end
end
```

`presence`は`blank?`で判定し、`nil`、空文字、空白だけの文字列を必須違反にします。`maximum: 80`は80文字を許可し、超えた値を拒否する条件です。[Railsのpresence・length validation](https://api.rubyonrails.org/v8.1.3/classes/ActiveModel/Validations/HelperMethods.html)

通常の`save`はvalidationが失敗すると`false`を返すので、controllerは失敗側へ進みます。`errors.details`からは属性ごとのerror typeを取り出せます。この例では`blank`を公開用の文字列へ変換していますが、実APIで内部のerror typeをそのまま公開契約にするかは別に決める必要があります。[Active Recordのvalidation](https://api.rubyonrails.org/v8.1.3/classes/ActiveRecord/Validations.html#method-i-save)、[Active Modelのerrors.details](https://api.rubyonrails.org/v8.1.3/classes/ActiveModel/Errors.html#method-i-details)

前提はRuby 3.4.4、Rails 8.1.3、RSpec 3.13.0、RSpec Rails 8.0.4です。専用テストDBに`layer_signups`テーブルを用意し、主キー`id`と`email:string, null: false`を持たせます。`POST /layer_signups`は`layer_signups#create`へ割り当て、test環境のRailsアプリとRSpec Railsのhelperを読み込んでから実行します。

`X-Example-Identity`は説明用の固定値判定で、本物の認証ではありません。このheaderだけで利用者を認証する設計はできません。例はCSRF保護を組み込んでおらず、認証機構やCSRFの正しさを保証しません。

最初のRubyブロックはアプリが一度読み込むモデルとcontrollerの定義です。以降のmodel specとrequest specは、そのアプリをhelperで読み込むspecファイルへ保存します。同じモデル定義を再評価するとvalidationが重複するため、定義はspec内に重ねません。各DBテストは専用テーブルを初期化します。この固定構成で通常8例を実行し、すべて成功しました。別枠の意図的な失敗1例も、後述する422と201の食い違いを確認しています。

## 細かい入力条件は、どこで一覧にしますか

モデルでは、HTTPステータスを使わずに必須違反と長さ違反を区別します。

```ruby
RSpec.describe LayerSignup, type: :model do
  before { described_class.delete_all }

  [nil, "", "   "].each do |email|
    it "#{email.inspect}を必須違反として扱う" do
      signup = described_class.new(email: email)

      expect(signup).not_to be_valid
      expect(signup.errors.details.fetch(:email)).to include(error: :blank)
    end
  end

  it "上限の80文字を受け入れる" do
    signup = described_class.new(email: "a" * 67 + "@example.test")

    expect(signup).to be_valid
  end

  it "81文字を長さ違反として扱う" do
    signup = described_class.new(email: "a" * 68 + "@example.test")

    expect(signup).not_to be_valid
    expect(signup.errors.details.fetch(:email)).to include(error: :too_long, count: 80)
  end
end
```

`be_valid`でvalidationを実行し、`errors.details`で拒否した理由を見ます。ここにはルーティングやJSONの項目名を持ち込みません。「81文字を許す実装へ変わった」という回帰は、モデルの境界例で検知できます。

この例では文字列型の属性を使っています。整数などの入力をどう型変換するか、Unicodeの長さをどの単位で数えるかまで網羅する仕様ではありません。実際の入力仕様に必要なら、条件を追加して別の観測点を用意します。

## API側では、何を重ねれば十分ですか

空文字を代表の失敗入力にします。ここでの問いは「空文字が無効か」だけではなく、「リクエストを受け取ったアプリが、保存せず、422と決めたJSONを返すか」です。

```ruby
RSpec.describe "POST /layer_signups", type: :request do
  before { LayerSignup.delete_all }

  let(:headers) { { "X-Example-Identity" => "alpha" } }

  it "空のemailを422と公開用error codeへ変換し行を増やさない" do
    expect do
      post "/layer_signups", params: { signup: { email: "" } }, headers: headers, as: :json
    end.not_to change(LayerSignup, :count)

    expect(response).to have_http_status(422)
    expect(response.media_type).to eq("application/json")
    expect(JSON.parse(response.body)).to eq("errors" => { "email" => ["blank"] })
  end

  it "受け取ったemailを保存して201と保存値を返す" do
    expect do
      post "/layer_signups", params: { signup: { email: "reader@example.test" } }, headers: headers, as: :json
    end.to change(LayerSignup, :count).by(1)

    signup = LayerSignup.order(:id).last
    expect(signup.email).to eq("reader@example.test")
    expect(response).to have_http_status(201)
    expect(JSON.parse(response.body)).to eq("id" => signup.id, "email" => signup.email)
  end

  it "識別headerなしでは有効な入力でも保存しない" do
    expect do
      post "/layer_signups", params: { signup: { email: "reader@example.test" } }, as: :json
    end.not_to change(LayerSignup, :count)

    expect(response).to have_http_status(401)
    expect(JSON.parse(response.body)).to eq("error" => "unauthorized")
  end
end
```

空文字を使う点はモデルの例と同じです。ただし、controllerが`save`の失敗を無視して201を返したり、入力の項目名を取り違えたりすれば、request specの期待値は崩れます。正常系では、件数だけでなく実際に保存したemailと、応答のid・emailを照合しています。

さらに、入力が有効でも識別headerがなければ401になり、行が増えないことを別に確認します。本物の認証・認可を持つアプリなら、ログイン状態、権限、対象レコードの所有者など、モデル単体に届く前の条件を実際の仕組みで確かめます。request specが通す経路は[request specとcontroller specの違い](/tech-note/articles/rails/rspec/request-spec-vs-controller-spec)で扱います。

`as: :json`は入力をJSONとして符号化して対応するheaderを設定する指定です。単にRubyのHashをcontrollerへ直接渡す場合とは、入力の変換も含めた確認範囲が異なります。[Railsのintegration request API](https://api.rubyonrails.org/v8.1.3/classes/ActionDispatch/Integration/Session.html#method-i-process)

## 保存結果をstubしたら、どの確認が消えますか

次の例では、`LayerSignup.new`が実モデルの代わりにdoubleを返し、`save`は必ず成功したことにします。空のemailを送っても本物のvalidationは実行されないため、422という本来の契約を確認すると失敗する想定です。通常のテストから外し、`LAYER_CONTRACT_EXPECT_FAILURE=1`を明示したときだけ有効にします。

```ruby expected-failure
if ENV["LAYER_CONTRACT_EXPECT_FAILURE"] == "1"
  RSpec.describe "保存成功のstubで必須検証を切り離した例", type: :request do
    before { LayerSignup.delete_all }

    it "空のemailを拒否するという本来の契約を確認できない" do
      signup = instance_double(LayerSignup, save: true, id: 123, email: "")
      allow(LayerSignup).to receive(:new).and_return(signup)

      post "/layer_signups", params: { signup: { email: "" } },
        headers: { "X-Example-Identity" => "alpha" }, as: :json

      expect(response).to have_http_status(422) # 期待する失敗: stubにより実際は201
    end
  end
end
```

期待する失敗は「422を期待したが201だった」です。読み込みエラーやDB接続エラーは、この再現に成功したことにはなりません。このテストの期待値を201へ変えれば、固定した成功分岐に合うだけで、emailの必須条件を確認できません。

`instance_double`は、存在するメソッドや引数の形とstubが合うかを検証します。返り値の`true`が実際の入力条件に照らして正しいかまでは保証しません。[RSpecのverifying double](https://rspec.info/features/3-13/rspec-mocks/verifying-doubles/instance-doubles/)

controllerの失敗応答だけを局所的に調べたい場合など、stubで切り分ける目的はあります。その場合は、実モデルとつながったrequest specを別に残すかを判断します。内部メソッドを一つずつmockし、実装の呼び出し順だけを期待すると、外から見える振る舞いを保ったリファクタリングにも追従が必要になりがちです。

## どのテストを減らし、どれを残しますか

この例での分担は次のようになります。テストピラミッドは比率を決める規則としてではなく、どの欠陥をどの範囲の準備と実行で見つけるかを考える目安として使います。

| 変化・失敗 | 主に残す場所 | 観測するもの |
| --- | --- | --- |
| 必須条件や最大長が変わる | model spec | 有効性、error type、境界値 |
| 入力の受け取り方や失敗応答が壊れる | request spec | 422、JSON、行が増えないこと |
| 正常に受け取った値を別の値として保存する | request spec | DBの保存値と201の応答 |
| 未認証や権限不足でも処理できる | 実認証を通すrequest spec | 拒否応答、副作用がないこと |
| 画面の送信操作からAPIへつながらない | 必要なsystem spec | 利用者の操作と画面結果 |

削除候補を見るときは、各例について「どの変更で落ちるか」「外から意味のある結果を観測しているか」「同じ欠陥を別の例が拾えるか」を確認します。重要な購入や権限変更などでは、下位の細条件と上位の代表フローを意図して重ねる判断もあります。

この登録例は単一行の保存です。複数モデルをまとめて更新する機能なら、途中の失敗で一部だけ残らないかも機能境界のテストへ加えます。外部送信までDBと一緒に戻るとは限らないため、その場合は[DBと外部ストレージの境界](/tech-note/articles/rails/data/db-s3-transaction-boundary)を分けて設計します。

実行時間の改善量や適切なテスト数は、ここでは測定していません。まず削除前後で検知できる失敗を比べ、setupや実行時間に問題がある場合に計測して絞り込みます。
