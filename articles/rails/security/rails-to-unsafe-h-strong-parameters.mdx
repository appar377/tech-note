検索条件をHashへ変換するとき、`to_unsafe_h`を`permit(...).to_h`へ置き換えれば、必要な対策は済むでしょうか。`permit`で選べるのは受け付けるキーと値の形です。ページ番号として妥当か、その利用者が見てよいレコードかは、別に判断します。

まず、変換する前のオブジェクトを確認します。Rails 8.1.3では、`request.query_parameters`はHash系の値で、`to_unsafe_h`を持ちません。コントローラの`params`が`ActionController::Parameters`です。以下はRuby 3.4.4、Action Pack・Active Record 8.1.3、PostgreSQL 17.10で確かめる説明用の例です。

## query_parametersとparamsを区別する

GETのクエリ文字列を読み取るだけなら、次の型になります。`query_parameters`は[`ActionDispatch::Request#GET`](https://api.rubyonrails.org/v8.1.3/classes/ActionDispatch/Request.html#method-i-GET)の別名です。

```ruby
request = ActionDispatch::Request.new(Rack::MockRequest.env_for('/?q=sample'))
request.query_parameters.class.name # => "ActiveSupport::HashWithIndifferentAccess"
request.query_parameters.respond_to?(:to_unsafe_h) # => false

input = ActionController::Parameters.new(request.query_parameters)
input.permitted? # => false
```

最後の行では、比較のため明示的にParametersへ包んでいます。コントローラの`params`にはクエリだけでなく、ルーティングやリクエストボディ由来の値も含まれます。GETかPOSTかという区別で入力を信頼せず、受け付ける項目を処理ごとに選びます。[Railsのパラメータの説明](https://guides.rubyonrails.org/action_controller_overview.html#parameters)

## to_unsafe_hは、許可済みの印を付ける操作ではない

ParametersをActive Recordの属性一括代入へ渡す場合、許可状態が検査されます。次の`SearchItem`は、後の検索例で使うモデルです。専用のテストDBに`search_items`を作り、`account_id:bigint`、`name:string`、`status:string`をすべて`NOT NULL`で用意します。

```ruby
class SearchItem < ActiveRecord::Base
end

input = ActionController::Parameters.new(name: 'Sample', account_id: 2)

begin
  SearchItem.new(input)
rescue ActiveModel::ForbiddenAttributesError => error
  error.class.name # => "ActiveModel::ForbiddenAttributesError"
end

allowed = input.permit(:name)
allowed.to_h # => {"name" => "Sample"}
allowed.permitted? # => true
input.permitted? # => false

SearchItem.new(input.to_unsafe_h).account_id # => 2
input.permitted? # => false
```

`permit`は指定したキーを取り出した別のParametersを返します。`to_h`は未許可のParametersなら例外になります。一方、`to_unsafe_h`は許可リストで絞らずHashへ変換します。元の`input`を許可済みにするのではなく、変換後のHashに許可状態の検査がなくなる点に注意します。[ParametersのAPIと変換処理](https://api.rubyonrails.org/v8.1.3/classes/ActionController/Parameters.html)

この例の`new`はDBへ保存していません。示しているのは、入力側にあった`account_id`が属性へ渡ることです。どの属性が変更可能かは、その処理の用途から決めます。

## 検索ではキー・値・レコードの範囲を分ける

`permit(:page)`は、文字列`"2x"`を整数2へ変換しません。また、`account_id`というキーを許可しても、そのアカウントを閲覧する権限が得られるわけではありません。

| 判断すること | この例で置く場所 |
| --- | --- |
| どのレコードを検索してよいか | 認証済みアカウントから作るRelation |
| どのキーを受け付けるか | `permit(:status, :sort, :page)` |
| 値が使える形・範囲か | 文字列、状態の候補、ページ番号の検証 |
| どの列で並べるか | 固定した名前とorder Hashの対応表 |

次のQuery Objectは、検索対象のRelationを外から受け取ります。状態は`active`か`draft`、ページは1〜1,000に限定します。1ページ2件は、小さい合成データで結果を確認するための設定です。

```ruby
class CatalogQuery
  class InvalidInput < StandardError; end
  SORTS = {
    'name_asc' => { name: :asc, id: :asc },
    'name_desc' => { name: :desc, id: :desc }
  }.freeze
  PAGE_SIZE = 2

  def initialize(scope:)
    @scope = scope
  end

  def call(params)
    %w[status sort page].each do |key|
      if params.key?(key) && !params[key].is_a?(String)
        raise InvalidInput, 'search values must be strings'
      end
    end
    options = params.permit(:status, :sort, :page).to_h
    status = options.fetch('status', 'active')
    sort = options.fetch('sort', 'name_asc')
    page_text = options.fetch('page', '1')
    raise InvalidInput, 'invalid status' unless %w[active draft].include?(status)
    raise InvalidInput, 'invalid sort' unless SORTS.key?(sort)
    unless /\A[1-9][0-9]{0,3}\z/.match?(page_text) && page_text.to_i <= 1000
      raise InvalidInput, 'invalid page'
    end

    @scope.where(status: status).reorder(SORTS.fetch(sort))
      .limit(PAGE_SIZE).offset((page_text.to_i - 1) * PAGE_SIZE)
  end
end
```

値が配列やHashで来たときは、`permit`に落とされて初期値へ戻る前に拒否します。この検索の入力は文字列に限定する方針です。JSON APIなどで数値も受け付けるなら、受け付ける型と変換を別に設計します。

並び順はユーザーの文字列をSQLへ埋め込まず、定義したHashから選びます。`reorder`は既存の並び順を置き換えます。`id`も指定することで、同名の行の順番を決めています。[Railsのorder・reorder](https://api.rubyonrails.org/v8.1.3/classes/ActiveRecord/QueryMethods.html#method-i-reorder)

ここで`where(status: status)`のようなHash条件と、SQL文字列の直接補間は区別します。`where(params.to_unsafe_h)`を一律に「SQLインジェクション」と呼ぶのは不正確です。Hashの値はRailsが扱いますが、想定しない検索キーや対象範囲を渡す問題は残ります。[RailsのSQLインジェクション対策](https://guides.rubyonrails.org/security.html#sql-injection)

Ransackのような検索ライブラリを使う場合も、そのライブラリの許可属性・関連の設定が別に必要です。この例ではRansackを導入しておらず、その設定やSQL生成は検証対象に含めません。

## 不許可のキーと不正な値をリクエストで確かめる

次は、ネットワークを使わずRack経由で呼ぶテスト用コントローラです。`fixture.account_id`はテスト側が置く認証済みアカウントの代わりで、クエリ文字列から取得しません。実アプリでは認証済みユーザーやポリシーから同じ役割のRelationを作ります。

```ruby
class ParameterReviewController < ActionController::API
  def index
    # The fixture adapter supplies an authenticated account ID, never a query value.
    scope = SearchItem.where(account_id: request.env.fetch('fixture.account_id'))
    items = CatalogQuery.new(scope: scope).call(params)
    render json: items.pluck(:name)
  rescue CatalogQuery::InvalidInput
    render json: { error: 'invalid search' }, status: :bad_request
  end
end

PARAMETER_REVIEW_ROUTES = ActionDispatch::Routing::RouteSet.new
PARAMETER_REVIEW_ROUTES.draw do
  get '/search', to: 'parameter_review#index'
end
```

次の例は、上のクラスとルート、RSpecを読み込んだテストDBで実行します。

```ruby
RSpec.describe 'account-scoped search' do
  before do
    SearchItem.delete_all
    SearchItem.create!(account_id: 1, name: 'Visible', status: 'active')
    SearchItem.create!(account_id: 2, name: 'Other account', status: 'active')
  end

  it '別アカウントの指定を検索範囲に採用しない' do
    response = Rack::MockRequest.new(PARAMETER_REVIEW_ROUTES)
      .get('/search?account_id=2', 'fixture.account_id' => 1)
    expect(response.status).to eq(200)
    expect(JSON.parse(response.body)).to eq(['Visible'])
  end

  it '不正なページを400として返す' do
    response = Rack::MockRequest.new(PARAMETER_REVIEW_ROUTES)
      .get('/search?page=2x', 'fixture.account_id' => 1)
    expect(response.status).to eq(400)
    expect(JSON.parse(response.body)).to eq('error' => 'invalid search')
  end
end
```

この例では未知のキーは検索に使わず、既知のキーの不正な値は400にします。`permit`自体が常に400を返すわけではありません。`action_on_unpermitted_parameters`を`:raise`にする設定もありますが、全体設定をリクエスト途中で変更するのは避けます。設定差で例外が起こるプロジェクトでは、その応答方針も合わせて確認します。[Parametersの設定](https://api.rubyonrails.org/v8.1.3/classes/ActionController/Parameters.html)

認証機構そのものや実サービスのポリシーは、このローカルテストの対象外です。確認しているのは、信頼できる範囲を受け取った後にクエリ入力で範囲を広げないことです。

## ネストした入力とログには、別の指定が必要

Rails 8.1.3の`expect`なら、ルートの必須項目と許可する形を一緒に指定できます。次は`profile`の中の名前と、文字列などの許可されたスカラーの配列を受け付ける例です。配列の要素が業務上使えるラベルかどうかまでは、この宣言では決まりません。

```ruby
profile = ActionController::Parameters.new(
  profile: { name: 'Sample', labels: ['ruby'], admin: true }
)
profile.expect(profile: [:name, { labels: [] }]).to_h
# => {"name" => "Sample", "labels" => ["ruby"]}
```

`profile`に文字列を渡すなど形が違えば、この指定では`ActionController::ParameterMissing`になります。古いRailsで`require(...).permit(...)`を使う場合も、利用バージョンのAPIと不正な形の入力を確認します。[expectの形の検査](https://api.rubyonrails.org/v8.1.3/classes/ActionController/Parameters.html#method-i-expect)

最後に、入力の許可とログの伏せ字は別です。次はログ用のフィルタだけを確認する例です。

```ruby
filter = ActiveSupport::ParameterFilter.new([:token])
filter.filter('q' => 'sample', 'token' => 'fixture-only')
# => {"q" => "sample", "token" => "[FILTERED]"}
```

実アプリでは`config.filter_parameters`に伏せる項目を指定します。独自に`params.to_unsafe_h.inspect`をログへ出す処理にまで、フィルタが自動適用されるとは限りません。検索語にも個人情報が入り得るため、必要な項目だけ記録します。[Railsのパラメータのログフィルタ](https://guides.rubyonrails.org/action_controller_advanced_topics.html#parameters-filtering)
