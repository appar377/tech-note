画面を閉じた後のHTTPレスポンスを使わないなら、通信を始めた側が終了条件も決める必要があります。`mounted`の確認は破棄済みのWidgetを更新しないための処理です。Dioのリクエストを中止するには、要求に渡した`CancelToken`をキャンセルします。

以下はFlutter 3.41.9、Dart SDK 3.11.5、Dio 5.9.2、flutter_riverpod 3.3.2で確認した説明用の例です。実在するユーザー情報やAPIは使っていません。

## 一度だけ読み込む画面では、Stateがトークンを持つ

この画面は表示時に一度だけ`/users/me`を取得します。外から受け取る`Dio`は画面の存続中に入れ替えない前提です。トークンはStateごとに作り、`dispose`で中止します。

```dart
import 'package:dio/dio.dart';
import 'package:flutter/material.dart';

class UserPage extends StatefulWidget {
  const UserPage({super.key, required this.dio});
  final Dio dio;

  @override
  State<UserPage> createState() => _UserPageState();
}

class _UserPageState extends State<UserPage> {
  final _token = CancelToken();
  String _message = '読み込み中';

  @override
  void initState() {
    super.initState();
    _load();
  }

  Future<void> _load() async {
    try {
      final response = await widget.dio.get<String>(
        '/users/me',
        cancelToken: _token,
      );
      if (!mounted) return;
      setState(() => _message = response.data ?? 'データなし');
    } on DioException catch (error) {
      if (CancelToken.isCancel(error)) return;
      if (!mounted) return;
      setState(() => _message = '読み込めませんでした');
    }
  }

  @override
  void dispose() {
    _token.cancel('page disposed');
    super.dispose();
  }

  @override
  Widget build(BuildContext context) => Text(_message);
}
```

注目するのは三つの処理です。`cancelToken`を要求へ渡し、キャンセルによる例外は`CancelToken.isCancel`で見分け、レスポンスや通常の通信エラーを画面へ反映する前に`mounted`を確認しています。キャンセルと完了が近い時刻に起きても、表示側の確認を残します。

Dioはキャンセルを`DioException`として通知します。この例では利用者が画面を閉じた結果なので、通信障害の表示へ変換しません。500応答などの通常の通信失敗は画面に表示します。キャンセル用APIと共有トークンの挙動は[Dio 5.9.2のCancellation](https://pub.dev/packages/dio/versions/5.9.2#cancellation)で確認できます。

画面から`dio.close()`を呼んでいないのは、同じクライアントを別の画面も使う可能性があるためです。画面は自分のリクエストを止め、クライアント自体を作った側がその終了を担当します。

## 「見えなくなった」と「破棄された」は同じではない

`dispose`はStateがツリーから恒久的に外れたときに呼ばれます。別の画面を上に重ねただけで、元のStateが残る場合には呼ばれません。アプリの突然の終了時にも呼ばれる保証はありません。[State.disposeの仕様](https://api.flutter.dev/flutter/widgets/State/dispose.html)に従い、「画面が見えない間も不要」という要件なら、ルートの表示状態など別の終了条件を設けます。

この例に再読込ボタンを追加する場合も、同じトークンを使い続ける実装にはしません。キャンセル済みのトークンは再利用できません。古い要求を中止して新しいトークンを作り、結果を反映するときは要求番号などで最新の要求かも確認します。二重送信防止が目的なら、送信中の操作制限やサーバー側の重複排除も別に必要です。

## Riverpodでは画面ではなくProviderの寿命へ結び付ける

取得処理をProviderが所有するなら、トークンもProviderの生成時に作ります。次の例では、共有Dioの終了と、一つの取得要求のキャンセルを別々に登録しています。

```dart
import 'package:dio/dio.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';

final dioProvider = Provider<Dio>((ref) {
  final dio = Dio(BaseOptions(baseUrl: 'https://example.invalid'));
  ref.onDispose(() => dio.close(force: true));
  return dio;
});

final userProvider = FutureProvider.autoDispose<String?>((ref) async {
  final dio = ref.watch(dioProvider);
  final token = CancelToken();
  ref.onDispose(() => token.cancel('provider disposed'));
  final response = await dio.get<String>('/users/me', cancelToken: token);
  return response.data;
});
```

`example.invalid`は説明用のアドレスなので実サービスには接続できません。テストでは`dioProvider`をfake adapter付きのDioへ差し替えています。

自動破棄は、最後の購読がなくなり、その状態が一フレーム続いたときに行われます。別の画面も同じProviderを購読していれば、片方を閉じただけでは破棄されません。また、依存するProviderの変更によって再計算される場合にも、前の状態は破棄されます。[RiverpodのAutomatic disposal](https://riverpod.dev/docs/concepts2/auto_dispose)がこの条件を説明しています。

そのため`ref.onDispose`には「特定の画面が閉じた」という意味を持たせず、そのProviderが所有する要求を終了する処理を置きます。キャンセルであるかの判定は、画面表示やエラー報告側でも通常の失敗と区別します。

## クライアントのキャンセルを、サーバーの取り消しと扱わない

DioのIO adapterはキャンセル通知を受けるとクライアントの要求を中断します。この動作から、すでにサーバーで始まった更新の取り消しまで保証することはできません。保存要求の直後に画面を閉じた場合、次に開いたときには保存が終わっている可能性があります。

更新処理では再取得で状態を確かめる、操作IDで結果を照会するなど、API側の契約に沿って扱います。キャンセルと、業務上の取消操作を同じAPIにはしません。

ここで確認したのは、fake adapterを使う5テストです。共有トークンによる二つの要求のキャンセル、キャンセル済みトークンの再使用失敗と新規トークンでの成功、Widget破棄、成功・500応答の表示、最後のProvider購読解除を含みます。実HTTP、実機での画面遷移、サーバーの処理中断は未検証です。
