## 概要

feature単位のディレクトリ構成をDDDと呼んでよいのか迷った。実際には、ファイル配置の軸と、ドメインモデル/境界づけられたコンテキストを考える手法は別だった。

Feature-firstはコードを機能単位に近接配置する構成戦略、DDDは複雑な業務知識をモデル化し境界を定義する設計思想である。併用できるが同義ではない。

## この記事で学べること

- layer-firstとfeature-first
- feature内のpresentation/application/domain/infrastructure
- DDDのEntity、Value Object、Aggregate、Domain Serviceを必要な範囲だけ
- Bounded Contextと単なる画面featureの違い
- `shared`肥大化
- feature間依存の向き

## 前提知識

- Dart、Flutter、Future、ProviderやHTTP通信の基本を読めること
- フレームワークのAPIを使った経験があり、状態・トランザクション・非同期処理の境界で詰まり始めていること
- この記事のコード例は匿名化した最小例であり、利用中のバージョンでは公式ドキュメントと実装を確認すること

## 本編

### 発生した状況

feature単位のディレクトリ構成をDDDと呼んでよいのか迷った。実際には、ファイル配置の軸と、ドメインモデル/境界づけられたコンテキストを考える手法は別だった。

### 当初の理解・誤解

当初は、API名やメソッド名から直感的に挙動を推測していました。しかし実際には、Feature-firstはコードを機能単位に近接配置する構成戦略、DDDは複雑な業務知識をモデル化し境界を定義する設計思想である。併用できるが同義ではない。 という観点で見る必要がありました。

### 観測したこと

- 小規模feature-firstディレクトリ例
- DDDを併用したfeature構造
- 禁止依存をlint/architecture testで確認する案

### 修正案の比較

| 方針 | 見るべき点 |
| --- | --- |
| Feature-first | 変更の局所性／横断共有の設計が必要 |
| DDD | 業務複雑性に強い／学習・実装コスト |

## 内部動作

FlutterやDartでは、UIのライフサイクル、非同期処理、HTTP通信、状態管理が同時に動きます。画面が閉じたこと、Futureが完了したこと、Providerが更新されたこと、通信がキャンセルされたことは、それぞれ別のイベントです。

- DDDをフォルダ名のセットとして説明しない
- すべてのFlutterアプリにdomain層が必要としない

```text
Widget lifecycle
  -> state owner
  -> async operation
  -> network/storage boundary
  -> UI update
```

## 調査手順

1. まず、入力値・保存前状態・保存後状態・コールバックや非同期処理の発火地点をログに残します。
2. 次に、DBやHTTP通信など外部境界をまたぐ処理を分けて、どこまでが同じトランザクションや同じライフサイクルに属するかを確認します。
3. 最後に、修正後の設計を最小テストへ落とし込み、同じ誤解が再発しないようにします。

- DDDをフォルダ名のセットとして説明しない
- すべてのFlutterアプリにdomain層が必要としない

## 一般化できる設計原則

- API名が短いほど、裏側の実行モデルを確認する
- 状態を「値」「オブジェクト」「DB row」「外部サービス」のどこに置いているかを分けて考える
- トランザクションや非同期処理の境界をまたぐ副作用は、明示的な設計として扱う
- テストは成功確認だけでなく、誤解しやすい境界条件を固定する

## まとめ

ディレクトリ構造は変更単位を表し、DDDは業務の意味境界を表す。解く問題が違う。


この記事では、次のような短絡的な一般化は避けます。

- Clean Architecture、DDD、Feature-firstを同一視しない
- 層を増やすことを設計品質と見なさない
