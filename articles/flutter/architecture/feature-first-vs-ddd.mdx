`features/catalog/domain/`というフォルダを作れば、DDDを採用したことになるのでしょうか。フォルダ名だけでは、そこで使う言葉の意味や、どのルールをモデルが守るかは決まりません。

ここでは、変更するファイルを機能ごとに近づける配置をFeature-firstと呼びます。DDDと併用できますが、配置を選ぶことと、業務の意味をモデル化することは別の判断です。

## 最初に、どの変更を近くへ置きたいかを決める

たとえば商品一覧と編集画面があるなら、まず次のような構成で始められます。これは説明用の案であり、Flutterが要求する標準配置ではありません。

```text
lib/
  features/
    catalog/
      presentation/
        catalog_page.dart
        catalog_view_model.dart
      data/
        catalog_repository.dart
        catalog_api.dart
    editor/
      presentation/
        editor_page.dart
      data/
        editor_repository.dart
```

`presentation/`や`data/`を最上位に置くlayer-firstなら、同じ責務のファイルをまとめて探せます。上の配置では、商品一覧を変更するときに関連ファイルを一つの機能の中で探せます。どちらも、フォルダを作るだけで責務が分離されるわけではありません。

Flutterの公式ガイドはUI層とData層の責務を分け、必要な場合にDomain層を追加する構成を説明しています。Domain層をすべての機能へ一律に用意することは勧めていません。[Flutterのアーキテクチャガイド](https://docs.flutter.dev/app-architecture/guide#optional-domain-layer)

## DDDでは、同じ言葉がどこまで同じ意味かを考える

DDDのBounded Contextは、モデルをどの範囲で一貫した意味として使うかの境界です。Eric EvansのDDD Referenceでは、モデルが適用される文脈と境界を明確にすることが説明されています。[DDD Reference（Bounded Context）](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf#page=9)

たとえば「商品」は、販売の文脈では表示名や価格を持ち、倉庫の文脈では保管場所や出荷可能数が重要かもしれません。これは説明のための仮例です。同じ`Product`という名前でも、何を同じものとして追跡し、どんな変更を許すかが違えば、一つの万能モデルへまとめるとは限りません。

画面の`catalog`フォルダと業務上の境界が一対一になる保証はありません。一つの画面が複数の文脈の情報を表示することも、一つの業務モデルを複数画面が使うこともあります。Clean Architectureの依存方向を採用する判断も、Feature-firstやDDDの名前だけから自動的には決まりません。

## 業務ルールが増えたとき、配置と責務を一緒に見直す

複雑な変更の手順や不変条件が増えたなら、一例として次のように整理できます。

```text
features/catalog/
  presentation/    # 表示と入力
  application/     # 操作の手順
  domain/          # この文脈のモデルとルール
  data/            # 外部形式と通信への対応
```

この構成でも、すべてのフォルダを先に埋める必要はありません。単純なCRUDへ空のクラスや受け渡しだけの層を増やすと、変更箇所を追う負担も増えます。まず、同じルールが複数の画面へ重複している、UIの外でも使いたい、複数データを合わせた操作が複雑、といった具体的な理由を探します。

モデル化では、同じ個体として追跡するEntity、属性の値で扱うValue Object、まとめて整合性を守るAggregateなどの区別が役立つ場面があります。しかし、これらのクラス名を並べることが目的にはなりません。どの不変条件を、どの操作から守るかを先に言葉で説明します。[DDD Reference](https://www.domainlanguage.com/ddd/reference/)

## フォルダではなく、依存の規則を検査する

たとえば「この例のdomainはUIとdata実装をimportしない」と決めても、Dartはフォルダ名だけではその規則を強制しません。次はanalyzer 9.0.0とpath 1.9.1を使い、直接のimport/exportを検査する小さなルールです。

```dart
import 'package:analyzer/dart/analysis/utilities.dart';
import 'package:analyzer/dart/ast/ast.dart';
import 'package:path/path.dart' as p;

// Example direct-edge rule, not a complete architectural dependency graph.
List<String> domainViolations(String sourcePath, String source) {
  final normalized = p.posix.normalize(sourcePath);
  if (!normalized.startsWith('lib/features/') || !normalized.contains('/domain/')) {
    return [];
  }
  final unit = parseString(content: source).unit;
  final violations = <String>[];
  for (final directive in unit.directives.whereType<NamespaceDirective>()) {
    final uris = [directive.uri.stringValue,
      ...directive.configurations.map((config) => config.uri.stringValue)];
    for (final value in uris.whereType<String>()) {
      if (value.startsWith('package:flutter/')) {
        violations.add(value);
        continue;
      }
      final uri = Uri.parse(value);
      final target = value.startsWith('package:tech_note_workbench/')
          ? 'lib/${value.substring('package:tech_note_workbench/'.length)}'
          : uri.hasScheme ? null : p.posix.normalize(p.posix.join(p.posix.dirname(normalized), value));
      if (target != null && (target.contains('/data/') || target.contains('/presentation/'))) {
        violations.add(value);
      }
    }
  }
  return violations;
}
```

この関数に`lib/features/catalog/domain/item.dart`と、`import '../data/item_api.dart';`を含むソースを渡すと、そのURIが違反として返ります。相対パスだけでなく、このパッケージ名から始まるimport、export、条件付きimport、FlutterのUI依存も検査します。Dart SDK 3.11.5で許可・禁止の7ケースをテストしました。[analyzerのパッケージ説明](https://pub.dev/packages/analyzer/versions/9.0.0)

これはこの配置に対する直接の依存だけを検査する例です。間接的な再export、part、別パッケージの内部、依存の循環まで解析するものではありません。実際に導入するなら、守る境界を決めてからプロジェクト全体を走査する処理や既存のlintへ組み込みます。DDDを採用できているかを、この検査で判定することもできません。

## sharedへ移す前に、共有する意味を確認する

似たクラスを見つけたとき、すぐに`shared/`へ移すと、別の文脈の変更が伝わる範囲を広げることがあります。UI部品の共有なのか、同じ意味の値型なのか、異なるモデルを変換する境界なのかを分けて考えます。

Feature-firstを選ぶときは変更単位を、DDDを使うときは業務の言葉・ルール・意味の境界を確かめる。両方が必要なら併用し、まだ理由がない層や抽象化は増やさずに進められます。
