Widgetの`build`で起きた例外と、待たれていない非同期処理の例外は、同じ入口に届くとは限りません。共通の報告先を用意する場合も、まずどこが例外を受け取るのかを分けて考えます。

以下の説明用コードはFlutter 3.41.9、Dart SDK 3.11.5で確認しています。外部の監視サービスへは送信せず、メモリ上の記録先を使って捕捉と報告の接続を検証しました。

## 捕捉する入口と、代わりの画面を混同しない

- `FlutterError.onError`: Flutterがbuild・layout・paintなどのコールバックで捕捉したエラーを受け取ります。
- `PlatformDispatcher.instance.onError`: root isolateで処理されなかったエラーを受け取ります。
- `runZonedGuarded`: 作成したZone内の同期例外と、そのエラーZoneに属する未処理の非同期エラーを扱います。
- `ErrorWidget.builder`: buildに失敗したWidgetの代わりに何を表示するかを決めます。

Flutterの捕捉範囲と代替表示は[Handling errors in Flutter](https://docs.flutter.dev/testing/errors)で説明されています。`ErrorWidget.builder`でメッセージを表示できても、失敗した処理やアプリの状態が回復したことにはなりません。同じ例外をここからもう一度報告すると、framework側の報告と重なる可能性があります。

また、[PlatformDispatcher.onErrorの仕様](https://api.flutter.dev/flutter/dart-ui/PlatformDispatcher/onError.html)は、子isolateからのエラーが直接は届かないこと、ハンドラーが呼ばれる前にプロセスが終了する場合があることを明記しています。これらの入口を設定しても、あらゆるクラッシュを捕捉できるという意味にはなりません。

## 共通の報告先には、元の例外・スタック・経路を渡す

次の`ErrorReporter`は報告の受付をまとめる小さな部品です。実送信は行わず、`enqueue`として渡す同期関数に記録を預けます。元のスタックを受け取り、報告側で新たに取得したスタックに置き換えません。

同じ例外オブジェクトが短時間に複数経路から届く場合に備え、同一性で重複を除きます。文字列が同じ別の例外は別件です。

```dart
import 'dart:collection';
import 'package:flutter/foundation.dart';

enum ErrorSource { framework, platform, zone }

typedef ErrorSink =
    void Function(Object error, StackTrace stack, ErrorSource source);

class ErrorReporter {
  ErrorReporter(this.enqueue, {DateTime Function()? now})
    : _now = now ?? DateTime.now;

  // 同期的にキューへ積むだけの関数。実送信・再試行は別の担当。
  final ErrorSink enqueue;
  final DateTime Function() _now;
  final _seen = LinkedHashMap<Object, DateTime>.identity();
  int dropped = 0;

  void capture(Object error, StackTrace stack, ErrorSource source) {
    final now = _now();
    _seen.removeWhere(
      (_, at) => now.difference(at) >= const Duration(seconds: 2),
    );
    if (_seen.containsKey(error)) return;
    if (_seen.length >= 128) _seen.remove(_seen.keys.first);
    _seen[error] = now;
    try {
      enqueue(error, stack, source);
    } catch (_) {
      // 報告処理の失敗を同じ報告先へ再帰させない。
      dropped++;
    }
  }
}

VoidCallback installErrorHooks(ErrorReporter reporter) {
  final previousFlutter = FlutterError.onError;
  final previousPlatform = PlatformDispatcher.instance.onError;
  FlutterError.onError = (details) {
    reporter.capture(
      details.exception,
      details.stack ?? StackTrace.empty,
      ErrorSource.framework,
    );
    previousFlutter?.call(details);
  };
  PlatformDispatcher.instance.onError = (error, stack) {
    reporter.capture(error, stack, ErrorSource.platform);
    // 送信の受付だけで「処理済み」へ変更しない。
    return previousPlatform?.call(error, stack) ?? false;
  };
  return () {
    FlutterError.onError = previousFlutter;
    PlatformDispatcher.instance.onError = previousPlatform;
  };
}
```

2秒・128件はこの例の方針で、Flutterの保証値ではありません。同じオブジェクトでも時間窓を過ぎれば再び記録し、上限に達したら古い項目を捨てます。これは報告先への到達を保証する仕組みではなく、最初の経路だけを残す簡単な重複排除です。複数のエラーが同じオブジェクトを使う設計には適しません。

`enqueue`は同期的に受付を済ませる契約です。Futureを返す非同期送信を直接渡すと、その後の失敗はこの`try`では処理できません。送信担当でバッファの上限・再試行・失敗時の扱いを決めます。ここでは受付自体が例外を投げた場合だけ`dropped`を増やし、同じ報告処理へ再帰させないようにしています。

例外のメッセージやスタックには、URLや識別子などが含まれることがあります。生の内容を外部へ送る前に、送信項目の選別や秘匿化を行います。このコードには送信処理や汎用的な秘匿化機能はありません。

## 既存ハンドラーの動作と、処理済みの判断を保つ

`installErrorHooks`は元のハンドラーを保存し、独自の報告後に呼びます。Flutterの通常のログ出力やテスト環境のエラー管理を、代入だけで失わないためです。ただし、既存の監視SDKも送信する場合、その送信はこの`ErrorReporter`の重複排除の外にあります。アプリ起動時にどの部品がハンドラーを所有するかを決め、重ねてインストールしない前提です。

Platform側の戻り値にも意味があります。`true`はエラーを処理したという通知です。報告キューへ積めたことだけで処理済みにはせず、この例は既存ハンドラーの判断を返します。元のハンドラーがなければ`false`とし、プラットフォームのフォールバックに委ねます。回復や終了の方針は別途決める必要があります。

起動側は、報告先の準備後に次の関数を一度呼びます。`error_reporter.dart`には先ほどのコードを置きます。

```dart
import 'package:flutter/widgets.dart';
import 'error_reporter.dart';

// reporter.enqueueの準備が済んでからmainで一度呼ぶ。
void startApp(Widget app, ErrorReporter reporter) {
  WidgetsFlutterBinding.ensureInitialized();
  installErrorHooks(reporter);
  runApp(app);
}
```

フックから返す復元関数はテストなどで使います。この簡単な復元処理は、その後に別のSDKがハンドラーを書き換えていないことを前提にしています。

## Zoneを追加するなら、初期化も同じZoneへ置く

すでに上の入口で扱える範囲に、理由なく`runZonedGuarded`を重ねる必要はありません。Zoneの境界が必要な場合は、`WidgetsFlutterBinding.ensureInitialized()`と`runApp()`を同じZone内で実行します。片方だけを外に置くと、[FlutterのZone mismatch](https://docs.flutter.dev/release/breaking-changes/zone-errors)に該当します。

さらに、[runZonedGuardedの仕様](https://api.dart.dev/dart-async/runZonedGuarded.html)では、異なるエラーZoneの境界を非同期エラーが越えないとされています。内側で失敗したFutureを外側で待つと、完了しないように見える場合があります。「アプリ全体を包んで、そのFutureを外からawaitすればよい」とは限りません。

入力の検証失敗や通信エラーなど、呼び出し側で回復方法が分かる失敗は、その場で処理します。グローバルな入口は、通常の画面操作で必要なエラー表示や再試行を置き換えるものではありません。

検証は5テストです。同一オブジェクトの重複・時間窓・保持数上限・受付失敗、既存ハンドラーとスタックの保持、実際のWidget build失敗と代替表示、Zone内の非同期例外を確認しました。Platform側は登録コールバックを直接呼ぶ検証であり、実機の未処理例外の配送やネイティブクラッシュ、監視サービスへの送信は未確認です。
