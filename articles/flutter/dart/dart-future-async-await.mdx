## 概要

interfaceに`Future&lt;String?&gt; readRefreshToken();`と書かれているのに`await`がなく、なぜ非同期なのか分からなかった。戻り値の型、実装側の修飾子、呼び出し側の待機構文を同じものとして捉えていた。

`Future&lt;T&gt;`は将来得られる値を表す型、`async`は関数本体を非同期に書くための修飾子、`await`はFutureの完了まで現在のasync関数を一時停止する式である。宣言・実装・呼び出しを分けて理解する。

## この記事で学べること

- interface/abstract methodは実装を持たないため`async`不要
- `Future&lt;T&gt;`を返す同期的な関数宣言
- `async`関数が返り値をFutureで包むこと
- 呼び出し側の`await`
- Futureをそのままreturnする場合
- `return await`が必要になるtry/catch等の文脈

- Dart、Flutter、Future、ProviderやHTTP通信の基本を読めること

- この記事のコード例は匿名化した最小例であり、利用中のバージョンでは公式ドキュメントと実装を確認すること

## 本編

### 発生した状況

interfaceに`Future&lt;String?&gt; readRefreshToken();`と書かれているのに`await`がなく、なぜ非同期なのか分からなかった。戻り値の型、実装側の修飾子、呼び出し側の待機構文を同じものとして捉えていた。

### 当初の理解・誤解

当初は、API名やメソッド名から直感的に挙動を推測していました。しかし実際には、`Future&lt;T&gt;`は将来得られる値を表す型、`async`は関数本体を非同期に書くための修飾子、`await`はFutureの完了まで現在のasync関数を... という観点で見る必要がありました。

### 観測したこと

- `Future&lt;String?&gt; read()`のinterfaceと実装
- `return storage.read(...)`と`return await storage.read(...)`比較
- `Future.wait`で並列化する例
- エラー伝播のunit test

### 修正案の比較

| 方針 | 見るべき点 |
| --- | --- |
| Futureを直接返す | 簡潔・スタックが明確／局所try-catchしにくい |
| `async/await` | 読みやすい／不要なasyncは層を増やす |

## 内部動作

FlutterやDartでは、UIのライフサイクル、非同期処理、HTTP通信、状態管理が同時に動きます。画面が閉じたこと、Futureが完了したこと、Providerが更新されたこと、通信がキャンセルされたことは、それぞれ別のイベントです。

- `await`はスレッドをブロックする説明にしない
- `async`を付けるだけで別スレッド実行になるわけではない
- イベントループ/Isolateの詳細へ必要以上に広げない

```text
Widget lifecycle
  -> state owner
  -> async operation
  -> network/storage boundary
  -> UI update
```

1. まず、入力値・保存前状態・保存後状態・コールバックや非同期処理の発火地点をログに残します。
