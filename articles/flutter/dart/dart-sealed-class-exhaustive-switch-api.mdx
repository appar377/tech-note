`send(method: 'PUT', id: 'guide', text: null)`という呼び出しを受け取ったら、本文が足りないことを実行時に検査する必要があります。GETには不要で、PUTには必要な値を一つの引数群へまとめると、このような組み合わせを作れてしまいます。

操作ごとに必要なデータが違うなら、別の型として表す方法があります。ここでは通信処理を外し、GETとPUTの入力を組み立てて分岐する部分に絞ります。Dart 3以降のsealed classとパターンを使い、Dart SDK 3.11.5で検証しています。

## 操作ごとの引数をコンストラクタで受け取る

```dart
sealed class DocumentRequest {
  const DocumentRequest();
}

final class GetDocument extends DocumentRequest {
  const GetDocument(this.id);
  final String id;
}

final class PutDocument extends DocumentRequest {
  const PutDocument(this.id, this.text);
  final String id;
  final String text;
}

String describe(DocumentRequest request) => switch (request) {
  GetDocument(:final id) => 'GET $id',
  PutDocument(:final id, :final text) => 'PUT $id: $text',
};

void main() {
  print(describe(const GetDocument('guide'))); // GET guide
  print(describe(const PutDocument('guide', 'updated')));
  // PUT guide: updated
}
```

`GetDocument`には本文を渡す引数がなく、`PutDocument`にはnullではない本文が必須です。`'POT'`のような任意のmethod文字列を受け取る入口もなくなります。switch内のオブジェクトパターンは、該当する型のフィールドを取り出しています。[オブジェクトパターン](https://dart.dev/language/pattern-types#object)

この例の`describe`は説明用の文字列を返すだけです。HTTP通信、認証、署名付きURLの生成は行っていません。

## sealedが閉じる範囲はライブラリ単位

`sealed`な基底型を直接extends・implementsする型は、同じライブラリ内に限られます。そのため解析器は、基底型の直接のサブタイプを把握できます。sealed class自体は暗黙にabstractです。[sealedの制約](https://dart.dev/language/class-modifiers#sealed)

ここでいうライブラリは、単純にフォルダと同じ意味ではありません。通常はDartファイルが一つのライブラリを構成し、`part`を使えば複数ファイルが同じライブラリに属します。基底型とケースを別ファイルへ分ける場合は、この境界を確認します。[ライブラリの説明](https://dart.dev/language/libraries)

また、sealedの直接のサブタイプが自動的にfinalになるわけではありません。この例では末端の二つを`final class`にして、外部ライブラリからさらにextends・implementsすることを制限しています。同じライブラリ内のコードまで禁止する指定ではありません。

## ケースを追加すると、分岐の見落としを検出できる

同じライブラリに`DeleteDocument`を追加し、上のswitchを変更しない場合、switch式が網羅的でなくなります。解析器は未対応のケースを報告します。[網羅性の検査](https://dart.dev/language/branches#exhaustiveness-checking)

これは「すべての操作に対応する場所」を見つける助けになります。ただし、最初から`_ => ...`で残りをすべて受け取れば、新しいケースもその分岐へ入り、追加時の見落としを検出しにくくなります。各操作を明示的に扱いたい場所では、安易なcatch-allを置かない方が目的に合います。

検証では二つのケースの結果に加え、Deleteを追加した未対応のswitchと、外部ライブラリからsealed基底型を継承するコードが、解析エラーになることを確かめました。これらは意図的な失敗例なので、通常の実装へ混ぜません。

## enumで足りる場合と、実行時に残る検査

どの操作も同じデータを持ち、値の選択肢だけを限定したいならenumで十分なことがあります。sealedを使う理由は、今回のようにケースごとに必要なデータや処理が違うときに明確になります。

型を分けても、空のID、不正な本文、認証期限切れ、通信失敗まで防げるわけではありません。これらは入力検証や通信層の責務として残ります。「不正状態をすべて表現不能にする」ではなく、この例では「PUTなのに本文が指定されていない組み合わせを作れなくする」と範囲を限定して捉えます。

操作ごとに返り値の型まで変えたい場合は、ジェネリクスを含む別の設計が必要です。まずは入力の組み合わせを小さく整理し、必要になった段階で返り値の契約へ広げる方が、分岐の利点を確認しやすくなります。
