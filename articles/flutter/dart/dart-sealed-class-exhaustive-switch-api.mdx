## 概要

Presigned URLへのGET/PUT処理を文字列やbooleanで切り替えると、必要データの違いと不正組み合わせを表現しやすい。

各操作を異なるsubtypeとして表現し、sealed基底型に対する網羅的switchでdispatchする。不正状態を実行時チェックではなく型で表現不能にする。

## この記事で学べること

- 文字列method分岐の問題
- enumで足りる場合と、各caseが別データを持つ場合
- `sealed class S3Request&lt;T&gt;`
- `GetRequest`と`PutRequest`
- pattern matchingとexhaustiveness
- private subtype/constructor

## 前提知識

- Dart、Flutter、Future、ProviderやHTTP通信の基本を読めること
- フレームワークのAPIを使った経験があり、状態・トランザクション・非同期処理の境界で詰まり始めていること
- この記事のコード例は匿名化した最小例であり、利用中のバージョンでは公式ドキュメントと実装を確認すること

## 実装コード例

```dart
sealed class UserRequest {
  const UserRequest();
}

class GetUser extends UserRequest {
  const GetUser(this.id);
  final String id;
}

class PutUser extends UserRequest {
  const PutUser(this.id, this.body);
  final String id;
  final Map<String, Object?> body;
}
```

## 本編

### 発生した状況

Presigned URLへのGET/PUT処理を文字列やbooleanで切り替えると、必要データの違いと不正組み合わせを表現しやすい。

### 当初の理解・誤解

当初は、API名やメソッド名から直感的に挙動を推測していました。しかし実際には、各操作を異なるsubtypeとして表現し、sealed基底型に対する網羅的switchでdispatchする。不正状態を実行時チェックではなく型で表現不能にする... という観点で見る必要がありました。

### 観測したこと

- Dart 3に合わせたsealed classコード
- `switch (request)`でGET/PUTを処理
- 不正method文字列が存在しないことを示すtest

### 修正案の比較

| 方針 | 見るべき点 |
| --- | --- |
| sealed union | 型安全／型数が増える |
| enum+data | 単純／case固有データの不整合を許しやすい |

## 内部動作

FlutterやDartでは、UIのライフサイクル、非同期処理、HTTP通信、状態管理が同時に動きます。画面が閉じたこと、Futureが完了したこと、Providerが更新されたこと、通信がキャンセルされたことは、それぞれ別のイベントです。

- Dart/Flutterの実際の言語バージョンを確認
- sealedは同一library内のsubtyping制約を含むため正確に説明

```text
Widget lifecycle
  -> state owner
  -> async operation
  -> network/storage boundary
  -> UI update
```

## 調査手順

1. まず、入力値・保存前状態・保存後状態・コールバックや非同期処理の発火地点をログに残します。
2. 次に、DBやHTTP通信など外部境界をまたぐ処理を分けて、どこまでが同じトランザクションや同じライフサイクルに属するかを確認します。
3. 最後に、修正後の設計を最小テストへ落とし込み、同じ誤解が再発しないようにします。

## 一般化できる設計原則

- API名が短いほど、裏側の実行モデルを確認する
- 状態を「値」「オブジェクト」「DB row」「外部サービス」のどこに置いているかを分けて考える
- トランザクションや非同期処理の境界をまたぐ副作用は、明示的な設計として扱う
- テストは成功確認だけでなく、誤解しやすい境界条件を固定する

## まとめ

分岐条件をデータとして持つより、許される操作を型として定義する。


この記事では、次のような短絡的な一般化は避けます。

- 文字列分岐をすべてsealedへ置き換えるとしない
- 存在しない構文を生成しない
