同じフィールド値を持つ二つのインスタンスが、`==`で等しくなるとは限りません。`Object`から継承した既定の比較は同一性に基づくためです。値としての等しさが必要なら、どのフィールドで判断するかを型の側で定義します。[Object.operator ==](https://api.dart.dev/dart-core/Object/operator_equals.html)

| 確かめること | 使うもの |
| --- | --- |
| 同一のオブジェクトか | `identical(a, b)` |
| この型が定義する意味で等しいか | `a == b` |
| ハッシュコレクションで候補を探すための値 | `a.hashCode` |

## 同じ色を値として比較する

色名と濃さの組み合わせが同じなら等しい、という小さな型を作ります。ここでの`final class`は外部ライブラリでの継承を制限しますが、フィールドの不変性とは別の指定です。

```dart
final class Swatch {
  Swatch(this.name, this.shade);
  final String name;
  final int shade;

  @override
  bool operator ==(Object other) =>
      other is Swatch && name == other.name && shade == other.shade;

  @override
  int get hashCode => Object.hash(name, shade);
}

void main() {
  final first = Swatch('teal', 500);
  final second = Swatch('teal', 500);
  final different = Swatch('teal', 600);

  print(identical(first, second)); // false
  print(first == second); // true
  print(first.hashCode == second.hashCode); // true
  print({first, second, different}.length); // 2
}
```

このコンストラクタはconstではないため、二つの呼び出しは別のインスタンスを作ります。一方、`==`は両方のフィールドを比較するのでtrueです。Setは等しい二つを重複として扱い、濃さの違う一つと合わせて要素数は2になります。Dart SDK 3.11.5で、この結果と新しい同値インスタンスによる`contains`を確認しています。

なお、同じ定数をconstとして生成すると`identical`もtrueになる場合があります。「フィールド値が同じなら常に別インスタンス」とも言えません。[identicalのAPI](https://api.dart.dev/dart-core/identical.html)

## hashCodeだけでは等しいと判断できない

守る必要があるのは、`a == b`がtrueなら両者の`hashCode`も同じ、という方向です。異なる値でもハッシュ値は衝突します。ハッシュ値の一致だけで等しさを判定したり、永続的なIDにしたりしないようにします。実行をまたいで同じ数値になる保証もありません。[hashCodeの契約](https://api.dart.dev/dart-core/Object/hashCode.html)

たとえば、比較には`name`と`shade`を使い、ハッシュには無関係なインスタンス固有値を使うと、この契約を破ります。たまたま検索できた結果があっても、正しい実装の根拠にはなりません。

もう一つの問題は、Setへ入れたあとで比較に使うフィールドを変えることです。格納時と検索時でハッシュが変わると、期待した要素を見つけられなくなる可能性があります。壊れ方の具体的な結果を保証するのではなく、格納中の等価性とハッシュを変えない設計にします。[HashSetの注意事項](https://api.dart.dev/dart-collection/HashSet-class.html)

## Listの比較と、Listを持つモデルの比較は分ける

通常のListの`==`は、要素を一つずつ比較しません。そのため`<int>[1] == <int>[1]`はfalseです。ただし、二つとも同じconst Listなら、定数の共有によって同一になる場合があります。[List.operator ==](https://api.dart.dev/dart-core/List/operator_equals.html)

モデルがListを持つなら、「順序も含めて一致」「順序を無視」「特定の要素のIDだけ一致」のどれを求めるのかを先に決めます。`final List`でも要素の追加や削除ができることには注意が必要です。比較方式を決めることと、あとから値を変更させないことは別の作業です。

## Equatableではpropsが比較の範囲になる

Equatableは、`props`に列挙した値を使って`==`と`hashCode`の実装を補助します。色の例なら`props`へ`name`と`shade`を含めます。`shade`を省けば、濃さを変えても比較に反映されません。[Equatableの公式README](https://pub.dev/packages/equatable)

同READMEは不変なオブジェクトでの利用を前提としています。Equatableを継承しても、外部から渡したListやその要素を自動的に変更不能にするわけではありません。コレクションを含む比較の詳細は採用バージョンの実装とテストで確認してください。List自身の`==`が同一性比較だからといって、Equatableの`props`内でも必ず同じ扱いになる、と推論しないことが大切です。

この記事ではEquatableのパッケージを実行していません。手書きの値型をDart標準ライブラリで検証し、Equatableについては公式のAPI説明を確認した範囲を記載しています。導入時には、実際のモデルについて同値・異なる値・コレクションの内容変更をテストする必要があります。

単純な値の組み合わせならrecord、生成コードをすでに使うモデルならその等価性実装も候補になります。どの手段でも、先に「何が同じなら同じ値なのか」を決めることが出発点です。
