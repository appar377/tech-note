## 概要

Access TokenとRefresh Tokenを同じストレージへ保存する実装が単純に見えたが、寿命、権限、再起動後の必要性、漏洩時の影響が異なる。メモリ保持とSecure Storageの分離を検討した。

一般的には短命なAccess Tokenをメモリ、長命で再発行能力を持つRefresh TokenをSecure Storageへ置くと、永続化する秘密を減らせる。ただし絶対解ではなく、脅威モデル、UX、認証基盤の仕様で判断する。

## この記事で学べること

- Access TokenとRefresh Tokenの権限・寿命
- アプリ再起動時にAccess Tokenをrefreshで再取得する流れ
- ログアウト時の削除範囲
- `deleteAll()`ではなく専用キー削除を検討
- refresh token rotation
- 端末紛失・root/jailbreak・ログ漏洩

## 実装コード例

```dart
class TokenStore {
  String? _accessToken;
  final SecureStorage secureStorage;

  TokenStore(this.secureStorage);

  Future<void> saveTokens(TokenPair pair) async {
    _accessToken = pair.accessToken;
    await secureStorage.write('refresh_token', pair.refreshToken);
  }
}
```

## 本編

### 発生した状況

Access TokenとRefresh Tokenを同じストレージへ保存する実装が単純に見えたが、寿命、権限、再起動後の必要性、漏洩時の影響が異なる。メモリ保持とSecure Storageの分離を検討した。

### 当初の理解・誤解

当初は、API名やメソッド名から直感的に挙動を推測していました。しかし実際には、一般的には短命なAccess Tokenをメモリ、長命で再発行能力を持つRefresh TokenをSecure Storageへ置くと、永続化する秘密を減らせ... という観点で見る必要がありました。

### 観測したこと

- `AuthTokenHolder`のメモリ実装
- `TokenStorage`のrefresh token専用API
- 起動時bootstrapとlogoutの例
- Access Tokenが永続化されていないことを確認するtest

### 修正案の比較

| 方針 | 見るべき点 |
| --- | --- |
| メモリ保持 | 永続漏洩面を減らす／再起動時refreshが必要 |
| 永続化 | UXが単純／保存秘密と攻撃面が増える |

## 内部動作

FlutterやDartでは、UIのライフサイクル、非同期処理、HTTP通信、状態管理が同時に動きます。画面が閉じたこと、Futureが完了したこと、Providerが更新されたこと、通信がキャンセルされたことは、それぞれ別のイベントです。

- OAuth/OIDCサーバーの仕様を確認する
- Secure Storageは暗号化やOS保護を利用するが、侵害端末での完全防御ではない
- Access Tokenをメモリだけに置けない要件もある

## まとめ

トークンの保存場所は「秘密だから全部Secure Storage」ではなく、寿命と再発行能力に応じて最小化する。


この記事では、次のような短絡的な一般化は避けます。

- この保存戦略が全アプリの唯一解と断定しない
- Refresh Tokenをログへ出さない
