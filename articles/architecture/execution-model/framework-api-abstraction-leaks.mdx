`copyWith(note: null)` を呼んだのに、メモが消えない。メソッド名から「渡した値で置き換える」と考えても、実装が省略とnullを同じ意味にしていれば、その操作は表現できません。

APIを調べるときは、入力から戻り値までの間に何が起きるかを確認します。ここではDart 3.11.5向けの小さな例で契約の読み方を確かめ、Railsや保存・通信のAPIへ調査の視点を広げます。コードは説明用です。Dart 3.11.5で実行し、出力の全項目を期待値と照合しました。

## copyWithのnullは、削除ですか、変更なしですか？

`copyWith` はDart言語が動作を一律に決める特別な構文ではありません。手書きのメソッドや、採用した生成ツールの実装を読む必要があります。

次の `LegacyDraft` は、引数がnullなら既存の値を使います。`ArticleDraft` は用途を分け、名前の変更、メモの置換、メモの削除をそれぞれ明示した設計例です。このコード全体を `api_contract.dart` として実行できます。

```dart file="api_contract.dart"
import 'dart:convert';

final class LegacyDraft {
  final String title;
  final String? note;
  LegacyDraft(this.title, this.note);

  LegacyDraft copyWith({String? title, String? note}) =>
      LegacyDraft(title ?? this.title, note ?? this.note);
}

final class ArticleDraft {
  final String title;
  final String? note;
  ArticleDraft(this.title, this.note);

  ArticleDraft rename(String title) => ArticleDraft(title, note);
  ArticleDraft replaceNote(String note) => ArticleDraft(title, note);
  ArticleDraft clearNote() => ArticleDraft(title, null);
}

void main() {
  final legacy = LegacyDraft('Intro', 'review later');
  final draft = ArticleDraft('Intro', 'review later');
  final renamed = draft.rename('Revised');
  final replaced = draft.replaceNote('ready');
  final cleared = draft.clearNote();

  print(jsonEncode({
    'legacy_omitted_note': legacy.copyWith().note,
    'legacy_explicit_null': legacy.copyWith(note: null).note,
    'rename_keeps_note': {'title': renamed.title, 'note': renamed.note},
    'replace_note': replaced.note,
    'clear_note': cleared.note,
    'clear_twice': cleared.clearNote().note,
    'original_note': draft.note,
    'new_instance': !identical(draft, cleared),
  }));
}
```

実行結果から、代表的な操作と値の変化を抜き出すと次のようになります。

| 操作 | 期待する結果 |
| --- | --- |
| `legacy.copyWith()` | noteは `review later` のまま |
| `legacy.copyWith(note: null)` | やはり `review later` のまま |
| `draft.rename('Revised')` | titleだけ変わり、noteは残る |
| `draft.replaceNote('ready')` | noteが `ready` になる |
| `draft.clearNote()` | 返された別インスタンスのnoteがnullになる |
| 元の `draft.note` | `review later` のまま |

省略可能なnullable引数の既定値はnullです。そして `??` は左辺がnullなら右辺を使います。この2つを組み合わせた `LegacyDraft` の実装では、省略と明示的なnullを区別できません。[Dart: Named parameters](https://dart.dev/language/functions#named-parameters)、[Conditional expressions](https://dart.dev/language/operators#conditional-expressions)

この例の修正は、2つしかない属性に必要な操作を絞ったものです。属性が多いモデルや部分更新の入力では、`copyWith` を残し、未指定とnullを別に表現する設計も選べます。[DartのcopyWithで未指定とnullを分ける](/tech-note/articles/flutter/dart/dart-copywith-sentinel-pattern/)では、その設計を扱います。

## 戻り値が正しければ、契約を確認したことになりますか？

値の変化と、変更される対象も確認します。この例では新しい `ArticleDraft` を返し、元のインスタンスを変更しません。文字列の属性だけを扱うため、内側の可変オブジェクトを共有する問題は含めていません。一般の `copyWith` が深いコピーを行う、あるいは常に別インスタンスを返すと保証した例ではありません。

同じ確認を実際のAPIへ当てはめると、調べる対象は次のようになります。これらは一次資料による説明であり、下のフレームワーク動作を今回のDart CLI例で再現したわけではありません。

| API | 名前だけでは決められない点 | 確認先 |
| --- | --- | --- |
| Rails `with_lock` | transaction内で、ブロックの前にロックを伴うreloadが入る。未保存変更のある永続化済みインスタンスには制約がある | [Rails 8.1.3 Pessimistic Locking](https://api.rubyonrails.org/v8.1.3/classes/ActiveRecord/Locking/Pessimistic.html) |
| Rails `save` | 新規作成か更新か、validationやcallbackで保存が止まるか、falseと例外のどちらを扱うか | [Rails 8.1.3 Persistence](https://api.rubyonrails.org/v8.1.3/classes/ActiveRecord/Persistence.html#method-i-save) |
| 自作Repositoryの `save` | DB保存、HTTP通信、作成と更新のどれを含むか。契約はそのRepositoryが決める | [Repositoryの保存操作を設計する](/tech-note/articles/flutter/architecture/repository-save-create-update-design/) |
| `FlutterSecureStorage.deleteAll` | 選択した保存領域の複数キーが対象になる。ログアウトで消したい1キーと範囲が合うか | [flutter_secure_storage 10.3.1](https://pub.dev/packages/flutter_secure_storage/versions/10.3.1#usage) |
| Dio `CancelToken` | 同じtokenを共有する要求がまとめてキャンセルされる。サーバーの更新取り消しは別の契約として考える | [Dio 5.9.2 Cancellation](https://pub.dev/packages/dio/versions/5.9.2#cancellation) |
| Railsのscope | 返すのは通常、合成できるRelation。名前から単一行や真偽値を期待しない | [Rails 8.1.3 Named Scopes](https://api.rubyonrails.org/v8.1.3/classes/ActiveRecord/Scoping/Named/ClassMethods.html#method-i-scope) |

例えば `with_lock` の後にインスタンスの保存差分を調べるコードなら、ロックの排他性だけでなくreloadの影響も調べる必要があります。[with_lockで保存差分が失われる例](/tech-note/articles/rails/active_record/with-lock-dirty-tracking-after-commit/)が、その具体例です。

`CancelToken` の公開契約はDioの要求の中断です。そこから、既にサーバーで始まった処理の取り消しまで期待することはできません。保存結果の再確認や、業務上の取消操作は別に設計します。[CancelTokenの所有と寿命](/tech-note/articles/flutter/architecture/dio-cancel-token-lifecycle/)で詳しく扱います。

## どこまで内部実装を読む必要がありますか？

まず公開ドキュメントで、呼び出し側が依存してよい契約を確認します。次に採用版のソースや生成コードを読み、分からない挙動を絞ります。ソースに見つけた処理順やキャッシュ方法が、将来の版でも約束されるとは限りません。

レビューでは、APIの名前を分類するより、次の問いへ具体的に答えます。

| 見る対象 | `ArticleDraft` での答え | 保存や通信のAPIなら追加する問い |
| --- | --- | --- |
| 入力と戻り値 | 変更操作を明示し、新しい値を返す | 未指定・空・null・失敗の表現は何か |
| 状態変更 | 元のdraftは変更しない | 同じインスタンス、DB、キャッシュのどれが変わるか |
| I/O | 行わない | 呼び出した時点で外部処理が始まるか |
| 寿命 | 返した値を呼び出し側が保持する | token、接続、購読は誰が終了させるか |
| 失敗 | この例にはvalidationや外部失敗を含めない | 例外の時点で何が変更済みか |
| 並行実行 | この同期例では扱わない | 重複実行、キャンセル、再試行を誰が調整するか |

分からない点が残ったら、その点だけを動かす最小例を用意します。今回なら「nullを渡す」と「省略する」を並べ、元の値と戻り値を別々に確認します。外部APIなら、同じ方法で成功と失敗の境界を限定して調べます。

高水準のAPIを使うこと自体を問題にする必要はありません。呼び出し側が必要とする契約が広すぎるなら、今回の `clearNote` のように、用途に合う操作へ絞って公開できます。状態がいつ読み直されるかの追い方は、[状態・評価時点・境界からコードを読む](/tech-note/articles/architecture/execution-model/execution-model-over-syntax/)へ続きます。
