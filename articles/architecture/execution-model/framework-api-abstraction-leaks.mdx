## 概要

`with_lock`は囲むだけ、`save`は保存するだけ、`copyWith`はコピーするだけに見える。しかし実際にはreload、I/O、transaction、instance生成、null semanticsなどの副作用が隠れる。

便利なAPIは複雑さを削除するのではなく、通常経路から隠す。障害調査では、戻り値、状態変更、I/O、ライフサイクル、例外、並行性の6点で抽象化を開く。

## この記事で学べること

- `with_lock`: transaction/row lock/reload
- Repository `save`: create/update/network
- `copyWith`: 新instanceとnull semantics
- `deleteAll`: 保存領域の広すぎる削除
- `CancelToken`: client側だけのcancel
- Scope名: Relation/件数

- Rails、Dart、Swiftのいずれかで、状態や副作用の扱いに触れたこと
- フレームワークのAPIを使った経験があり、状態・トランザクション・非同期処理の境界で詰まり始めていること

## 本編

### 発生した状況

`with_lock`は囲むだけ、`save`は保存するだけ、`copyWith`はコピーするだけに見える。しかし実際にはreload、I/O、transaction、instance生成、null semanticsなどの副作用が隠れる。

### 当初の理解・誤解

当初は、API名やメソッド名から直感的に挙動を推測していました。しかし実際には、便利なAPIは複雑さを削除するのではなく、通常経路から隠す。障害調査では、戻り値、状態変更、I/O、ライフサイクル、例外、並行性の6点で抽象化を開く。 という観点で見る必要がありました。

### 観測したこと

- 各APIを1つずつ最小コードで示す
- 副作用チェックリストのMarkdown表
- wrapper APIで契約を狭める例

### 修正案の比較

| 方針 | 見るべき点 |
| --- | --- |
| 高レベルAPI | 生産性／障害時に内部理解が必要 |
| 低レベル直接操作 | 制御／重複と誤用 |

## 内部動作

複数の言語やフレームワークを横断すると、同じ名前の概念でも意味が変わります。構文を暗記するより、実行時に何が保持され、いつ評価され、どこで副作用が出るかを追う方が、保守時の判断に効きます。

- 抽象化漏れは必ずしも設計欠陥ではない
- 内部実装依存と公開契約を区別する

```text
syntax
  -> state
  -> lifecycle
  -> boundary
  -> execution model
```

## 調査手順

1. まず、入力値・保存前状態・保存後状態・コールバックや非同期処理の発火地点をログに残します。
2. 次に、DBやHTTP通信など外部境界をまたぐ処理を分けて、どこまでが同じトランザクションや同じライフサイクルに属するかを確認します。
3. 最後に、修正後の設計を最小テストへ落とし込み、同じ誤解が再発しないようにします。

- 抽象化漏れは必ずしも設計欠陥ではない
- 内部実装依存と公開契約を区別する

## 再発防止テスト

```text
given: 状態と境界を明示する
when: 実行モデルに沿って処理を進める
then: 期待した副作用だけが発生する
```

## 一般化できる設計原則

- API名が短いほど、裏側の実行モデルを確認する
- 状態を「値」「オブジェクト」「DB row」「外部サービス」のどこに置いているかを分けて考える
- トランザクションや非同期処理の境界をまたぐ副作用は、明示的な設計として扱う
- テストは成功確認だけでなく、誤解しやすい境界条件を固定する

## まとめ

API名から動作を推測せず、状態と境界を観測する習慣を持つ。


この記事では、次のような短絡的な一般化は避けます。

- フレームワークを使わない方がよいという結論にしない
- 内部実装の偶然を公開契約として扱わない
