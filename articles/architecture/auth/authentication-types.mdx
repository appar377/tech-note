「ログインはJWTにするか、OAuthにするか」という問いだけでは、決める対象が揃いません。JWTは情報の表現形式、OAuth 2.0はAPIへのアクセスを委譲する枠組みです。パスワードやPasskeyで認証し、OIDCで結果を受け取り、自分のサービスではCookieでセッションを維持する構成もあります。

方式を選ぶ前に、**何の制御を確かめるか、誰から結果を受け取るか、次のリクエストへどう引き継ぐか**を分けます。この記事はその境界を整理するもので、認証機能の実装や安全性を検証する手順ではありません。

## 「認証方式」の一覧には何が混ざっているのか

| 決めたいこと | 関係する用語 | 別に決めること |
| --- | --- | --- |
| アカウントに登録した認証手段を使えるか確かめる | パスワード、OTP、Passkey | 登録、紛失、復旧時の確認 |
| 外部の認証結果やアクセス権を受け取る | OIDC、SAML、OAuth 2.0 | 信頼する発行者、受信側での検証 |
| 情報をどの形式で表すか | JWT、SAML Assertion、不透明なトークン | 有効期間、利用先、失効方法 |
| ログイン状態を次の要求へ引き継ぐ | セッション、Cookie、Authorizationヘッダー | 状態の保存先とブラウザの送信条件 |
| 対象の操作を許可する | ロール、権限、リソースの所有関係 | 各リクエストでの認可 |

認証が成立しても、その利用者にすべての操作を許すわけではありません。また、アカウントに結びつく認証手段の制御確認と、公的な身元の確認も同じではありません。NISTも認証と身元確認を別の文書で扱っています。[NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)

## CookieとJWTはどう組み合わせるのか

Cookieはブラウザが保存し、条件に合うリクエストへ送る仕組みです。Cookieの値がサーバー内のセッションを引くIDの場合も、保護されたセッションデータ自体の場合もあります。たとえばRailsのCookieStoreは後者です。「Cookieを使う」と決めただけでは、セッション状態の保存先は決まりません。[Rails Security Guide: Session Storage](https://guides.rubyonrails.org/security.html#session-storage)

一方、JWTはクレームを表現する形式です。署名されたJWTと暗号化されたJWTを区別し、署名があるだけで内容が秘匿されるとは考えません。JWTをCookieで運ぶこともできるため、CookieとJWTを排他的な選択肢として比べると、保存・送信・検証の話が混ざります。[RFC 7519](https://www.rfc-editor.org/rfc/rfc7519)

アクセストークンも、JWT形式とは限りません。利用側が内部構造を読まない不透明な文字列もあります。さらにBearerは「持っている者が利用できる」という使用上の性質で、JWTという形式名とは別です。[RFC 6749 §1.4](https://www.rfc-editor.org/rfc/rfc6749#section-1.4)、[RFC 6750 §1.2](https://www.rfc-editor.org/rfc/rfc6750#section-1.2)

ここで必要なのは「JWTならセッション管理不要」という判断ではなく、有効期間内の資格情報をどこまで受け入れ、ログアウト・アカウント停止・漏えい時にどう無効化するかという設計です。

## XSSとCSRFでは、何を防ぐ必要があるのか

| 仕組み | 防げること・変わること | それだけでは防げないこと |
| --- | --- | --- |
| Cookieの`HttpOnly` | JavaScriptによるCookie値の読み取りを制限します | XSSが同じオリジンから認証付き操作を行うこと |
| Cookieの`Secure` | Cookieを送る通信をHTTPSに限定します | XSS、アプリケーションの認可漏れ |
| Cookieの`SameSite` | クロスサイト要求にCookieを付ける条件を制限します | すべてのCSRF、同一サイト内の別オリジンからの攻撃 |
| JavaScriptから付けるBearerヘッダー | 通常のクロスサイトフォームから同じヘッダーは自動では付きません | XSSによるトークン読取りや、アプリ自身のJavaScriptを利用した操作 |

この違いから「Cookieは危険、JWTは安全」とは言えません。JWTをCookieに入れれば、そのCookieの送信条件を考える必要があります。JavaScriptが読める保存先に置けば、XSSによる読取りを考える必要があります。`HttpOnly`はXSSそのものを解消しません。[OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html#httponly-attribute)

状態を変える処理では、フレームワークのCSRF対策、CSRFトークンやOrigin検証、Cookie設定を構成に合わせて確認します。`SameSite`の「site」は「origin」と同義ではなく、同じ親ドメイン配下の別ホストも考慮が必要です。[OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)

この節はブラウザの話です。ネイティブアプリの保存先は、[Flutterでアクセストークンとリフレッシュトークンの保存先を分ける](/tech-note/articles/flutter/auth/access-token-memory-refresh-token-secure-storage)で扱います。

## OAuthとOIDCとSAMLは、どの結果を受け取るのか

OAuth 2.0は、クライアントがリソースへアクセスする権限を得る枠組みです。OIDCはその上に認証の層を追加し、クライアント向けの認証結果をID Tokenで伝えます。ID TokenとAPIに提示するAccess Tokenは用途が異なります。[OIDC Core §1](https://openid.net/specs/openid-connect-core-1_0.html#Introduction)

受信側は、JSONを読めたことや署名の検査だけをもって受け入れません。信頼する発行者、対象クライアント・利用先、有効期限、フローに応じたnonceなどの条件を、利用するライブラリと設定で検証します。別用途のJWTを受け入れないことも必要です。[OIDC Core: ID Token Validation](https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation)、[RFC 8725 §3](https://www.rfc-editor.org/rfc/rfc8725#section-3)

実際のOAuth連携では、Authorization Code FlowとPKCE、リダイレクトURIの扱いなども確認対象です。古い実装例をそのまま使わず、セキュリティ更新を含む仕様に合わせます。[RFC 9700 §2](https://www.rfc-editor.org/rfc/rfc9700#section-2)

SAML 2.0はXMLのAssertionを使い、認証や属性などを組織間で伝えます。企業SSOでOIDCと比較する際も、まず接続先IdPが対応するプロファイル、要求する属性、検証条件を確認します。SAMLをCookieやPasskeyと同じ層の代替品にはしません。[OASIS SAML 2.0 Core §2](https://docs.oasis-open.org/security/saml/v2.0/saml-core-2.0-os.pdf)

### 外部アカウントはどの識別子で紐づけるのか

OIDCで安定した識別子として扱うのは、検証済みID Tokenの`iss`と`sub`の組です。`sub`だけでは別の発行者と衝突し得ます。メールアドレスの一致を理由に既存アカウントを自動統合する根拠にもなりません。[OIDC Core §5.7](https://openid.net/specs/openid-connect-core-1_0.html#ClaimStability)

次はRuby 3.4向けの合成例です。**すでに信頼性の検証を終えた識別子を受け取った後の紐づけだけ**を扱います。ログイン、署名、トークン検証、アカウント連携の承認は実装していません。

```ruby file=cli-workbench/account_mapping.rb
# frozen_string_literal: true

require "json"

# 合成データです。実際の利用では、OIDC の検証を終えた結果だけを渡します。
identities = [
  { issuer: "https://idp-a.example", subject: "member-7", account: "local-a" },
  { issuer: "https://idp-b.example", subject: "member-7", account: "local-b" }
]

by_subject = {}
by_issuer_and_subject = {}
identities.each do |identity|
  by_subject[identity.fetch(:subject)] = identity.fetch(:account)
  key = [identity.fetch(:issuer), identity.fetch(:subject)].freeze
  by_issuer_and_subject[key] = identity.fetch(:account)
end

puts JSON.generate(
  subject_only_count: by_subject.size,
  subject_only_result: by_subject.fetch("member-7"),
  issuer_subject_count: by_issuer_and_subject.size,
  first_account: by_issuer_and_subject.fetch(["https://idp-a.example", "member-7"]),
  second_account: by_issuer_and_subject.fetch(["https://idp-b.example", "member-7"])
)
```

期待値は、`subject_only_count`が`1`、その値が後から入れた`local-b`です。組をキーにした場合は`issuer_subject_count`が`2`となり、`first_account`は`local-a`、`second_account`は`local-b`になります。Hashのキーの一致による置換を観察する例で、認証セキュリティ全体の検証ではありません。[Ruby 3.4 Hash](https://docs.ruby-lang.org/en/3.4/Hash.html)

Ruby 3.4.4で実行し、出力の5項目が上の値と一致することを確認しました。実認証やトークンの検証は行っていません。

## パスワード・OTP・Passkey・MFAは何を比べるのか

パスワードは利用者が知る秘密、TOTPは共有秘密と時刻から生成するコードを使います。TOTPを追加しても、利用者が偽サイトへ入力したコードを中継される攻撃への耐性が自動で付くわけではありません。[RFC 6238](https://www.rfc-editor.org/rfc/rfc6238)、[NIST SP 800-63B-4: Phishing Resistance](https://pages.nist.gov/800-63-4/sp800-63b.html#phishres)

メールやSMSでコードを受け取る場合は、その受信先の制御や復旧経路まで含めて考えます。NIST SP 800-63B-4ではメールを帯域外認証に使うことを認めず、電話網を使う方式には制約を設けています。これは同基準の保証要件であり、「メールアドレスの確認」と「その要件を満たす認証」を同一視しないための区別です。[NIST: Out-of-Band Devices](https://pages.nist.gov/800-63-4/sp800-63b.html#ooba)

Passkeyでは、WebAuthnなどを通じてサービスに対応する公開鍵の資格情報を使います。指紋や顔などによる利用者確認は認証器側で行われ、サーバーが生体情報を受け取って照合する仕組みではありません。また、同期可能な資格情報もあるため、「秘密鍵は必ず一台の端末から出ない」とは限りません。[WebAuthn: User Verification](https://www.w3.org/TR/webauthn-3/#user-verification)、[Credential Backup State](https://www.w3.org/TR/webauthn-3/#sctn-credential-backup)

MFAは製品名や画面の段階数ではなく、異なる認証要素を使う性質です。パスワードを二度入力しても二要素にはなりません。Passkeyも利用者確認の要求と結果を見ずに、名前だけでMFA成立と扱わないようにします。位置情報や普段と違う操作はリスク判断の材料で、知識・所持・生体という認証要素と同列には数えません。[NIST: Authentication Assurance Level 2](https://pages.nist.gov/800-63-4/sp800-63b.html#aal2)

## サービスの要件をどの順に決めるか

利用者のログインなら、最初にアカウントの発行元と復旧方法を決めます。自分のサービスで認証するのか、外部IdPの結果を受け取るのかで、担当する境界が変わります。その上でセッションの保存・送信・失効と、操作ごとの認可を決めます。

サービス間のAPI呼び出しでは、API KeyやOAuthのClient Credentialsが候補になります。ここで確かめる主体は人間のログイン利用者とは限りません。API Keyの意味や権限は提供サービスの契約次第なので、キーがあるだけで利用者の本人確認やすべての認可を済ませたと扱いません。[RFC 6749 §4.4](https://www.rfc-editor.org/rfc/rfc6749#section-4.4)、[OWASP REST Security: API Keys](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html#api-keys)

設計時には「どの方式が最も安全か」よりも、漏えい、フィッシング、紛失、失効、復旧の各場面で何が残るかを確認します。同じ方式名でも、登録や復旧、保存先、検証条件が変われば保護できる範囲も変わります。
