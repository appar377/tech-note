CSSで画像の幅を320pxにしても、同じ画像URLを読み込むなら、そのファイルが320画素幅へ書き換わるわけではありません。表示領域を小さくすることと、配信する画像を小さくすることは別の操作です。

ただし、ここから「ブラウザは必ず原寸の全画素を展開する」「CSSを変えても処理負荷は一切変わらない」とまでは言えません。まず、どのサイズを変え、どの値を観測しているかを分けます。

## 「320px」はファイルの幅か、画面上の幅か

| 値 | 表しているもの | 確認する場所 |
| --- | --- | --- |
| CSSの`width: 320px` | レイアウト上の幅320 CSS px | 要素のレイアウト寸法 |
| PNGなどの幅・高さ | ファイルに記録されたラスター画像の画素数 | 画像ファイルのメタデータ |
| DPR | CSS pxとデバイス側の画素の比 | `window.devicePixelRatio` |
| ファイルのbytes | 符号化された画像ファイルの大きさ | ファイル情報、配信したレスポンス |
| メモリ量 | デコード、描画、キャッシュなどに使う容量 | 対象ブラウザでの別途計測 |

CSS pxは画面の物理画素と常に1対1ではありません。DPRは表示環境やページズームにも関係します。幅320 CSS pxでDPRが2なら、横640画素を一つの解像度の目安にできます。ただし、これは画質設計の出発点であり、その画像が必ず選択されるという保証ではありません。[CSS Values: Absolute Lengths](https://www.w3.org/TR/css-values-4/#absolute-lengths)、[CSSOM View: devicePixelRatio](https://drafts.csswg.org/cssom-view/#dom-window-devicepixelratio)

また、`naturalWidth`はファイルの生の画素幅を取り出すAPIではありません。密度補正を反映したCSS pxでの自然寸法です。`srcset`を使う実験でファイル寸法と同一視しないようにします。[HTML Standard: naturalWidth](https://html.spec.whatwg.org/multipage/embedded-content.html#dom-img-naturalwidth)

## 同じ画像でCSS幅だけを変えると何が残るか

次のHTMLは、同じPNGを160 CSS pxと320 CSS pxで表示します。`srcset`や画像変換サービスを使わず、`src`も変更しません。したがって、比較対象をCSSの表示寸法に限定できます。

HTMLの隣に`assets/sample.png`を置いて使います。例と同じファイルを使う場合は、[検証で参照した画像](/tech-note/images/articles/dart-final-vs-const.png)をその名前で保存します。この例で用意したPNGは1672×941画素、1,815,321 bytesの既存ファイルを無変換で複製したものです。ファイルを読み取って確認した値であり、ネットワーク転送量の実測ではありません。

```html file=static/image-size.html
<!doctype html>
<html lang="ja">
<meta charset="utf-8">
<meta name="viewport" content="width=device-width, initial-scale=1">
<title>同じ画像でCSS幅だけを変える</title>
<style>
  body { font: 16px/1.7 sans-serif; margin: 24px; }
  img { display: block; width: 320px; height: auto; }
  pre { white-space: pre-wrap; overflow-wrap: anywhere; }
</style>
<h1>同じ画像でCSS幅だけを変える</h1>
<p>画像を読み込んでから幅を切り替えます。参照先は固定です。</p>
<button type="button" data-width="160">160 CSS px</button>
<button type="button" data-width="320">320 CSS px</button>
<img id="sample" src="assets/sample.png" width="1672" height="941"
     alt="表示寸法を比較するための同一画像">
<pre id="result" aria-live="polite">読み込み待ち</pre>
<script>
  const sample = document.querySelector("#sample");
  const result = document.querySelector("#result");
  function report() {
    const rect = sample.getBoundingClientRect();
    const timing = performance.getEntriesByName(sample.currentSrc, "resource").at(-1);
    result.textContent = JSON.stringify({
      cssWidth: rect.width,
      cssHeight: rect.height,
      dpr: window.devicePixelRatio,
      currentSrc: sample.currentSrc,
      naturalWidth: sample.naturalWidth,
      naturalHeight: sample.naturalHeight,
      transferSize: timing?.transferSize ?? null,
      encodedBodySize: timing?.encodedBodySize ?? null,
      decodedBodySize: timing?.decodedBodySize ?? null
    }, null, 2);
  }
  document.querySelectorAll("button[data-width]").forEach((button) => {
    button.addEventListener("click", () => {
      sample.style.width = `${button.dataset.width}px`;
      report();
    });
  });
  window.addEventListener("load", report);
  sample.addEventListener("error", () => { result.textContent = "画像を読み込めませんでした"; });
</script>
</html>
```

期待するのは、ボタンに応じて`cssWidth`が160または320となり、`currentSrc`は同じままであることです。高さはアスペクト比に従い、CSS幅×941÷1672に近い値になります。小数の丸めはレイアウト実装に従います。

`width`と`height`属性には画像の比率を与え、CSSで表示幅を上書きしています。属性は読み込み前の領域確保にも役立ちますが、画像ファイルをリサイズする指定ではありません。[HTML Standard: Rendering of Images](https://html.spec.whatwg.org/multipage/rendering.html#attributes-for-embedded-content-and-images)

Headless Chrome 154.0.0.0、viewport 1280×900、DPR 1、CSS zoom 1、visual viewport scale 1、既定のキャッシュ設定で確認しました。同じページで読み込み完了後に320→160→320へ切り替え、`currentSrc`は変わらず、CSS高さは約180.094→90.047→180.094となりました。この条件の`naturalWidth`/`naturalHeight`は1672/941でした。再読み込みの速さやメモリ削減量は測っていません。

## bytesの表示は「画像を展開した大きさ」なのか

HTMLの出力にあるResource Timingの値は、HTTPで取得したリソースの大きさです。名前に`decoded`とあっても、画像をRGBAの画素配列にしたサイズではありません。

| 値 | 読み方 |
| --- | --- |
| `encodedBodySize` | HTTPのContent-Encodingを取り除く前のレスポンス本文の大きさ |
| `decodedBodySize` | そのContent-Encodingを取り除いた本文の大きさ。PNGなどの画像ファイルはまだ画像形式のままです |
| `transferSize` | 転送についてAPIが報告する値。キャッシュ利用では0になる場合があります |

参照した2026年9月1日の候補勧告草案では、`transferSize`のヘッダー相当分を固定値で扱います。実際の通信パケット全体のバイト数とは区別が必要です。別オリジンではTiming-Allow-Originなどの条件で一部の値が公開されないこともあります。取得できなかった値や0を、そのまま「画像が0 bytesになった」と読まないようにします。[W3C Resource Timing](https://www.w3.org/TR/2026/CRD-resource-timing-20260901/#dom-performanceresourcetiming-transfersize)

このHTMLはResource Timingの既存エントリを読むだけで、計測のための追加`fetch`を行いません。CSS幅を変える前後の値は、同じ取得についての値を表示している可能性があります。 今回の確認では、幅を変える前後とも`encodedBodySize`と`decodedBodySize`は1,815,321、`transferSize`は1,815,621でした。同じ画像取得のエントリを読み続けており、表示幅を半分にしたことで転送ファイルが半分になった結果ではありません。

## 画素数とメモリの式はどこまで使えるか

4000×3000画素の画像なら、画素数は1,200万です。幅と高さをそれぞれ半分にすると、画素数は4分の1になります。しかし、圧縮済みファイルのbytesまで4分の1になるとは限りません。画像の内容、形式、符号化設定、メタデータなどが関わります。PNGでも画素データをフィルタリングし圧縮するため、画素数とファイルサイズは別の値です。[PNG Specification: Compression](https://www.w3.org/TR/png-3/#10Compression)

RGBAの各成分を8ビットとし、1画素4 bytesのバッファを一枚だけ持つ仮定なら、4000×3000×4で48,000,000 bytes、約45.78 MiBです。これは**仮定した一枚の画素バッファの算術**です。ブラウザ全体の使用メモリや、あるブラウザがこのバッファを確保したという実測ではありません。

次のRuby 3.4向けコードはその計算と、320×240 CSS pxに対するDPR別の画素寸法の目安だけを出します。画像の読み込みやメモリ計測は行いません。

```ruby file=cli-workbench/image_dimensions.rb
# frozen_string_literal: true

require "json"

source_width = 4000
source_height = 3000
css_width = 320
css_height = 240

puts JSON.generate(
  source_pixels: source_width * source_height,
  rgba8_one_buffer_bytes: source_width * source_height * 4,
  rgba8_one_buffer_mib: (source_width * source_height * 4 / 1024.0**2).round(2),
  half_dimensions_pixel_ratio: (source_width / 2 * (source_height / 2)).fdiv(source_width * source_height),
  targets: [1, 2, 3].map do |dpr|
    { dpr: dpr, width: css_width * dpr, height: css_height * dpr }
  end
)
```

期待する`targets`は、DPR 1で320×240、DPR 2で640×480、DPR 3で960×720です。Ruby 3.4.4でこれらの計算結果との一致を確認しました。画素バッファのbytesはあくまで仮定からの算術で、ブラウザの実メモリ量ではありません。

ブラウザがどのタイミングでデコードし、どのデータを再利用するかは別の観測事項です。表示した要素数を上の仮定値に掛けても、実際のメモリ使用量を求めたことにはなりません。[HTML Standard: Decoding Images](https://html.spec.whatwg.org/multipage/images.html#decoding-images)

## 配信する画像も小さくするには何を変えるか

表示幅を決めたら、その幅と想定DPRに合う候補画像を用意します。元画像から候補を作るのは、画像処理ツールや変換サービス、配信側の役割です。URL末尾の`?w=640`にもブラウザ共通の縮小機能はなく、配信側がそのパラメーターを解釈して初めて別の画像を返します。

候補の実画素幅を`srcset`の`640w`などで伝え、画像を表示する幅を`sizes`で伝えます。`sizes="320px"`は選択のための情報で、要素のCSS幅を設定するものではありません。CSSの実際の幅と食い違うと、選択の前提も食い違います。[HTML Standard: Responsive Images](https://html.spec.whatwg.org/multipage/images.html#introduction-3)

たとえば表示幅が320 CSS pxなら、640画素幅の候補は密度2の候補になります。ただしUAはDPR以外の条件も考慮できるため、特定のURLを必ず選ぶと固定しません。`currentSrc`で選ばれたURLを確かめ、そのファイル寸法と配信bytesを別々に確認します。

今回の静的HTMLは単一画像の比較なので、この候補選択や圧縮率は検証していません。レスポンシブ画像を評価する際は、同じ内容・比率の複数解像度を実際に用意した別の実験に分けます。

`loading="lazy"`は読み込み時期の制御です。一枚のファイルのbytesを減らす指定とは別に、画面外の画像をいつ取得するかという判断で使います。[HTML Standard: Lazy Loading](https://html.spec.whatwg.org/multipage/urls-and-fetching.html#lazy-loading-attributes)

一覧を改善するときは、表示幅を決め、配信候補を用意し、選ばれたURLと転送量を確認する順で追えます。メモリ量や描画時間に問題が残った場合に、そのブラウザと条件を固定して追加計測します。APIの名前から処理を推測しすぎない考え方は、[フレームワークAPIの抽象化が隠す境界](/tech-note/articles/architecture/execution-model/framework-api-abstraction-leaks)でも扱っています。
