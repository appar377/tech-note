PRを取り込んだ後、元のコミットをそのままたどりたいのか、PR全体を一つの変更として残したいのか、整理済みのコミットを直線状に並べたいのか。その目的によって、GitHubのマージ方式を選べます。

最終的なファイルが同じでも、mainからたどれる履歴は同じになりません。ここでは、通常の非空コミット2つを持つPRを例に、履歴の違いと、GitHubで選択できる条件を分けて整理します。

## 3つの方式は、何を履歴に残すのか

2026年10月2日に確認したGitHubの英語版ドキュメントでは、選択肢は`Create a merge commit`、`Squash and merge`、`Rebase and merge`です。通常のマージでは、実行ボタンは`Merge pull request`と表記される場合があります。[GitHubのマージ手順](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/merging-a-pull-request#merging-a-pull-request)

| 方式 | baseブランチ側へ残るもの | 元のコミットとの関係 |
| --- | --- | --- |
| Create a merge commit | マージコミットと、元のコミットへ続く経路 | 元のコミットをそのままたどれます |
| Squash and merge | PRの変更をまとめた1コミット | 元のコミット群を祖先として結ぶ方式ではありません |
| Rebase and merge | 個々の変更を載せ替えたコミット列 | GitHubでは新しいSHAになります |

通常のマージは`--no-ff`相当で、取り込みの節目となるマージコミットを作ります。squashはPRの変更をまとめ、rebaseはマージコミットを作らずに取り込みます。[GitHubの方式比較](https://docs.github.com/en/pull-requests/reference/pull-request-merges)

「squashで履歴が消える」は、baseブランチからたどれる途中のコミットが残らない、という意味で読む必要があります。この操作だけで元ブランチ上のコミットやPRの記録がすべて即座に削除される、という意味ではありません。

## 同じ変更をローカルで3通りに取り込む

以下はGitの履歴を比べるための実験です。GitHubのPR、レビュー、CI、署名、マージキューは再現しません。各方式を、同じ`main`から作った別のブランチで比較します。

以下は説明用のファイルだけを扱う再現例です。Git 2.46.0とmacOSの `/bin/bash` で実行し、記載した状態を確認しました。再現コードはGit 2.34以上を前提にしますが、その全バージョンで動作を確認したものではありません。

この記事の`bash`ブロックを上から順に一つの`example.sh`へ保存し、`/bin/bash example.sh`で実行する構成です。端末へ断片だけ貼り付けたり、`source`で読み込んだりしないでください。最初に環境を分け、新しい一時ディレクトリ内にリポジトリを作ります。既存のGit設定を変更せず、このリポジトリにだけ説明用の名前・メールアドレスと署名無効を設定します。remoteは作らず、通信もしません。

`expect_status`は終了コードが期待どおりか調べる関数です。`test`が失敗するとスクリプトはそこで止まります。出力の`REPO`が再現用リポジトリの場所です。

```bash file=setup.sh
set -eu

# Save all blocks as one file and run it with /bin/bash, not by sourcing it.
if [ "${1:-}" != "--isolated" ]; then
  exec env -i PATH="$PATH" TMPDIR="${TMPDIR:-/tmp}" LC_ALL=C \
    GIT_CONFIG_NOSYSTEM=1 GIT_CONFIG_SYSTEM=/dev/null \
    GIT_CONFIG_GLOBAL=/dev/null GIT_ATTR_NOSYSTEM=1 \
    GIT_TERMINAL_PROMPT=0 GIT_EDITOR=true GIT_SEQUENCE_EDITOR=true \
    /bin/bash "$0" --isolated
fi

demo_root=$(mktemp -d "${TMPDIR%/}/git-note.XXXXXX")
mkdir "$demo_root/repo" "$demo_root/empty-template" "$demo_root/empty-hooks"
cd "$demo_root/repo"
git --version
git init -q -b main --template="$demo_root/empty-template"
git config --local user.name 'Git Example'
git config --local user.email 'git-example@example.invalid'
git config --local commit.gpgSign false
git config --local tag.gpgSign false
git config --local core.hooksPath "$demo_root/empty-hooks"
git config --local core.autocrlf false
git config --local gc.auto 0
git config --local maintenance.auto false
git config --local rerere.enabled false
printf 'REPO %s\n' "$demo_root/repo"

expect_status() {
  expected_status=$1
  shift
  if "$@"; then actual_status=0; else actual_status=$?; fi
  if [ "$actual_status" -ne "$expected_status" ]; then
    printf 'Expected status %s, got %s\n' "$expected_status" "$actual_status" >&2
    exit 1
  fi
}
```

`feature`に`D`と`E`を作り、その間に`main`を別ファイルの変更`C`で進めます。rebaseで載せ替えが必要になるよう、意図的に分岐させています。

```bash file=merge-methods/01-history.sh
printf 'base\n' > base.txt
git add base.txt
git commit -qm 'A'
git tag base
git switch -c feature
printf 'first change\n' > first.txt
git add first.txt
git commit -qm 'D'
printf 'second change\n' > second.txt
git add second.txt
git commit -qm 'E'
git tag original-feature
git switch main
printf 'base branch work\n' > base-extra.txt
git add base-extra.txt
git commit -qm 'C'
git branch method-merge main
git branch method-squash main
git branch method-rebase main
```

`method-merge`では2つの履歴をつなぎます。先端コミットの親が2つあることと、元の`feature`先端へたどれることを確認します。

```bash file=merge-methods/02-merge.sh
git switch method-merge
git merge -s ort --no-ff -m 'M' feature
set -- $(git show -s --format=%P HEAD)
test "$#" -eq 2
git merge-base --is-ancestor original-feature HEAD
test "$(git rev-list --count main..HEAD)" = 3
test "$(git rev-list --first-parent --count main..HEAD)" = 1
printf 'CHECK merge=parents_2_original_reachable_added_reachable_commits_3\n'
```

`method-squash`では、マージ結果を準備してから1コミットにします。ローカルの`git merge --squash`だけではコミットしないため、`git commit`も必要です。[git-merge](https://git-scm.com/docs/git-merge/2.34.0#Documentation/git-merge.txt---squash)

```bash file=merge-methods/03-squash.sh
git switch method-squash
git merge -s ort --squash feature
git commit -qm 'S'
set -- $(git show -s --format=%P HEAD)
test "$#" -eq 1
expect_status 1 git merge-base --is-ancestor original-feature HEAD
test "$(git rev-list --count main..HEAD)" = 1
git diff --quiet method-merge method-squash
printf 'CHECK squash=parents_1_original_not_reachable_added_reachable_commits_1\n'
```

`method-rebase`では、元の`feature`を残したコピーを`main`へ載せ替え、その結果へfast-forwardします。最後には、比較用に「すでに祖先であるコミットへ向けた、何も載せ替えないローカルrebase」も確認します。

```bash file=merge-methods/04-rebase.sh
git switch -c rebased-feature feature
git rebase --merge -s ort --no-fork-point main
git switch method-rebase
git merge --ff-only rebased-feature
set -- $(git show -s --format=%P HEAD)
test "$#" -eq 1
expect_status 1 git merge-base --is-ancestor original-feature HEAD
test "$(git rev-list --count main..HEAD)" = 2
test "$(git rev-list --first-parent --count main..HEAD)" = 2
git diff --quiet method-merge method-rebase
test "$(git rev-parse feature)" = "$(git rev-parse original-feature)"
printf 'CHECK rebase=parents_1_original_not_reachable_added_reachable_commits_2\n'
printf 'CHECK all_methods=same_final_tree\n'

# A local no-op rebase is not GitHub's Rebase and merge implementation.
git switch -c unchanged feature
before_rebase=$(git rev-parse HEAD)
git rebase --merge -s ort --no-fork-point base
test "$(git rev-parse HEAD)" = "$before_rebase"
printf 'CHECK local_rebase_onto_existing_ancestor=sha_unchanged\n'
```

この実験で確認した結果は次のとおりです。「増える数」は、操作前の`main`からはたどれなかったコミットの数で、新しく作成したコミット数とは異なります。

| 比較ブランチ | 先端の親の数 | 元のEは祖先か | mainからたどれるコミットが増える数 |
| --- | --- | --- | --- |
| method-merge | 2 | はい | 3：D、E、M |
| method-squash | 1 | いいえ | 1：S |
| method-rebase | 1 | いいえ | 2：D′、E′ |

3つの先端のファイル内容が同じであることを、`git diff --quiet`でも照合しました。マージコミットだけを数えるのか、全親をたどるのかによって数え方が変わるため、通常のmergeでは`--first-parent`を使った件数も比較しています。

## ローカルのrebaseをGitHubの動作と同一視してよいか

上のコードの最後では、ローカルrebaseの前後でSHAが変わらないことを期待しています。載せ替えが不要なら、そのまま終わる場合があるからです。

一方、GitHubの`Rebase and merge`はcommitter情報を更新し、新しいSHAを作ると明記されています。また、最初から空だったコミットを落とす点も、通常のローカルrebaseの既定動作とは異なります。上の比較例には空コミットを含めていません。[GitHubが説明する相違点](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github#rebasing-and-merging-your-commits)、[ローカルrebaseの空コミット](https://git-scm.com/docs/git-rebase/2.34.0#Documentation/git-rebase.txt---keep-empty)

そのため、「rebaseなら元のコミットをすべてそのまま維持する」という説明も正確ではありません。残したいのが変更の粒度なのか、元のSHAなのかを区別します。

## 方式を選べないときは、履歴以外に何を見るか

GitHub上の選択肢はリポジトリで許可された方式に限られます。設定とrulesetで許可する方式が食い違うとマージできず、マージキューを使う場合はキュー側の方式が適用されます。[マージ方式の設定](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github)

また、線形履歴を要求するブランチにはマージコミットを入れられないため、squashかrebaseが必要です。それとは別に、必要な権限、レビュー、ステータスチェック、署名などの条件を満たす必要があります。DraftのPRもそのままではマージできません。[保護ブランチの線形履歴](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-linear-history)、[PRのマージ条件](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/merging-a-pull-request#about-pull-request-merges)

署名もローカル例の対象外です。とくにGitHubのrebaseで作られるコミットを、元の署名がそのまま付いたコミットとして扱うことはできません。署名必須の運用では、[GitHubの署名に関する説明](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github#rebasing-and-merging-your-commits)と実際の適用ルールを確認します。

## 調査や取り消しの単位を、先に決める

元のコミットと分岐のつながりを残したいならmerge commit、PRを一つの変更として調べたいならsquash、個々の変更を残しつつ直線状に並べたいならrebaseが候補になります。ただし、途中のコミットを単位に調査する運用なら、各コミットが意味のある状態かも確認する必要があります。

squashは取り消す対象を1コミットにまとめられますが、その後の変更と競合しないことまでは保証しません。また、同じfeatureブランチを使い続ける運用では、次回の祖先関係まで考える必要があります。[Squash後の再merge・rebase](/tech-note/articles/git/merge/squash-merge-rebase-conflict/)では、その問題を具体的な履歴で扱っています。
