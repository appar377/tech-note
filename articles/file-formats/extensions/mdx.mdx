`.mdx`は、Markdownの文章にJSXの要素やコンポーネントを組み込めるテキスト形式です。ただ拡張子を付け替えれば、ブラウザやMarkdownビューアで同じように表示できるわけではありません。MDXを処理するツールと、本文が使うコンポーネントの定義が必要です。[MDX: What is MDX?](https://mdxjs.com/docs/what-is-mdx/)

ファイルを見つけたときは、「文章にどの記法があるか」に加えて、「どの処理が読み込んでいるか」を確認します。ここではReactを使う小さな例で、本文、描画、frontmatterの役割を分けます。

## Markdownの文章に、何を足せますか？

次が説明用の`example.mdx`です。見出し、太字、インラインコードはMarkdownの記法で、`Notice`がコンポーネントです。

```mdx file=mdx-workbench/example.mdx
## 読み込みの確認

<Notice label="説明用">

本文は **Markdown** です。

</Notice>

型は `Array<T>` と書きます。
```

`Notice`という名前に、MDX共通の特別な意味はありません。この例で用意する部品の名前です。コンポーネントはimportする、文書内で定義する、描画側から渡すといった方法で利用します。どの方法が使えるかはMDXの統合方法にも依存します。[MDX: Using components](https://mdxjs.com/docs/using-mdx/#components)

Markdownのコードブロックへ`<Notice />`と書いた場合は、コードとして表示されます。本文のJSXとして書いた場合とは違います。説明したいタグまで実行対象にしないよう、文章とコード例の境界を明示します。

## コンポーネントを書けば、その場でHTMLになりますか？

一般には、MDXのコンパイラがソースをJavaScriptへ変換し、その結果をReactなどのランタイムが描画します。HTMLを配信するサイトでは、この描画をビルド時に行うこともできます。ブラウザが`.mdx`を直接解釈する仕組みではありません。[MDX: How MDX works](https://mdxjs.com/docs/using-mdx/#how-mdx-works)

次の`render.mjs`はNode.jsからHTML文字列を作る小さな例です。`next-mdx-remote` 6.0.0、React / React DOM 19.2.4を前提とします。先ほどの`example.mdx`を同じディレクトリへ置き、`Notice`を描画側から渡します。

```js file=mdx-workbench/render.mjs
import { readFile } from "node:fs/promises";
import { createElement } from "react";
import { renderToStaticMarkup } from "react-dom/server";
import { compileMDX } from "next-mdx-remote/rsc";

function Notice({ label, children }) {
  return createElement("aside", { "aria-label": label }, children);
}

export async function renderExample(source, components = { Notice }) {
  const { content } = await compileMDX({ source, components });
  return renderToStaticMarkup(content);
}

const source = await readFile(new URL("./example.mdx", import.meta.url), "utf8");
console.log(await renderExample(source));
```

生成されるHTMLには、`aside`の`aria-label="説明用"`、太字に対応する`strong`、型名に対応する`code`が含まれることを期待します。`Array<T>`は画面ではそのままの型表記になり、HTML文字列では山括弧がエスケープされます。

この例は自分で管理する文書を対象にしています。MDXにはJavaScriptへ変換される記法があるため、任意の投稿内容を通常の文章データと同じつもりで評価しません。公式コンパイラも、評価APIがJavaScriptを実行することを明記しています。[MDX compilerの評価API](https://mdxjs.com/packages/mdx/#evaluatefile-options)

## 同じMDXなのに、式が表示されないのはなぜですか？

MDXの形式としては、次のようなJavaScriptの式も書けます。

```mdx file=mdx-workbench/expression.mdx
答え: {2 + 3}
```

`@mdx-js/mdx`を使ってこの説明用の式を評価した場合は、`答え: 5`を期待します。一方、`next-mdx-remote` 6.0.0は既定で`blockJS: true`になっており、本文のJavaScript式を除去します。この設定では同じ入力でも`5`は表示されません。構文エラーになるのとは違い、式が取り除かれる挙動です。[next-mdx-remote 6.0.0の設定](https://github.com/hashicorp/next-mdx-remote/blob/v6.0.0/README.md#javascript-expressions-in-mdx)

Tech Noteも、この既定値を変更せずに使っています。属性値の式も対象なので、たとえば文字列属性の`label="説明用"`と、式を使う`label={value}`を同じ条件で使えるとは考えません。MDX一般の機能一覧だけでなく、利用中のライブラリと設定を見ます。

このサイトでは、描画側の`components/mdx-content.tsx`から`Accordion`、`YouTube`、`Video`などを渡しています。`Notice`はこの記事の独立したサンプル用で、サイト本体へ登録した部品ではありません。本文中のimportを使う`@next/mdx`の構成とも分けています。[Next.js: MDX](https://nextjs.org/docs/app/guides/mdx)

## frontmatterを書けば、下書きは自動で非公開になりますか？

次はfrontmatterを付けた説明用の文書です。

```mdx file=mdx-workbench/frontmatter.mdx
---
title: 説明用ノート
draft: true
---

## メタデータとは別の本文
```

先頭のYAMLをメタデータとして扱う処理は、MDXの標準動作とは別に必要です。`@mdx-js/mdx`だけで、`title`や`draft`の意味まで決まるわけではありません。[MDX: Frontmatter](https://mdxjs.com/guides/frontmatter/)

たとえば`next-mdx-remote`には`parseFrontmatter: true`という選択肢があります。Tech Noteではそれを使わず、`lib/mdx-source.ts`でYAMLと本文を先に分けています。本文の描画は`parseFrontmatter: false`、メタデータの型や用途は別の処理が受け持ちます。

`draft: true`を公開一覧や静的ルートから除外するのも、サイト側の実装です。ファイルの拡張子やfrontmatterを書いただけでは公開を止められません。出力するURLや検索データまで含めて、どこへ渡されるかを確認します。[Next.jsの静的exportとdraftの除外](/tech-note/articles/nextjs/github-pages/static-export/)も、この区別が必要になる例です。

## コンパイルと表示のどちらで失敗していますか？

閉じタグのない次のファイルは、意図的な構文エラーの例です。正常な本文とは別に保存して扱います。

```mdx expected-error file=mdx-workbench/expected-errors/unclosed.mdx
<Notice label="説明用">

閉じタグを忘れた例です。
```

これはMDXをJavaScriptへ変換する段階で失敗することを期待します。一方、次はJSXとしての形は整っています。

```mdx expected-error file=mdx-workbench/expected-errors/unknown-component.mdx
<MissingNotice />
```

コンパイルが通っても、`MissingNotice`を渡さずに描画すれば、そのコンポーネントが見つからないというエラーになります。構文だけの検査と、実際の部品を使う描画の検査を分ける理由です。

本文に型名や記号を書くときも注意します。MDXではエスケープされていない左山括弧や左波括弧がJSXや式の開始として解釈されるため、`Array<T>`のようなコード表記はインラインコードへ入れます。通常のMarkdownで使えるHTML記法や字下げによるコードブロックにも差があり、Markdown文書の名前だけを`.mdx`へ変更して互換性を保証することはできません。[MDXのMarkdownとの差](https://mdxjs.com/docs/what-is-mdx/#markdown)

## .mdと.mdxは、何を基準に選びますか？

文章だけを複数のMarkdownビューアで読みたいなら、まず`.md`で足りるかを考えます。文書の途中に独自UIを置き、その実装と一緒に管理するなら、`.mdx`が候補になります。MDXはReact専用のファイル形式ではなく、JSXを扱うほかの統合もありますが、このサンプルとTech NoteはReactを使っています。

移動や引き継ぎの際は、本文だけでなく次の対応を見ます。

| ファイルや設定 | 確認すること |
| --- | --- |
| MDX本文 | 独自コンポーネント、式、import、frontmatterがあるか |
| 描画側のコード | どの名前のコンポーネントを提供するか |
| プラグイン | 表・数式・コード装飾などをどう追加しているか |
| ページ生成処理 | どのURLにし、どの文書を公開対象にするか |

Node.js 21.6.1、`@mdx-js/mdx` 3.1.1、`next-mdx-remote` 6.0.0、React / React DOM 19.2.4で掲載例を実行しました。登録コンポーネントとMarkdown、型のインラインコード、式の評価と既定設定による除去、frontmatterの明示処理、未閉鎖JSXのコンパイルエラー、未登録コンポーネントの描画エラーを確認しています。別のMDX統合との互換性や、任意の外部入力の安全性を検証したものではありません。

[世界の拡張子](/tech-note/series/world-file-extensions/)から、同じシリーズの入口へ戻れます。拡張子から用途を推測した後、実際の中身と読み込み処理までたどる、という見方で読むと他の形式も整理しやすくなります。
